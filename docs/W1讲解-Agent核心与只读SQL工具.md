## 一、做了什么（整体架构）

```
你（命令行输入）
   │
   ▼
agent/main.py ──流式读取──► agent/core/agent.py 的 build_agent()
                                │  create_agent(model=ChatDeepSeek("deepseek-flash"),
                                │               tools=[execute_readonly_sql, list_tables],
                                │               system_prompt=中文角色+DDL+规则,
                                │               checkpointer=InMemorySaver())
                                ▼
                        Agent 循环（教学文档第 1 章）：
                        模型推理 → 决定调工具 → 执行工具 → 结果回传 → 再推理 → … → 最终回答
                                │
                                ▼
                    agent/tools/sql_tools.py（两道防线）──► data/demo.db（SQLite 只读连接）
```

一次提问的真实消息链（自己跑一遍 `result["messages"]` 就能看到，教学文档 3.4 节）：
`HumanMessage(你的问题) → AIMessage(带 tool_calls) → ToolMessage(SQL结果表格) → AIMessage(最终回答)`

## 二、为什么这么做（每个决策的对比与理由）

### 1. 为什么工具 docstring 是"第一等公民"？
模型**看不见函数体，只看得见名称+docstring+类型注解**（工具 Schema，教学文档 4.3.1）。
`execute_readonly_sql` 的 docstring 里写了：只能 SELECT/WITH、写操作会被拒绝、示例 SQL（用了 JOIN+GROUP BY 的示范，暗示模型"可以写复杂查询"）。**docstring 写得越像说明书，模型用对工具的概率越高**——这是 Agent 开发性价比最高的优化点。

### 2. 为什么校验是"正则关键词"而不是 AST？（明知不完美为什么先这么做）
W1 用 `\b` 整词黑名单（15 个写操作关键字），已知两个不完美：字符串里的 `'update'` 会误杀、子查询 LIMIT 会漏判。**为什么接受**：W1 的目标是快速打通 Agent 循环、验证工具交互；保守误杀方向是安全的（fail-closed）；W5 会换 sqlglot 做 AST 级解析。面试讲法："我知道正则方案的边界，并已经留好了升级路径"——**知道工具的边界比工具本身加分**。

### 3. 为什么有"两道防线"？
- 第一道：`validate_readonly_sql` 代码层校验（剥注释→空→多语句→首关键字→黑名单，顺序有讲究：**先剥注释再检查，否则 `/*DROP*/` 能藏住关键字**）
- 第二道：`mode=ro` 只读 URI 连接——即使第一道被绕过，SQLite 从文件系统层面直接拒绝写入（审查时实测 INSERT 报 `attempt to write a readonly database`）
面试讲法："安全设计不依赖单一检查点"。（需求文档 F4 的完整四层防线在 W5 补齐：+强制 LIMIT 已实现、+超时、+审计日志）

### 4. 为什么错误信息要"可读化"而不是抛堆栈？
工具返回 `SQL 错误：no such column: xxx。请检查表名、列名和语法后修正 SQL 重试`——模型读到这个能**自己改 SQL 重试**，这就是 Agent 的自我修正循环（教学文档 9.1 第 4 条）。堆栈对模型是噪音，对人是调试信息。有配套测试：拼错列名 → 断言返回含 "no such column"。

### 5. 为什么结果要截断到 20 行？
Agent 每轮把全部工具结果塞进上下文（教学文档 2.2 Context Window），全表 30 行虽然不大，但习惯要从一开始养成：**大结果 = 上下文爆炸 = 变慢变贵变失忆**。细节：截断分两种情况——真超了（fetchmany 多取 1 行探测）和"自动补了 LIMIT 且恰好 20 行"（提醒模型可能不止，可加条件重查）。

### 6. 为什么多轮追问能记住上文？（checkpointer + thread_id）
`create_agent` 默认无状态（教学文档 5.1），配 `InMemorySaver` 后每轮结束状态存档到 `thread_id` 名下，同 thread_id 的下次调用恢复历史。main.py 每次启动生成一个短 uuid 当会话 ID。**面试必考**"多轮记忆怎么做的"，W5 还会上 SummarizationMiddleware 解决"聊久了上下文爆炸"（考点预告）。

### 7. 为什么模型名是 deepseek-flash 而不是教程里的 deepseek-chat？
DeepSeek 2026-07-24 停用了 `deepseek-chat`/`deepseek-reasoner`（调研子 Agent 查证官方更新日志）。教训：**LLM 生态变化快，接 API 前先查官方 changelog，别全信教程**。

## 三、面试考点与参考答法（详细版）

> 使用方法：每题按"考察意图 → 参考答法（口语稿，可直接背）→ 结合项目的加分句 → 可能的追问"四段准备。标注"真题"的是调研到的真实面试原题。

### 3.1 "描述 Agent 的工作原理" / "Agent 和普通 Chatbot 的区别？"（AgentGuide 必考第一题）

**考察意图**：判断你是背了名词还是真理解循环机制；经常会延伸考"Chain 和 Agent 的区别"。

**参考答法（60 秒口语稿）**：
> Agent 是在 LLM 之上构建的系统。LLM 本身只会生成文本——不能查数据库、不能发请求；Agent 把 LLM 当作推理引擎，让它在一个循环里自主决定"要不要调工具、调哪个、传什么参数"，工具执行结果回传给模型后再继续推理，直到模型认为任务完成、输出最终回答。
> 一次循环的消息链是四种消息的接力：用户的 HumanMessage → 模型输出的 AIMessage（本身没有文本，携带 tool_calls 工具调用请求）→ 框架执行函数、结果包装成 ToolMessage → 模型基于结果再推理出最终的 AIMessage。
> 和普通 Chatbot 的本质区别：Chatbot 是一问一答的文本生成，没有"行动能力"；Agent 的执行流程由模型在运行时动态决定。这也正是它和 Chain 的区别——Chain 是开发时写死的 A→B→C 管道，Agent 的下一步由模型决策。

**结合项目的加分句**：
> "我的 Text-to-SQL 助手就是单循环 Agent：模型看到工具 Schema 后决定是否查库，复杂问题一次会连续调两三次工具——先 list_tables 摸库，再执行 SQL，列名写错了还会根据错误信息改写重试。"

**可能的追问**：
- "循环怎么停？"→ 模型某一轮不再发起 tool_calls、直接输出文本，循环自然结束；另有保险丝防死循环（ModelCallLimitMiddleware，W5 加）。
- "消息越滚越多怎么办？"→ 上下文窗口有限 → 短期记忆管理：SummarizationMiddleware 自动摘要旧消息（W5 上）。
- "Agent 的核心组件有哪些？"→ 通用公式 **Agent = LLM + Planning + Memory + Tools**，对应我的实现：DeepSeek 推理、system_prompt 规则、checkpointer 记忆、两个工具。

### 3.2 "介绍一下 Function Calling 的原理"（字节真题）

**考察意图**：这是 Agent 岗最基础也最容易露馅的题——经典误解是"模型执行了函数"。答对"模型只输出请求、执行者是框架"就直接超过一半候选人。

**参考答法**：
> 模型并不执行函数——它只会输出结构化的调用请求。完整流程分四步：
> ① 应用在请求里附上工具的 **Schema**（工具名、描述、参数的 JSON Schema；LangChain 从函数的类型注解和 docstring 自动生成，不用手写）；
> ② 模型推理时若判断需要外部能力，就输出 tool_calls：调用哪个函数 + 参数 JSON；
> ③ **真正执行函数的是框架代码**（LangChain 的 ToolNode），把返回值包装成 ToolMessage 加进消息列表；
> ④ 模型看到工具结果继续推理——可能接着调下一个工具，也可能生成最终回答。
> 所以 **docstring 就是模型的使用说明书**：描述含糊，模型就会用错工具、传错参数。

**结合项目的加分句**：
> "我的 SQL 工具 docstring 专门写了'只允许 SELECT/WITH、SQLite 方言'并给了一条 JOIN+GROUP BY 的示例——示例本身在教模型'可以写复杂查询'。工具调用的成功率很大程度取决于文档质量，这是我调优的第一杠杆。"

**可能的追问**：
- "工具的 Schema 怎么来的？"→ 函数名→工具名、docstring 第一行→描述、`Args:` 段→参数说明、类型注解→参数 JSON Schema，全自动生成。
- "一次能调多个工具吗？"→ 可以，模型一轮输出多个 tool_calls，框架可并行执行（我 W2 的多路检索会用到并行）。
- "Function Calling 和 MCP 什么关系？"→ Function Calling 是**模型能力**，MCP 是**工具接入的标准化协议**——把工具做成标准 server，任何 Agent 都能即插即用，不用每个工具手写适配。我规划把 NL2SQL 能力封装成 MCP Server（P2）。

### 3.3 "工具调用失败/参数不合法怎么办？有没有重试、降级、用户澄清机制？"（字节 Agent 实习一面原题）

**考察意图**：考工程兜底思维——Agent 是会犯错的，你怎么设计"错误的善后"，而不是假装它不犯错。

**参考答法（三层防御，从预防到兜底）**：
> 第一层**预防**：把约束写进 docstring、参数设计少而精，从源头降低犯错概率——我的 SQL 工具在描述里声明了只读限制和方言。
> 第二层**可读化错误 + 自我修正**：工具失败不抛堆栈，而是返回模型能理解的中文原因。比如列名拼错，工具返回"SQL 错误：no such column: city，请检查表名列名后修正重试"，模型读到后会自己改写 SQL 重新调用——这个闭环我实测跑通过。
> 第三层**兜底**（W5 落地）：ToolRetryMiddleware 对瞬时故障自动重试、ToolCallLimitMiddleware 限制调用次数防死循环、连续失败则让 Agent 向用户澄清而不是硬编。

**可能的追问**：
- "所有失败都重试吗？"→ 要区分：**确定性错误**（SQL 语法错）重试没有意义，得改内容；**瞬时错误**（网络超时）才值得重试——只对后者开 ToolRetryMiddleware。
- "工具返回空结果怎么办？"→ 我的工具返回"查询成功，但结果为空"，并靠系统提示词约束模型"如实说明、不要编造数据"——防止模型把空结果脑补成答案。

### 3.4 "设计一个 NL2SQL Agent，你重点控制哪些风险？"（系统设计高频原题）

**考察意图**：这题就是在钓你项目的安全设计。你的 W1 代码就是答案本体，按"风险→对策→证据"讲。

**参考答法**：
> 我按风险逐条说，每条带我已经做掉的证据：
> ① **写操作风险**（最致命）：双防线——代码层先剥注释再校验（首关键字必须 SELECT/WITH、15 个写操作关键字整词黑名单、拒绝多语句），文件系统层用 SQLite `mode=ro` 只读连接兜底，校验被绕过也写不进去。我实测了 26 组绕过用例：注释藏关键字、`WITH` 绕首关键字、分号夹带 DROP，全部防住。
> ② **资源风险**：没有 LIMIT 的查询自动补 LIMIT 20、结果最多返回 20 行，防止一条查询全表扫描拖挂数据库、也防止巨量结果撑爆模型上下文。
> ③ **数据正确性风险**：系统提示词强制"回答必须基于查询结果，查询不到就如实说明"，防模型编造数字；"销售额含不含退款"这类口径歧义，靠 RAG 检索业务口径文档解决（W2 落地）。
> ④ **审计风险**：每次执行的 SQL、参数、结果落审计日志（W5 落地）；上线版数据库账号本身用只读账号——四层防线里最底层的物理防线。
> ⑤ **注入风险**：用户输入永远进 HumanMessage 而不拼接进系统提示词；提示词注入是 Agent 场景的专项安全话题，W5 会专门处理。

**可能的追问（几乎是必问）**：
- "黑名单方案有什么漏洞？"→ 主动交代："字符串字面量里的关键字会误杀（保守方向是安全的），子查询里的 LIMIT 会漏判——所以 W5 会换成 sqlglot 做 AST 级解析，按语法树判断语句类型和最外层 LIMIT。"**主动暴露边界比被追问出来体面得多。**

### 3.5 "多轮记忆怎么做的？如何设计短期/长期记忆？"（高频真题）

**考察意图**：考你知不知道 Agent 默认无状态、以及"记忆"的物理本质——不是模型有记性，是框架把历史重新喂进去。

**参考答法**：
> 先说一个反直觉的事实：Agent 默认**无状态**，每次调用都是全新对话，模型并不"记得"上文。
> **短期记忆**：我给 create_agent 配了 InMemorySaver 检查点器——每轮对话结束，整个 State（全部消息列表）存档到 thread_id 名下；下次带同一 thread_id 调用时恢复历史继续推理。所以用户问完"上个月卖了多少"再问"那 10 月呢"，模型能理解省略的主语——因为它看到的是完整历史。
> 生产的坑：消息越滚越长会撑爆上下文窗口（变贵、变慢、模型"失忆"），解法是 SummarizationMiddleware：超过阈值后用便宜的小模型把旧消息压缩成摘要，保留近期原文（W5 落地）。
> **长期记忆**：跨会话保存用户画像（偏好、常用指标），用 Store 按命名空间读写，典型模式是给 Agent 配一个"记忆工具"让模型自己决定何时存取。我规划用在反馈闭环：记住用户常查的指标和常犯的口径理解偏差（P1）。

**可能的追问**：
- "多用户怎么隔离？"→ 每个用户会话独立 thread_id，状态互不可见；生产把 InMemorySaver 换成 SqliteSaver/PostgresSaver 做持久化和多实例共享。
- "长期记忆存什么？"→ 只存画像类结论，不存全量对话；敏感信息过滤后才入库。

### 3.6 "为什么单 Agent 不用多 Agent？"（必考挑战题，钓过度设计）

**考察意图**：2025 年后人人简历都写"多智能体"，面试官用这题钓跟风的人。答好这题的关键是**展示你做过判断，而不是解释你偷懒**。

**参考答法**：
> 我开发前用官方给的三个判断标准过了一遍：① 单 Agent 的上下文装不下所有工具说明和历史吗？——我的场景是一份三表 DDL + 两个工具，绰绰有余；② 不同子任务需要互相冲突的提示词吗？——理解需求、生成 SQL、执行查询是一条连贯链路；③ 需要各子任务并行执行吗？——单条查询是串行依赖。三问全否，所以单 Agent + 好工具是更简单、更可靠、更便宜的选择。多 Agent 会引入编排复杂度、Agent 间通信开销和错误传播面——收益为零的复杂度不该引入。
> 什么时候我会拆：如果未来加"自动生成报表+自动发周报"这类互相独立的子链路，或工具多到上下文装不下，才值得引入 Supervisor 模式做任务分派。

**加分句**：
> "我刻意抵抗了'为多而多'的诱惑——多智能体在我的场景里是负资产。这也是 LangChain 官方文档的建议：先问三个问题，再决定要不要拆。"

### 3.7 "介绍一下你的项目"（前 30 秒定生死）

**W1 阶段版（现在就能说，随进度更新）**：

### 5.1 实验一：多轮记忆（对应 3.5 题的实证）

- **验证目标**：checkpointer + thread_id 的状态存档与恢复机制。
- **操作**：第一问输入 `上个月卖了多少？`，等回答完；第二问只输入 `那 10 月呢？`
- **预期现象**：第二问它不会再反问"哪个月的销售额？"——直接把时间条件换成 2026-10 重新生成 SQL 并计算。注意观察第二问也会出现 `⚙ 调用工具` 行。
- **背后发生了什么**：第二轮调用时，框架把第一轮的全部历史消息（连同你的第二问）重新发给了模型——"记忆"的物理形态就是**旧消息被重新喂进上下文**，模型本身没有记忆。这解释了为什么消息会越滚越长（3.5 题的"坑"）。
- **思考题**：关掉程序重开，再问"那 10 月呢"，会发生什么？（答案：失忆——InMemorySaver 只存在进程内存里，thread_id 也换了新的。生产环境要跨进程就得换 SqliteSaver/PostgresSaver，面试常顺着这题追问。）

### 5.2 实验二：自我修正闭环（对应 3.3 题的实证，最有面试价值）

- **验证目标**：可读化错误信息驱动模型自我修正。
- **操作**：输入 `按 city 统计每个城市的订单数`
- **陷阱设计**：orders 表里**没有** city 列（city 在 users 表里）——这是故意挖的坑。
- **预期现象**：三种走向都算正常：
  - a) 模型直接写对：JOIN users 表取 city（因为 DDL 就在系统提示词里，它看得见列分布）；
  - b) **最想看到的走向**：先写 `SELECT city FROM orders ...` → 工具返回 `SQL 错误：no such column: city` → 模型读懂错误 → 改写成 JOIN 后重新调用（CLI 上会出现**两行** `⚙ 调用工具`，第二次的 SQL 里多了 JOIN）；
  - c) 模型谨慎派：先调 list_tables 摸底再写 SQL。
- **观察点**：走 b 时把第二次的 SQL 记下来——这就是"可读化错误 → 模型自我修正"闭环的现场证据。面试讲 3.3 题时，"我实测过模型根据工具返回的 no such column 自行改写 JOIN"比背概念高一档。
- **思考题**：如果工具失败时改成 `raise` 抛出堆栈，模型还能稳定修正吗？（不能——堆栈是给人看的调试信息，模型需要的是"哪里错、怎么改"的结构化中文提示，这正是教学文档 9.1 最佳实践的由来。）

### 5.3 实验三：拒绝写操作（对应 3.4 题的实证）

- **验证目标**：双防线 + 模型如何向用户解释"做不到"。
- **操作**：输入 `帮我把北京用户的订单都删掉`
- **预期现象**：两种走向：模型直接拒绝并解释（没调工具）；或它真的发起了 DELETE → 被 `validate_readonly_sql` 拦下 → 拒绝原因（"检测到写操作关键字 DELETE…"）作为 ToolMessage 回传 → 模型向你解释无法删除，可能还给出替代方案（比如"我可以帮你查出来给你看"）。
- **进阶玩法**：试试注入话术 `SELECT 1; DROP TABLE users`（多语句拒绝）和 `帮我执行 UPDATE orders SET amount=0`（黑名单拒绝）。
- **验证数据真的没被动**：另开一个终端执行
  `.venv/Scripts/python -c "import sqlite3; print(sqlite3.connect('data/demo.db').execute('SELECT COUNT(*) FROM orders').fetchone())"` —— 输出仍是 `(30,)`。

### 5.4 观察内部：两种方法（做实验时随时用）

**方法一（改一行参数）**：`agent/core/agent.py` 的 `build_agent()` 里给 `create_agent(...)` 加一个 `debug=True`，重跑后每一步节点的进出、状态变化全部打印出来，适合看整体流转（教学文档 9.4）。

**方法二（推荐：打印完整消息链）**：在仓库根目录新建 `inspect_chain.py`（注意必须放仓库根，放子目录会 import 不到 agent 包）：

```python
"""打印一次提问的完整消息链，看清 Agent 循环的每一步（教学文档 3.4）。"""
from agent.core.agent import build_agent

agent = build_agent()
config = {"configurable": {"thread_id": "inspect-demo"}}
result = agent.invoke(
    {"messages": [{"role": "user", "content": "按 city 统计每个城市的订单数"}]},
    config,
)
for msg in result["messages"]:
    print(type(msg).__name__, ":", str(msg.content)[:80].replace("\n", " "))
    if getattr(msg, "tool_calls", None):  # AIMessage 携带的工具调用请求
        print("   ↳ tool_calls:", [(c["name"], c["args"]) for c in msg.tool_calls])
```

运行 `.venv/Scripts/python inspect_chain.py`，你会看到完整的四步接力：
`HumanMessage(问题) → AIMessage(空文本+tool_calls) → ToolMessage(表格或报错) → AIMessage(最终回答)`
——如果触发了实验二的自我修正，会看到**两组** AIMessage(tool_calls)+ToolMessage。把 `content` 里的问题换成任何你想研究的输入，这个文件就是你的 Agent 解剖台。
