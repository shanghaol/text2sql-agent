## 一、做了什么（W2 全景）

W2 把 W1 的"玩具 Agent"升级成了有真实数据、有检索能力的系统：

```
用户问题 ──► 检索层（agent/rag/）
             ├─ BM25 路：jieba 分词（28 词自定义词典）→ rank-bm25 按 doc_type 分组
             ├─ 向量路：bge-small-zh-v1.5（512 维，查询侧加指令前缀）→ Chroma cosine
             └─ 自实现 RRF（k=60，平局按 (-score, id)）──► top 8 片
                        │
                        ▼
     build_system_prompt(静态骨架 + 动态【参考资料】)
                        │
                        ▼
     create_agent（DeepSeek，共享 checkpointer 多轮记忆）
                        │
                        ▼
     execute_readonly_sql ──三层只读防线──► MySQL mart 库（6 表 37 万行）
```

五张拼图：
1. **MySQL 数据集**：app/mart 双库单实例，6 表 37 万行，Faker 固定种子 8 秒生成、5.4 秒导入，勾稽自检 R1-R8
2. **三层只读防线**：只读账号（内核级）→ 会话 READ ONLY（连接池事件）→ 代码校验（中文拒绝）
3. **28 片语料**：6 份表文档（按表切）+ 11 条口径（按条目切）+ 11 条金标 QA（按条切），全部经真库核对
4. **混合检索管线**：双路召回 → RRF 融合 → top_n 注入
5. **动态提示词**：静态骨架（方言规则 + 常驻表一览 + 数据锚点）+ 动态参考资料 + 行为规则

## 二、为什么这么做（六个关键决策的完整论证）

### 2.1 SQLite 换 MySQL 后，文件级 mode=ro 没了，怎么保安全？

W1 的第二道防线是 SQLite 文件级只读（`mode=ro`），MySQL 没有等价物。三层替换方案，**每层拦的事故类型不同**：

| 层 | 机制 | 拦什么 | 为什么不能只靠它 |
|---|---|---|---|
| 只读账号 | `GRANT SELECT ON mart.*` | 一切写入、DDL、临时表、跨库访问——**权限在 DBMS 内核执行，代码任何 bug 都绕不过**（实测：INSERT 报 1142、建临时表报 1044、跨库报 1142） | 报错是英文错误码，模型拿到没法自我修正 |
| 会话 READ ONLY | Engine 的 connect 事件对每个池化连接 `SET SESSION TRANSACTION READ ONLY` | 防运维事故：将来有人误把高权限账号配进 .env | 只覆盖当前会话语义，且同样无中文提示 |
| 代码校验 | W1 黑名单 + 6 个 MySQL 新词（`FOR UPDATE`/`INTO OUTFILE` 等） | 在 SQL 出手**之前**给中文拒绝原因 | 纯文本匹配有已知边界（W5 换 sqlglot） |

**面试一句话**：三层各补其余两层的短板——账号层保证"物理上写不进去"，校验层保证"模型体验上知道为什么被拒"。

**实现细节考点**：会话只读挂在 `_build_engine` 的产物上而不是 `get_engine` 里——这样**任何路径创建的引擎都自带防线**；`set_engine` 注入新引擎时对旧引擎 `dispose()`，防 TCP 连接泄漏到 GC。这两处都是审查子 Agent 提的 P2，"事件挂载位置"这种细节就是代码审查的价值。

### 2.2 为什么数据集要有"剧情"？（月度权重 / 重尾 / 部分退款）

W3 评测集的每道题都需要**唯一且稳定的正确答案**，数据分布直接决定题目质量：

- **月度权重**（2025-11 占 13% 是双11、2026-06 占 12% 是 618）→"哪个月订单最高、为什么"成为有信号的问题；若均匀分布，这道题没有讨论价值
- **重尾用户分布**（26% 用户 0 单、头部 1% 人均 29 单）→ 复购率 ≈69% 有区分度；均匀分布下人人复购（≈100%）或人人一单（≈0%）都会让题目失效
- **部分退款设计**（1,325 笔部分退款订单 status 保持 completed）→ 故意制造"退款率"双口径：查 `orders.status='refunded'` 得 5.65%，查 refunds 表得 7.75%——**两个都"对"但口径不同**，这就是 W3 口径陷阱题的命题依据，也是面试讲"口径管理"的活例子
- **状态-年龄约束**（completed 需下单 ≥7 天前）→ 防"9 月 29 日下单 9 月 30 日已完成"的穿帮数据。生成脚本的勾稽自检 R1-R8 曾拦住一个真实 bug：部分退款分支最初会落在 shipped 订单上

**被否掉的备选**：随机均匀生成（省事，但评测题全废）；真实数据（合规风险）。

### 2.3 为什么数据锚定 2026-09-30，并在提示词里显式声明？

W1 实验一里模型主动用 `SELECT date('now')` 对齐时钟——这个好行为在**静态快照**下会变成致命伤：数据停在 2026-09-30，而真实日期是 10 月以后，模型拿 `NOW()` 算"近 7 天"必然查到 0 行。

所以双管齐下：① 提示词静态声明"相对时间以 2026-09-30 为今天"；② few-shot 金标 SQL 全部用 `DATE_SUB('2026-09-30', ...)` 示范。**被否掉的备选**：让数据滚动更新——W2 的目标是数据层稳定供评测，动态追加是维护负担且破坏可复现性（W6 后如需"新鲜数据"用同脚本重生成一期，代价是评测数字重测）。

### 2.4 为什么语料这样切？（chunking 策略——面试原题）

| 语料 | 切法 | 理由 |
|---|---|---|
| 表文档（6 片） | **按表**，1 表 1 片 | 列名和列含义强内聚，拆开就失去意义 |
| 口径（11 片） | **按条目** | 检索命中"客单价"就该只注入客单价口径，不是整本口径书 |
| QA 对（11 片） | **按条** | 注入单位 = 一个完整示例（问+SQL+说明） |

两个必须能讲的权衡：
1. **bge-small 输入上限 512 token，单表文档会超**——超的部分向量路"看不见"，但 Chroma 的 `documents` 存的是全文，BM25 路索引完整原文，**混合检索恰好兜住了向量截断**。这不是疏忽，是双路互补的具体收益。W6 消融可对比"1 片 vs 2 片"。
2. **28 片是不是太少？**——语料小是诚实的现状：质量优先于体量，W5 反馈闭环（👍 入库）会让 qa_pair 路自然增长。向量路在 28 片规模下 HNSW 近似退化为近全量比对，调 `ef_search` 无意义——**知道什么时候不用调参也是调参素养**。

### 2.5 为什么混合检索三路语料？RRF 在工程里怎么落地？

**场景化答法**（背下来）：用户问"order_amount 的口径是什么"——表名列名这种**精确 token** 靠 BM25 保命（语义向量未必把 order_amount 和"订单金额"贴得很近）；"上个月卖了多少钱"这种**自然语言**靠向量泛化（"卖"≈"GMV"≈"成交额"）。RRF 融合两头。

工程落地三细节（都写了测试）：
- **jieba 必须喂自定义词典**——实测 `order_items` 被切成 order/_/items、`客单价` 被切成 客/单价，不修词典 BM25 路对领域词全瞎。28 个词逐一断言（回归锁）
- **RRF 平局按 `(-score, id)` 排序**——分数相同按 id 字典序，保证同输入同输出（评测可复现的底线）
- **bge 查询侧加指令前缀**（"为这个句子生成表示以检索相关文章："）、文档侧不加——从 W2 就统一封装进 embedder，W6 消融时它不再是变量

### 2.6 为什么提示词是"静态骨架 + 动态注入"，还要常驻一张表清单？

检索是**概率性**的：某次查询可能召不回任何 schema 片。如果提示词里只有动态内容，模型会**幻觉出不存在的表**。所以静态骨架里常驻 6 行"表名+一句话+行数量级"——检索失灵时模型至少知道库里有什么，可以调 `list_tables` 兜底。行为规则第 1 条相应从 W1 的"先 list_tables"改为"先查参考资料，list_tables 降级为兜底"——检索命中时省一次工具往返。

**已知妥协（W3 复核）**：多轮问"那 10 月呢"时，检索层拿到的裸 query 检索不出东西，当前方案是"上一条用户消息 + 当前消息"拼接。代价是长拼接稀释关键词；若 W3 评测发现伤害单轮精度，升级为"让模型先改写 query"（P1）。

## 三、面试考点更新（在 W1 基础上新增/升级，每题四件套）

### 3.1 "构建知识库时，切块（chunking）策略怎么选？大小和重叠长度怎么定？"（RAG 高频真题）

**考察意图**：考 RAG 工程第一性功底。背"512 token、overlap 20%"这种通用答案的人过不了关——面试官想听你**按内容类型**思考。

**参考答法（口语稿）**：
> 我的语料分三类，按"语义内聚单元"分别定切法，而不是拍一个统一的 chunk_size：表结构文档按**表**切——列名和列含义是强内聚的，把列说明从 DDL 拆开两片都没有意义；业务口径按**条目**切——用户问客单价，就该只注入客单价那一条，注入整本口径书是噪声；few-shot 问答对按**条**切——它的注入单位天然就是一个完整示例。
> 大小和重叠：我的片是 80-150 字的小片，天然小于 embedding 上限，**重叠设 0**；如果是长文档场景，我会按语义边界（标题/段落）切并设 10-20% 重叠，保证被切断的句子至少在一片里是完整的。

**结合项目的加分句**：
> "还有一个实测权衡：bge-small 输入上限 512 token，我的单表文档超了——超出部分向量路'看不见'，但 Chroma 的 documents 存全文、BM25 路索引全文，**混合检索恰好兜住了向量截断**。这不是疏忽，是双路互补的具体收益。W6 我还计划消融'每表 1 片 vs 2 片'。"

**可能的追问**：
- "切太碎有什么问题？"→ 片间上下文丢失（表文档的"注意事项"会引用列说明），所以我的表文档坚持整片不切——切分粒度和内容内聚性要匹配。
- "怎么评估你的切法好不好？"→ 不看感觉看数字：检索 Recall@K + 端到端执行准确率的消融对比（W3/W6 落地）。

### 3.2 "为什么用混合检索？"（W1 答法的工程升级版）

**考察意图**：W1 阶段答"BM25 管关键词、向量管语义"只算及格；W2 之后你要能讲融合机制、可复现性和自家实证。

**参考答法（口语稿）**：
> 单路各有盲区：向量路擅长语义泛化（"卖了多少钱"≈GMV≈成交额），但对精确 token 不敏感；BM25 对表名、列名、指标名这类**必须精确匹配的关键词**是保命的，但不懂同义改写。我的场景两类查询都有——问表结构时用户直接说列名，问分析问题时全是自然语言。
> 融合用 RRF 而不是分数加权，因为量纲不可比：余弦相似度在 [-1,1]、BM25 分数无上界；RRF 只用排名（score = Σ 1/(k+rank)），天生免归一化。k=60 平滑排名差距。

**结合项目的加分句**：
> "RRF 是我自己手写的纯函数（rrf_fuse），平局按 (-score, id) 稳定排序——这个细节是被'评测跑两次结果不一样'的风险逼出来的，评测系统要求同输入同输出。"

**可能的追问**：
- "两路结果冲突听谁的？"→ RRF 奖励"两路都认可"的文档：单路第一名不如双路都进前几名——这正是混合检索的设计意图。
- "还有什么融合方式？"→ WeightedRanker 线性加权（需要分数归一化，可调"更信语义还是关键词"）；学习排序 LTR（需要标注数据，我的语料规模下是过度设计）。
- "什么时候纯向量就够了？"→ 语料全是自然语言、无领域术语时；我的语料里全是表名列名这种 token，砍掉 BM25 是自废武功（W6 消融会出有无 BM25 的对比数字）。

### 3.3 "讲一下 BM25 算法原理"（真题原话）

**考察意图**：考检索基础。很多人用过 rank-bm25 却讲不清公式——能画出三要素就超过大半候选人。

**参考答法（口语稿）**：
> BM25 是基于词频的关键词打分算法，可以理解为 TF-IDF 的改进版。对查询里的每个词，文档得分由三部分组成：① **词频 TF**：词在文档里出现越多越相关，但做**饱和处理**——出现 10 次不会是 1 次的 10 倍（参数 k1 控制饱和速度，默认 1.2）；② **逆文档频率 IDF**：越稀有的词信息量越大，"退款率"比"的"值钱；③ **文档长度归一化**：长文档天然词频高，参数 b 控制惩罚力度（b=1 完全按相对长度惩罚，b=0 不惩罚，默认 0.75）。
> 我的场景里它负责精确匹配：用户问 order_amount，BM25 把这个 token 的权重精确命中到含它的表文档。

**可能的追问**：
- "中文为什么要分词？"→ BM25 按词项（term）匹配，中文没有空格，jieba 切词就是在构造词项。而且必须喂自定义词典——我实测过不喂的话 order_items 被切成 order/_/items、客单价被切成 客/单价，领域词全军覆没。
- "BM25 有什么局限？"→ 纯词项匹配，不懂同义（"成交额"≠"GMV"）、不懂语序——这正是要用向量路互补的原因。

### 3.4 "NL2SQL 怎么控制风险？"（W1 两层 → W2 三层，系统设计原题升级版）

**参考答法（口语稿）**：
> W1 我做了两道防线（文本校验 + SQLite 文件级只读）。迁到 MySQL 后 mode=ro 没有了，重新设计成**三层，每层拦的事故类型不同**：
> ① **只读账号**（主防线）：`GRANT SELECT ON mart.*`，权限在 DBMS 内核执行，代码任何 bug 都绕不过——我实测 INSERT 报 1142、建临时表报 1044、跨库访问报 1142；
> ② **会话级 READ ONLY**：连接池每个新物理连接建立时自动执行 `SET SESSION TRANSACTION READ ONLY`——防的是"将来有人误把高权限账号配进配置文件"这类运维事故；
> ③ **代码校验**：黑名单从 W1 的 15 词扩到 21 词，加的 6 个是 MySQL 特有攻击面——`SELECT ... FOR UPDATE` 是合法锁读、`INTO OUTFILE` 能以 SELECT 开头写服务器文件系统，SQLite 根本没这些语法所以 W1 防不到。
> 代码层存在的独立价值：前两层只甩英文错误码，它给**中文可读拒绝原因**，模型拿到能自我修正。W5 再上 sqlglot AST 解析替换文本匹配、执行超时和审计日志。

**可能的追问**：
- "为什么不全依赖数据库账号？"→ 安全和可用性分层：账号层保证写不进去，但它只说 denied，模型不知道怎么改；代码层说"检测到 FOR UPDATE，本工具只允许 SELECT"——同一次拒绝，两种信息量。
- "黑名单的漏洞？"→ 主动交代（W1 已备好的答案）：字符串字面量误杀 + 子查询 LIMIT 漏判，W5 换 AST。

### 3.5 "Embedding 模型怎么选的？为什么本地跑？"（新增，高频）

**参考答法（口语稿）**：
> 四个维度：语言匹配、维度与质量、成本、部署约束。我选 BAAI/bge-small-zh-v1.5：中文专门优化；**512 维 small 档是刻意的内存决策**——部署服务器只有 2G 内存，ONNX 常驻约 200-300MB，base/large 档直接爆预算；fastembed 跑本地 ONNX，零 API 成本、离线可部署，还和我简历上的 ONNX Runtime 经验呼应。
> 一个使用细节：bge 系模型查询侧要加指令前缀（"为这个句子生成表示以检索相关文章："），文档侧不加——我从 W2 就封装进 embedder，保证口径统一，W6 消融时它不再是实验变量。
> 备选：阿里 DashScope text-embedding-v3（API 方案，省本机内存）——服务器内存宽裕时的合理选择；我把 embedder 做成了可注入接口，换实现不动上层，这就是回退路径。

**可能的追问**：
- "为什么不用 OpenAI text-embedding-3？"→ 国内网络稳定性、按量成本、数据不出域三个理由。
- "small 档效果打折怎么办？"→ 我的语料只有 28 片，small 的区分度绰绰有余；语料上万条再谈升档——**按规模选型，不为大而大**。

### 3.6 "RAG 检索质量怎么评估？"（W3 主战场，先备框架）

**参考答法（口语稿）**：
> 分两层。**检索层**：Recall@K——每道评测题预先标注"金标片"（这题必须召回的表文档/口径条目），看它是否进了 top-N。我的金标 QA 天然就是标注：问"上个月 GMV"就应该召回 glossary:gmv 和 qa_003。
> **生成层**：执行准确率——金标 SQL 和模型 SQL 各自在库里执行，**结果集一致才算对**。为什么比结果不比文本？因为同义 SQL（JOIN 写法不同、列序不同）应该算对，文本相似度会误伤。
> 方法论上最重要的是**消融实验**：基线 → 加 BM25 → 加 rerank，每步出数字，每个优化的贡献才能拆解——我简历上"准确率从 X% 到 Y%"的每组数字都对应一个消融开关。

**可能的追问**：
- "执行准确率的漏洞？"→ 也要防：结果碰巧相同但 SQL 语义错（比如都返回 1 行但口径错）——所以金标要带"期望口径"标注，口径错=错，即使数字恰好一样。

### 3.7 "多轮追问时，检索层怎么办？"（诚实妥协题）

**参考答法（口语稿）**：
> 先点破问题：Agent 的多轮记忆在 checkpointer 里，但**检索层是无状态的**——用户第二轮说"那 10 月呢"，拿这个裸 query 去检索什么都召不回。很多实现直接拿每轮输入检索，多轮一问就露馅。
> 当前方案：检索 query = 上一条用户消息 + 当前消息拼接。代价明确：长拼接稀释关键词，是有损妥协。
> 升级路线：让模型先做指代改写（"那 10 月呢"→"2026 年 10 月的 GMV 是多少"），用改写后的 query 检索——W3 评测如果证明拼接伤害了单轮精度就上。这是 plan-and-known-tradeoff，不是没想过。

**可能的追问**：
- "query 改写本身不也要一次 LLM 调用吗？"→ 对，多一次延迟和成本——所以要用评测数字决定值不值，而不是拍脑袋上。

## 五、动手实验（做完才算消化 W2）

### 5.0 实验准备与观察工具

- 服务在跑的确认：`docker ps` 有 text2sql-mysql；`python -m agent.rag.build_index` 输出 28 片；`.env` 三类配置齐全
- **inspect_chain.py 已升级**：每轮会打印检索 query 和注入的片 id——W2 的每个实验都建议用它跑一遍，CLI 看结论、inspect 看真相（W1 实验 2 的教训）
- 所有实验的对照数字都在 `docs/qa_verification.md` 里存档（真实核对值），判断模型答没答对不用猜

### 5.1 实验一：口径检索改变 SQL 行为（RAG 价值的铁证）

- **验证目标**：业务口径文档被检索注入后，模型的 SQL **选择**发生可观测的改变——这是"RAG 有没有用"的最直接证据
- **操作**：输入 `9 月份的退款率是多少？`
- **预期现象（三种走向都值得记录）**：
  - a) **最佳走向**：注入 `glossary:refund_rate` → 模型写 `SUM(refunds.amount)/SUM(payments.amount)` → 答出 **≈7.75%**，并且按行为规则自报口径（"按退款金额口径"）
  - b) **陷阱走向**：模型用 `orders.status='refunded'` 过滤 → 算出 **5.65%**——这不是 bug！这正好漏掉了 1,325 笔部分退款订单（它们的 status 是 completed），**错答样本本身就是 W3 评测集的命题素材**，遇到请原样记录
  - c) **优秀走向**：模型两个口径都算、都报——说明它读到了双口径条目且理解了"必须声明口径"的规则
- **背后机制**：glossary 的 refund_rate 条目白纸黑字写着"必须查 refunds 表，status 会漏掉部分退款"——检索把它送进上下文，模型的 SQL 生成随之改变。对比：W1 的模型在无口径文档时是"自由发挥"
- **思考题**：如果把 glossary.md 里的 refund_rate 条目删掉重建索引，走向 b 的概率会上升吗？（这就是 W6 消融实验的微缩版——用单条语料的增减验证检索的因果作用）

### 5.2 实验二：RETRIEVER_TOP_N=0 对照（感受 RAG 的边际价值）

- **验证目标**：动态检索注入到底贡献了什么——用"抽掉它"的对照法看塌方点在哪
- **操作**：`.env` 里 `RETRIEVER_TOP_N=8` 改成 `0` → 重启 `python -m agent.main` → 问 `上个月 GMV 多少？环比呢` → 改回 8 重启，再问同样两句
- **预期现象**：top_n=0 时【参考资料】整段为空（代码里有空检索兜底文案），但**不会崩**——常驻的 6 行表一览和 MySQL 方言规则还在。模型仍能写出能跑的 SQL，但：
  - 口径大概率出错：可能直接 `SUM(order_amount)` 不滤状态（算出 ~20M 级别，虚高 26.5%），也可能不知道走 payments 表
  - "自报口径"的行为大概率消失（规则 3 还在，但没有口径内容可报）
  - 数字对照：正确版 16,029,955.34 vs 降级版大概率不同——差值就是 RAG 的贡献
- **背后机制**：这正是"检索失灵时的降级路径"的真实样子——常驻表一览防住了"幻觉出不存在的表"（最恶性），但防不住"口径算错"（更隐蔽）。**防恶性错误靠静态兜底，保口径质量靠检索**
- **思考题**：为什么表清单可以常驻、11 条口径不能也常驻？（表清单 6 行成本极低且永不增长；口径全量常驻 = 放弃 RAG——口径条目会随业务增长，token 账会失控。这个权衡就是"静态兜底 vs 动态注入"的边界）

### 5.3 实验三：同义改写鲁棒性（双路互补的直观体验）

- **验证目标**：语义路 + BM25 路对不同措辞的覆盖能力
- **操作**：三个问法各跑一遍（用 inspect_chain 对比注入片）：
  1. `上个月 GMV 多少`（标准问法，语料里的原词）
  2. `上月成交额是多少`（同义词，语料正文里出现"成交总额"）
  3. `9 月卖了多少钱`（口语化，语料里完全没有"卖"这个说法）
- **预期现象**：三种问法的注入片高度重叠（gmv 口径 + qa_003 都应出现），算出的数字一致（16,029,955.34）；但注入片的 RRF 排名和个别片会有差异——**top 集合稳定、排序对措辞敏感**
- **背后机制**：问法 2 靠语义路（"成交额"的向量和"GMV（成交总额）"很近）+ BM25 的"成交"token 双保险；问法 3 里"卖"这个口语词是语义路在救——它本身不在语料里，但它的 embedding 离 GMV/Sales 类文本近
- **思考题**：构造一个三条路都救不了的问法？（比如"上个月赚了多少钱"——"赚"可能被理解成利润而非销售额，这已经不是检索问题而是语义歧义，需要澄清反问能力——W5 的 HITL/澄清机制话题）

### 5.4 实验四：方言纠错（提示词规则 + 错误可读化的合力）

- **验证目标**：系统提示词的方言规则能不能防患于未然；万一没防住，错误可读化能不能兜住
- **操作**：输入 `用 strftime 按月统计订单量`（故意用 SQLite 的函数名）
- **预期现象（两种走向）**：
  - a) **大概率**：模型读到【数据库】段的方言规则（"禁止 SQLite 的 strftime"，白纸黑字），直接用 `DATE_FORMAT` 生成——规则在生成端就生效，根本不报错
  - b) **小概率**：模型照写了 strftime → MySQL 报 1305 FUNCTION does not exist → 工具的 errno 映射返回"SQL 语法错误，注意这是 MySQL 方言 + 原文" → 模型改写重试（inspect_chain 里能看到两次 execute_readonly_sql）
- **背后机制**：走向 a 是"提示词层预防"、走向 b 是"错误层自愈"——两层都已实现，这个实验让你亲眼看到防线的纵深
- **思考题**：为什么不在工具里静默把 strftime 替换成 DATE_FORMAT？（三个理由：① 偷改 SQL 会掩盖方言错误模式，而 W3 评测恰恰要统计这些错误模式；② 静默改写让模型得不到反馈，永远学不会正确方言；③ 工具应该诚实——改写输入是隐藏的副作用，违背最小惊讶原则）
