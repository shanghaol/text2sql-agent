## 1. BYOK 密钥管理（本周核心新需求，重点设计）

### 1.1 威胁模型与总体链路

**要防什么、不防什么**（先说清楚边界，加密方案才有评判标准）：

| 威胁 | 是否防 | 手段 |
| --- | --- | --- |
| key 明文落库（拖库即泄漏） | 防 | AES-256-GCM 加密，主密钥环境注入（§1.3/1.4） |
| key 进传输日志/应用日志/访问日志 | 防 | key 只走 HTTP 头与请求体，绝不进 URL；日志脱敏规则 §1.5 |
| 内网嗅探（浏览器→服务器） | 防 | HTTPS 全站（§5.3） |
| Java→Python 内网链路被窃听 | 接受风险 | 同 Docker bridge 网络内明文传 key；Python 容器**不发布任何端口**，宿主机外不可达（§5.1）。再加密一层的收益（防宿主机 root/容器逃逸）低于复杂度成本，被否——见 §1.5 备选讨论 |
| 前端 XSS 偷 localStorage 里的 key | 防 | 前端**不存 key**：录入后只保存掩码（§1.3 论证点） |
| 站方滥用用户 key 跑自己的量 | 结构性防 | 服务器上**不配置站点级 DEEPSEEK_API_KEY**（compose 里该变量注释掉，§5.5）；Python 的 env 回退只在开发机 CLI/评测场景生效 |
| 用户 key 被别的用户用 | 防 | key 与账号绑定 + 每请求按 JWT 身份取本人 key；SSE 响应不回显 key |

**全链路一张图**（后文反复引用编号 ①-⑥）：

```
浏览器（localStorage 只存掩码，无明文 key）
   │ ① HTTPS：PUT /api/user/key {key}        POST /api/chat {question, threadId}
   ▼
Caddy（TLS 终结，flush_interval -1 保 SSE）
   ▼
Java :8080（只发 8080 给 Caddy 的容器网络）
   │ ② JWT 校验 → 限流/并发闸 → 读 api_key 行 → AES-GCM 解密（微秒级，不缓存明文）
   │ ③ POST http://python:8000/agent/chat（Docker 内网，非 HTTPS）
   │      头：X-User-LLM-Key: <明文key>   X-User-Id: <userId>   X-Internal-Token: <共享密钥>
   │ ④ 逐事件透传 SSE 给浏览器，同时旁路解析 delta/tool/done
   │ ⑤ 流结束 → 写 query_history → 向流内注入 saved 事件（带 history_id）
   ▼
Python :8000（不发布端口，仅 compose 内网可达）
   │ ⑥ 校验 X-Internal-Token → thread_key = f"u{userId}:{threadId}"（按用户隔离命名空间）
   │     prepare_turn()（检索+prompt+agent）→ ChatDeepSeek（按 key 指纹缓存实例）→ 流式
   ▼ 只读账号 text2sql_ro                    ▼ 用户的 key
MySQL mart 库                              api.deepseek.com
```

### 1.2 Key 的录入与校验

**录入入口**：前端设置页（§4.1），密码型输入框 + 明文切换；提交 `PUT /api/user/key`。录入流程五步：

1. 前端格式预检 `^sk-[0-9a-zA-Z]{20,}$`（宽松匹配，只挡手滑，不冒充权威校验）→ 不过就地红字，不发请求；
2. Java 收到后先做同样格式预检（防绕过前端），再**同步调用 DeepSeek 轻量接口校验**；
3. 校验通过 → AES-GCM 加密 → upsert `api_key` 行（一人一把，重复录入走更新、IV 重新随机生成）→ 返回掩码与指纹；
4. 校验失败 → **不落库**（状态机里没有"已存的无效 key"这种状态，省掉一整类处理）→ 返回 400 + 可读原因；
5. 前端展示"已配置：`sk-****ab3d`（指纹 `1a2b3c4d`，上次校验 2026-10-11 14:30）"。

**校验接口选型：`GET https://api.deepseek.com/models`（Bearer 头带 key），否决"1-token completion"。**

| 方案 | 成本 | 能验出什么 | 验不出什么 |
| --- | --- | --- | --- |
| **GET /models（选定）** | 零 token、免费、幂等 | key 存在与有效性（无效 key 返回 401） | 余额是否为 0 |
| POST /chat/completions + max_tokens=1 | 消耗（极小但非零）、非幂等 | 上述 + 余额可用性 | （比 /models 多验余额一项） |

选 /models 的理由：① **免费且幂等**——"重新校验"按钮和限流重试都可以随便触发，1-token 方案每次都花钱且是有副作用的调用，不适合做可重复的校验动作；② 余额缺口由**对话时错误映射兜住**：DeepSeek 余额不足返回 402（§1.6 错误表），前端据此提示"请充值"并跳设置页——校验期验不出的，使用期第一时间报出，延迟从"录入时"变"首轮对话时"，代价可接受；③ DeepSeek 官方文档即以 /models 作为 key 有效性验证方式，权威无疑义。被否 1-token 的补充理由：max_tokens=1 的响应解析、计费到账延迟等细节反而引入新的不确定。
（标注验证项 §9.2-2：/models 对有效/无效/余额为零的 key 的实际返回码与响应体，编码首日实测。）

**错误提示文案表**（校验失败的前端表现，错误码见 §1.6 汇总表）：

| DeepSeek 侧结果 | Java 返回 | 前端提示 |
| --- | --- | --- |
| 200 | 200，落库 | "配置成功" |
| 401 | 400 `key_invalid` | "Key 无效或已被删除，请到 DeepSeek 平台核对" |
| 429 | 429 `verify_rate_limited` | "校验请求过于频繁，请一分钟后再试" |
| 超时/网络不通（Java 侧 5s 超时） | 502 `verify_unreachable` | "DeepSeek 校验服务暂时不可达，请稍后重试（本次未保存）" |

### 1.3 Key 的存储：AES-GCM 落库（主方案）vs localStorage 透传（被否但记录）

**主方案：与账号绑定，AES-256-GCM 加密落 app 库 `api_key` 表**。这是需求 v1.3 的明文要求（"录入/校验/**加密存储**/按请求传递"），本节论证它的技术合理性并完整记录备选取舍。

**为什么选 AES-GCM（而不是 AES-CBC / 只哈希）**：
- GCM 是**认证加密**：密文被篡改时解密直接抛 `AEADBadTagException`——拖库者改一个字节都无法静默伪造，这是 CBC（无内建完整性）给不了的；
- JDK 17 **内置**（`javax.crypto.Cipher` + `SecretKeySpec`），零第三方依赖，用户可逐行讲解——正好落在"用自己的舒适区实现 AI 工程关键环节"的项目叙事上；
- 被否 AES-CBC：还要自己拼 HMAC 才有完整性，两套原语两倍讲解成本；被否"只存哈希"：哈希不可逆，而对话时必须拿回明文 key，哈希根本不满足需求（哈希只用于**指纹**这个辅助字段，§1.5）。

**加解密要点**（Java `KeyCipherService`，设计骨架，编码按此实现）：

```java
// 加密：IV 每次重新随机生成（12 字节），GCM tag 128 位
byte[] iv = new byte[12]; secureRandom.nextBytes(iv);
Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
c.init(Cipher.ENCRYPT_MODE, masterKey, new GCMParameterSpec(128, iv));
byte[] ct = c.doFinal(key.getBytes(UTF_8));      // ct 已含 16 字节 tag
// 存：key_iv = iv, key_ciphertext = ct, key_fingerprint = sha256(key) 前 8 hex, key_masked = "sk-****" + 后 4 位
// 解密：new GCMParameterSpec(128, key_iv) 反向 doFinal；tag 不匹配抛 AEADBadTagException → 映射"主密钥不匹配，请联系管理员重置 key"
```

- 35 字节左右的 key 加密后约 51 字节，`VARBINARY(255)` 留足余量；
- **GCM 的 IV 复用是灾难性错误**（同 key 同 IV 两次加密会泄漏明文异或），IV 必须每次 `SecureRandom` 重新生成并与密文同存——这条写进代码注释，是面试可讲的密码学细节；
- 加解密发生在 `KeyService` 服务层**显式调用**，不藏在 JPA Converter/TypeHandler 魔法里——用户要求能讲清每一行，显式加密点=可讲解点；
- 每次对话请求现读现解密（AES-GCM 对 35 字节是微秒级），**Java 内存不做明文 key 缓存**——省掉一层失效管理，也缩小明文驻留面。被否"解密结果缓存进 Caffeine"：收益是省微秒级运算，代价是多一套缓存失效逻辑+明文驻留内存，净负。

**备选方案 B：仅 localStorage 透传、服务端不落库**（完整记录，供 §10 拍板）：

| 维度 | A：AES-GCM 落库（推荐） | B：localStorage 透传不落库 |
| --- | --- | --- |
| 服务端静态风险 | 密文+主密钥分离，拖库不泄漏 | **零静态风险**（服务端根本没有 key） |
| 传输面 | 录入 1 次 + 每轮对话 Java 侧解密后内网转发 | **每轮对话**都从浏览器带明文 key 出发（HTTPS 保护下风险可控但暴露面大） |
| 多设备/换浏览器 | 登录即用 | 每个设备都要重录 |
| XSS 后果 | 偷到的只是掩码 | localStorage 里的明文 key 直接丢失 |
| 实现量 | 加密服务+一张表（~150 行 Java） | 几乎为零 |
| 学习/简历价值 | AES-GCM、主密钥管理、日志脱敏——安全叙事完整 | 无新增内容 |
| 与需求 v1.3 的关系 | **符合**（"加密存储"是明文要求） | 偏离需求，需用户显式改需求才可用 |

结论：**推荐 A**。B 唯一的实质优势是"服务端零密钥托管"的极致姿态，但它把暴露面从"一次性录入"挪到"每轮请求"，且丢掉多设备体验与本项目最想讲的密钥管理叙事。若用户选 B，§1.4/§2.2 的 `api_key` 表与 AES 部分整体砍掉，Java 只做转发——工单 T1 工作量减 1/3，其余设计不变（链路 ③ 的头照旧）。

**V1 限制（写明不是疏忽）**：一人一把 key（`UNIQUE KEY uk_api_key_user`）。多把命名 key 需要选择 UI 与默认 key 概念，演示场景无此需求。被否"一人多把"：无使用动机，纯增复杂度。

### 1.4 主密钥管理

| 项 | 方案 |
| --- | --- |
| 生成 | `openssl rand -base64 32`（或 Python `secrets`）→ 256 位随机，Base64 编码 |
| 注入 | 环境变量 `BYOK_MASTER_KEY`。开发机放 `.env`（已在 .gitignore）；服务器放 `deploy/.env.prod`（**不进 git**，§5.5 部署清单里标注手工放置） |
| 加载 | Java 启动时 `@PostConstruct` 读取并构 `SecretKeySpec`；**缺失即启动失败**（fail-fast，缺主密钥的 BYOK 应用等于裸奔，不许带病运行） |
| 入 git 防线 | `.gitignore` 已有 `.env`；新增检查：T1 验收时 `git log -p | grep BYOK_MASTER_KEY` 应无结果 |
| 丢失后果 | 所有已存 key 不可解密 → 用户到设置页重新录入即可（无数据损失，写入运维手册即可，不做补救代码） |
| 泄漏后果 | 运维动作：清空 `api_key` 表 + 通知重录（demo 规模发一条公告即可）；代码不做在线轮换 |
| 轮换预留 | `key_version` 列（默认恒 1）——将来多主密钥时按版本选 key 解密、惰性重加密，现在不实现 |

被否备选：**按用户派生密钥（HKDF(master, user_id)）**——单行泄漏不影响他人，理论上更优；但对 35 字节 key 的场景属于密码学军备竞赛，多一套 KDF 讲解成本，V1 明确不做（面试可答"知道更优解、按成本选了简单解"）。**KMS/云密钥服务**——2核2G 自托管服务器引入云依赖，否。

### 1.5 Key 的传输链路与日志脱敏规则

**三段链路的取舍**：

| 段 | 方式 | 安全论证 |
| --- | --- | --- |
| 浏览器 → Java | HTTPS（Caddy 终结 TLS，§5.3）；key 只在 **POST/PUT body** | body 不进任何访问日志——这是"绝不入 URL"的根本原因：URL 会落进 uvicorn/Caddy/nginx 的 access log 与浏览器历史，header/body 不会 |
| Java → Python | Docker compose 内网 HTTP，头 `X-User-LLM-Key` | 同一 bridge 网络、Python 不发布端口（宿主机 `ss -tlnp` 不可见），链路两端都在单台宿主机内存/环回范围内。**再加密备选被否**：应用层再加密需要双方共享第二把密钥+加解密代码，防的是"宿主机被 root"——那个威胁模型下 MySQL 密码、JWT_SECRET 也全丢了，单加密 key 是安全剧场。记录为"若未来多机部署，此段必须升级为 mTLS 或应用层加密"的已知边界 |
| Java 内部 | 解密后即用即弃，不缓存、不落盘 | §1.3 |

**头名定案**：`X-User-LLM-Key`（任务指定，沿用）。配套两个内部头：`X-User-Id`（Java 鉴权后注入，Python 据此做 thread 命名空间与 @tool 调用归属）、`X-Internal-Token`（Java/Python 共享密钥，值来自环境变量 `INTERNAL_TOKEN`，Python 中间件校验，防止将来有人误开 Python 端口后内部接口裸奔——30 行换一层纵深，值得）。

**日志脱敏规则（可执行的规则表，编码与 review 逐条对照）**：

| # | 规则 | 落点 |
| --- | --- | --- |
| 1 | BYOK 相关端点（/api/user/key、/api/chat）**不打请求体全文**；要打就打 `len=` 与 `fp=<指纹>` | Java Controller/Service 日志语句 |
| 2 | key 的唯一日志替身 = `key_fingerprint`（SHA-256 前 8 hex）+ 长度，如 `key saved userId=42 fp=1a2b3c4d len=35`；指纹同时落库（§2.2），滥用排查按指纹反查用户而无需解密 | Java `KeyService` |
| 3 | key 绝不进 URL/查询串（所有 BYOK 与对话端点均为 POST/PUT body）——URL 会进 uvicorn access log、Caddy 访问日志、浏览器历史 | 接口设计层面（§2.4/§3.2） |
| 4 | Java 侧关闭一切 wire-level 日志（JDK HttpClient 不开日志；确认无 `CommonsRequestLoggingFilter` 之类的过滤器挂在路由上） | T1 验收 grep |
| 5 | Python：uvicorn access log 默认只记 method+path+status（不含 header），**保持默认即可**；httpx logger 级别设 WARNING（DEBUG 级会打请求头；openai SDK 对 Authorization 有默认 redact，但不赌） | `server.py` 启动时 `logging.getLogger("httpx").setLevel(logging.WARNING)` |
| 6 | Python 异常处理只 log 异常类型+message+指纹，不 log 原始堆栈里的 request 对象/headers；向上游返回的错误体只含业务错误码与可读 message | `server.py` 异常映射（§3.3） |
| 7 | SSE 下行流不回显 key；`error` 事件不携带 DeepSeek 原始报错全文（映射为业务码） | 事件契约（§3.2） |
| 8 | MySQL 全库无明文 key 列（只有 ciphertext/iv/fingerprint/masked） | §2.2 DDL |
| 9 | 验收动作：用假 key 走一遍录入+对话+失败路径后，`docker logs <java> 2>&1 | grep -c "sk-"` 必须为 0；Python 日志同理 | T1/T2 验收项 |

### 1.6 Python 侧改造：每请求 key、客户端复用、错误语义

**`build_agent` 签名扩展**（`agent/core/agent.py`，最小 diff）：

```python
def build_agent(system_prompt: str, api_key: str | None = None):
    # api_key=None：与现状逐字节等价（ChatDeepSeek 走环境变量回退）——CLI 与评测路径零变化
    model = get_chat_model(api_key)      # 内部走客户端缓存，见下
    ...

_LLM_CACHE: OrderedDict[tuple[str, str], ChatDeepSeek] = OrderedDict()
_LLM_CACHE_LOCK = threading.Lock()

def get_chat_model(api_key: str | None) -> ChatDeepSeek:
    cache_key = (hashlib.sha256(api_key.encode()).hexdigest()[:16] if api_key else "__env__", DEEPSEEK_MODEL)
    with _LLM_CACHE_LOCK:
        if cache_key in _LLM_CACHE:
            _LLM_CACHE.move_to_end(cache_key)
            return _LLM_CACHE[cache_key]
    kwargs = {"model": DEEPSEEK_MODEL, "api_base": "https://api.deepseek.com", "temperature": 0}
    if api_key:
        kwargs["api_key"] = api_key          # 只有显式给了才传——None 时绝不多传参数
    model = ChatDeepSeek(**kwargs)
    with _LLM_CACHE_LOCK:
        _LLM_CACHE[cache_key] = model
        while len(_LLM_CACHE) > LLM_CLIENT_CACHE_SIZE:   # 默认 16
            _LLM_CACHE.popitem(last=False)               # LRU 逐出（丢弃引用，由 GC 回收 httpx 连接池）
    return model
```

**客户端复用策略论证（任务点名要讨论"按 key 哈希缓存 ChatDeepSeek 实例"）**：

- **为什么缓存**：每个 ChatDeepSeek 内部持有一个 openai SDK client（含 httpx 连接池）。不缓存 = 每轮对话新建 TCP+TLS 到 api.deepseek.com（约 100-300ms 握手 + 2 核机器上可感的 CPU）。现状 CLI 每轮 `build_agent` 其实一直在付这个钱（单用户无感），服务化多用户后必须收口。
- **缓存键 = sha256(key)[:16] + 模型名**：不缓存明文 key 做键（避免明文常驻 dict 内存），哈希前 16 位碰撞概率在此规模可忽略；不同用户不同实例，auth 隔离天然正确。
- **容量 16（可配）**：演示规模并发用户个位数，16 个 httpx 池的内存（每个 KB~MB 级）在 2G 预算内忽略不计；LRU 保证有界。标注验证项 §9.2-4：底层 httpx client 的显式 close 途径（能找到就逐出时显式关，找不到靠 GC——实测确认无连接泄漏告警）。
- **被否方案一"每请求 new ChatDeepSeek"**：每轮付 TLS 握手税，2 核 CPU 上是真金白银；
- **被否方案二"全局单例 client、每请求换 api_key"**：openai SDK 的 api_key 在 client 构造时绑定，并发请求下换 key 是数据竞争——两个用户的请求可能带上对方的 key，这是**安全事故**不是性能问题，绝不可为。此条是本设计里最想让人记住的反面教材。

**无 key / 无效 key 的错误语义（HTTP 状态码约定）**：

关键设计点：**"无效 key"只能在流中报，不能在流前报**。DeepSeek 的 401 发生在第一次对话请求时——那时 SSE 已经 200 + 开始发送。提前预检（Python 或 Java 每轮先 ping 一次 DeepSeek）会让每轮对话多一个 RTT（300-600ms），否决。因此：

- **流前**（HTTP 状态码 + JSON body，前端 fetch 在解析流之前先查 `res.ok`）：
  - `X-User-LLM-Key` 头缺失且容器无环境 key → **401** `llm_key_missing`（生产上 Java 已前置拦截 key_not_set，此码是直接调用 Python 的防御）；
  - 内部头缺失/`X-Internal-Token` 错 → **403** `forbidden`；
  - question 超 2000 字符 / thread_id 格式非法 → **422** `bad_request`。
- **流中**（`event: error` 事件 + 正常结束流，前端在流里消费）：

| DeepSeek 侧现象 | SSE error code | 前端表现 |
| --- | --- | --- |
| 401（key 被删/改） | `llm_key_invalid` | 弹窗"Key 已失效，请到设置页重新录入" |
| 402（余额不足，DeepSeek 约定码，§9.2-3 实测确认） | `llm_insufficient_balance` | 提示"DeepSeek 余额不足，请充值后重试" |
| 429（DeepSeek 限流） | `llm_rate_limited` | "请求过于频繁，请稍后再试" |
| 5xx/超时/连接断 | `llm_upstream_error` | "模型服务暂时不可用，请重试" |

**评测/CLI 同构性不受影响的论证**（任务点名，全文见 §6，此处给结论链）：① `api_key=None` 时代码路径与现状逐字节等价（条件传参，不新增任何分支行为）；② 评测 runner 在**开发机进程内**直连核心，走 env key，不经过 HTTP 更不经过 Java；③ 服务器上不配 DEEPSEEK_API_KEY（§5.5），env 回退在服务端**结构性不可能**被触发——"服务端不留站点级 key"由部署清单保证，而非靠代码自觉。

### 1.7 滥用边界与限流

BYOK 后 LLM 成本由用户自担，站方仍要防三件事：**拿你的检索层和 MySQL 当免费跑批引擎**、**把 2 核 CPU 打满殃及他人**、**刷 DeepSeek 接口**。mart 库只读 + 工具层 LIMIT 20（W2 已有）+ W5 执行超时——数据面无写风险，剩下的都是频率问题。

**限流策略（全部在 Java 网关实现，Python 不重复建设）**：

| 维度 | 建议值 | 理由 |
| --- | --- | --- |
| 对话频率 | **10 次/分钟/用户**（固定窗口） | W3 实测 P95 7.4s/轮，人类节奏（读结果再提问）20-60s/轮；10/min 已覆盖最快的人类调试节奏，脚本滥用 600 次/时也无利可图（还撞下一行并发闸）。被否 30/min：对"滥用动机=白嫖检索"的场景太宽 |
| 全局并发流 | **4**（原子计数器，超出 503 `concurrency_full`） | 2 核 CPU 上每条流 = 模型 token 吞吐 + 检索 + MySQL 查询；4 并发是 P95 延迟不劣化的保守上界（部署验收实测复核）。这也是 2C2G"用户量上不去"的物理真相，面试可讲 |
| key 校验接口 | 5 次/分钟/用户 | 每次校验是一次出站 DeepSeek 调用，防被当代理用 |
| 认证接口（登录/注册） | 10 次/分钟/IP | 防撞库（demo 规模够了，不引入验证码） |

**实现**：手写固定窗口（`ConcurrentHashMap<String, Deque<Long>>`，~40 行）+ `AtomicInteger` 并发闸。被否 Bucket4j/Redis：单实例 Java 内存限流已满足单机事实（compose 只有这一个 Java），Redis 在 2G 服务器上是奢侈品；面试答案备好"生产做法是 Bucket4j 分布式限流，单机 demo 用固定窗口是成本匹配的选择"。

**越权防护**（顺手钉死）：`/api/history`、`/api/feedback` 一律 `WHERE user_id = 当前JWT用户`；`thread_id` 由 Python 侧按 `u{userId}:` 前缀命名空间隔离（§3.1）——猜到别人 thread_id 也读不到对方上下文。

### 2.3 JWT 认证流程

- **双 token、无状态**：access token（HS256，2h，claims: `sub=userId, username, typ=access`）+ refresh token（同密钥不同 `typ`，7d）。`JWT_SECRET` ≥ 32 字节环境注入。
- **流程**：注册（用户名 `^[A-Za-z0-9_]{4,32}$` + 密码 ≥8 位，BCrypt 入库，用户名冲突返回可读 409）→ 登录（校验 BCrypt → 发双 token + `hasKey` 布尔）→ 前端在 access 过期（401）时用 refresh 调 `/api/auth/refresh` **换发新双 token（旋转）** 并重放原请求。
- **已知限制（写明，供面试提问）**：无状态 refresh 无法服务端吊销——登出=客户端丢弃，token 在剩余有效期内仍有效。demo 规模接受；需要吊销时的正确做法是 refresh token 落库（每次登录写一行、刷新时校验并旋转、登出删行），**需要加第 5 张表**，与需求"四张表"的范围冲突，故不采用。JWT_SECRET 整体轮换可强制全员重新登录，作为应急手段写入运维注释。
- **与 SSE 的交互**：SSE 是 POST 请求，建立时带 Authorization 头即可，无需 cookie（同源部署也没有跨域 cookie 问题）。流建立后 token 过期不会中断流（服务端已放过鉴权）——前端对策是**开流前预检刷新**（§4.3），这是 §7 风险 2 的消解。
- 过滤器：`JwtAuthFilter` 放行 `/api/auth/**` 与 `/api/health`，其余解析 Bearer 并注入 `SecurityContext`。

### 2.5 SSE 代理与"Agent 调 Java"的边界论证（任务点名：哪些给模型，哪些不给）

**`POST /api/chat` 的完整流程**（`ChatProxyService`，约 150 行）：

1. JWT 已过 → 限流检查（10/min）→ 并发闸 `incrementAndGet()` > 4 → 503（`finally` 里必须 `decrementAndGet()`，流异常也要放闸）；
2. 读 `api_key` 行：无行 → 403 `key_not_set`（前端弹设置引导）；有行 → AES-GCM 解密；
3. JDK HttpClient `POST http://python:8000/agent/chat`，头三件：`X-User-LLM-Key` / `X-User-Id` / `X-Internal-Token`，body `{question, threadId}`；连接超时 5s、**读超时不设**（流可能静默数十秒，靠容器层健康检查兜死连接）；
4. 上游非 200：读 JSON 错误体 → 映射为对应 HTTP 状态返回前端（流前错误走这条路）；
5. 上游 200：`BodyHandlers.ofInputStream()` → `BufferedReader` **逐行读、逐行写** `response.getWriter()` 并每事件 flush（SSE 以空行分事件，逐行拷贝即逐事件透传）；同时旁路解析：`delta` 累加 answer_text、`tool` 记最后工具名、`done` 取 tokens/latency、`error` 取 code；
6. 流结束（含上游 error、客户端断连、异常三种收场）→ 写 `query_history`（status 按收场定 1/2/3）→ 成功时**向流内注入** `event: saved\ndata: {"historyId": N}\n\n`（写库失败注入 `historyId: null` 并打 ERROR 日志，不让落库失败弄断用户已收完的回答）→ 释放并发闸。
   - 客户端中途断连：servlet 写出抛 `ClientAbortException` → 停止读上游（关闭 InputStream，HTTP 层会向 Python 传 RST/连接关闭，Python 生成器收到 `GeneratorExit` 退出，§9.2-5 验证）→ 仍按 status=3 落库（已有多少 delta 存多少）。
   - 响应头透传 `Content-Type: text/event-stream; charset=utf-8`，并加 `X-Accel-Buffering: no`（禁代理缓冲的约定头，Caddy 侧另配 flush_interval，双保险）。

**"哪些做成 @tool 给模型，哪些做成请求后处理"——边界论证**（这是本周最重要的架构决策记录）：

| 职责 | 归属 | 论证 |
| --- | --- | --- |
| 查询历史**写入** | **Java 代理后处理，绝不经过模型** | ① 历史写入是**每轮必然发生的确定性副作用**，交给概率性组件等于"审计依赖被审计者自觉"——模型可以漏调、错调；② 工具调用时机上根本不成立：写入参数包含模型的**最终回答全文**，而工具调用发生在回答生成完之前，模型拿不到自己还没说出的话；③ Java 反正要逐事件透传（步骤 5），旁路重组零额外成本；④ 拒答/报错轮也要留痕，后处理天然覆盖，模型路径覆盖不了。每轮还省一次工具往返的 token（约几百 token） |
| 反馈记录 | **前端直调 REST，不经过模型** | 反馈的主体是用户对回答的评价，不是模型的决策；让模型中转只会引入失真（它需要替用户复述 question/answer）与无谓 token |
| 限流 / 审计 / BYOK 管理 | **Java 前置，在模型之前** | 安全边界必须在不可信组件（模型）之前生效，这是原则不是偏好 |
| **查询历史检索**（用户问"我之前问过退款率吗？"） | **@tool（教学文档 4.3.8 模式的 W4 落地点，可选工单项）** | 这才是模型真正的判断域：**要不要调、何时调、怎么组织回答**由模型决定。实现为 Python 侧只读 `@tool search_query_history(keyword, limit)` → HTTP 调 Java `GET /api/internal/history/search`（带 `X-Internal-Token` + `X-User-Id`，Java 按 user_id 过滤 LIKE 检索返回）。只读、低风险、恰好证明"Agent 跨语言调 Java REST"全链路 |
| W5 反馈闭环（点赞样本入 few-shot 库） | Java REST + Python 语料重建接口，**不是模型工具** | 触发者是用户点击不是模型；提前写明防止 W5 设计时误入"让模型确认要不要存"的歧途 |

一句话总结（也是面试答法）：**读路径、判断密集的给模型；写路径、确定性副作用、安全边界的不给模型**——"不是所有事都该让模型管"，Agent 的工程化恰恰体现在划清这条线。需求文档 P1 的"@tool 包装 Java REST"由 `search_query_history` 一个工具兑现；若 W4 工期紧，该工具降级为 T1 可选项顺延 W5，**写路径后处理的结论不受影响**。

## 3. Python FastAPI 服务设计

### 3.1 核心抽取：`agent/core/turn.py`（三方共用，同构红线）

把 `main.py` 主循环里的组装段抽成唯一组装点，**只移动代码、不改行为**：

```python
@dataclass
class PreparedTurn:
    agent: object            # build_agent 产物
    config: dict             # {"configurable": {"thread_key": ...}}
    injected_chunks: list[RetrievedChunk]
    retrieval_query: str

def prepare_turn(question: str, thread_key: str, api_key: str | None = None) -> PreparedTurn:
    """一轮对话的公共前半程：检索 query 拼接 → 混合检索 → prompt 组装 → build_agent。
    调用方（三选一）：
      - agent/main.py         CLI：prepare_turn() + agent.stream(...)   逐 chunk 打印
      - agent/server.py       FastAPI：prepare_turn() + stream → SSE 事件
      - eval/run_eval.py      评测：prepare_turn() + agent.invoke(...) 拿全量消息
    thread_key 是 checkpointer 的最终键：CLI 传 uuid 原文，FastAPI 传 f"u{userId}:{threadId}"
    （按用户隔离命名空间，§1.7），评测传 f"eval-{case}-r{run}"——与 W3 现状一致。
    """
    checkpointer = get_checkpointer()
    previous_question = previous_human_message(checkpointer, {"configurable": {"thread_id": thread_key}})
    retrieval_query = f"{previous_question}\n{question}".strip() if previous_question else question
    chunks = get_retriever().search(retrieval_query, top_n=RETRIEVER_TOP_N)
    agent = build_agent(build_system_prompt(format_context_block(chunks)), api_key=api_key)
    return PreparedTurn(agent, {"configurable": {"thread_id": thread_key}}, chunks, retrieval_query)
```

- 语义与 `main.py` 现行内联代码**逐行等价**（含 §3.6 拼接规则、`RETRIEVER_TOP_N`、兜底文案路径）；`previous_human_message`/`build_agent` 等函数已参数化（W2 遗产），抽取是纯搬运。
- **main.py 最小 diff**：循环体改为 `pt = prepare_turn(user_input, thread_id)` 后进入原有 stream/打印段（banner、preflight、工具名去重打印全部不动）。
- **run_eval.py 最小 diff**：组装段（现约 8 行，带 `[§2.3-N]` 注释锚点）换成 `prepare_turn(question, thread_id)` + `agent.invoke`；检索/prompt/agent 三步的调用者从"runner 内联"变为"核心函数"，评测明细里的 `injected_chunks` 来源不变。
- **同构契约升级**：W3 §2.3 的"main ↔ eval 逐点对照"升级为"三方向 `prepare_turn` 看齐"；`run_eval.py` 顶部 docstring 契约注释同步改写。**验收见 §6.2**（3 道固定题 injected_chunks 与 W3 明细 JSON 完全一致 + prompt 快照测试），这是允许重构的唯一通行证。

### 3.2 `/agent/chat` SSE 接口契约

```
POST /agent/chat
头：X-Internal-Token / X-User-Id（Java 注入）/ X-User-LLM-Key
体：{"question": "...", "threadId": "uuid"}
响应：Content-Type: text/event-stream
```

事件契约（`event:` + `data:` 两行一组，空行分帧）：

```
event: meta
data: {"threadKey":"u42:8f3a...","model":"deepseek-flash"}

event: delta                    ← 文本增量，n 次
data: {"text":"根据订单表…"}

event: tool                     ← 工具调用提示（CLI 打印逻辑的服务化），n 次
data: {"name":"execute_readonly_sql"}

event: done                     ← 正常收尾一次
data: {"tokens":{"input":8123,"output":640},"latencyMs":7400}

event: error                    ← 流中失败一次，之后流结束
data: {"code":"llm_insufficient_balance","message":"DeepSeek 余额不足"}

event: saved                    ← 仅由 Java 注入（Python 永不发），前端反馈按钮用
data: {"historyId":123}
```

- **实现形态**：FastAPI `StreamingResponse` + **同步生成器**（Starlette 在线程池中迭代同步生成器，`def` 端点同样跑线程池；不引入 async LangChain 栈——`agent.stream` 是同步 API，包 async 会引入 to_thread/队列两层胶水，教学负收益）。`agent.stream(stream_mode="messages")` 的 `(chunk, metadata)` 迭代映射为事件：`chunk.content` → `delta`；`tool_call_chunks` 非空且名字变化 → `tool`（沿用 main.py 的去重打印逻辑）；迭代自然结束 → 取 usage 汇总发 `done`。
- **异常必须转事件**：生成器内 try/except，把 DeepSeek 异常映射为 `error` 事件（§1.6 表）后 `return`——让裸异常打断连接会把可恢复错误（余额不足）变成前端不可读的连接中断。
- **meta 事件**放在首 delta 前，前端可先渲染"思考中"骨架。
- **客户端断连**：向已断开的 socket 写出时 Starlette 取消迭代，生成器收到 `GeneratorExit` → finally 中不做任何写入即可（历史落库是 Java 的职责，Python 侧无状态需要清理）。标注验证项 §9.2-5。
- **并发**：uvicorn **单 worker**（W2 §3.1 坑 #10 的正式落地：进程内单例——Chroma PersistentClient、fastembed、checkpointer、LLM 缓存——不允许 ×N 复制），并发靠线程池（默认 40 线程，远大于并发闸 4）。
- **不做 CORS**：前端只调 Java（同源），Python 无浏览器直连方，CORS 中间件不装（少一个安全面）。

### 4.2 SSE 消费：fetch-stream，否决 EventSource

**结论：`fetch()` + `ReadableStream` 手写 SSE 解析（~60 行）。** EventSource 被否的两个硬伤：① **只支持 GET**——对话需要 POST 携带 JSON body（question/threadId，且 key 与鉴权语义上也不该进 URL，§1.5 规则 3）；② **不能带自定义 Authorization 头**——JWT 就没地方放。此外 fetch 对非 200 的错误响应可以按普通 JSON 先读再判断（EventSource 的错误事件拿不到响应体），正好匹配"流前错误 vs 流中错误"两层语义（§1.6）。

解析要点（都是实操坑，写进 `sse.js` 注释）：
1. `res.ok === false` → 读 JSON body 按 §3.3 报错，**不要**进入流解析；
2. `TextDecoder` 流式 decode（`stream: true`），按 `\n\n` 分帧，**缓冲区保留不完整帧**（chunk 边界不保证对齐事件边界，最常见翻车点）；
3. 每帧解析 `event:` / `data:` 行（容忍 CRLF）；`:` 开头为注释行（心跳占位，当前实现不发）；
4. `AbortController`：停止按钮 abort → fetch 抛 `AbortError` → 前端标记消息"已停止"（服务端按 §2.5 落 status=3）；
5. 网络中断（无 abort）→ 消息标记"连接中断，可重试"，不清除已收文本。

### 4.3 交互细节

- **token 时序**：路由守卫检查 access 本地过期时间（签发时解码 exp 存 Pinia）；**剩 <5min 则先刷新再进对话页**——保证 SSE 建立时 token 新鲜（§7 风险 2 消解）；流中不处理 401（流已建立不会再来 401）。
- **降级文案**：`concurrency_full`、`rate_limited` 等全部映射为友好中文 toast，错误码-文案映射表与 §3.3 一一对应，写成常量文件。
- 开发链路：`vite dev` 代理 → Java(8080) → uvicorn(8000)，三方本机起；**Python 不经前端直接访问**，与生产同构。

## 5. 部署设计（2核2G）

### 5.1 拓扑与 Compose

`deploy/docker-compose.prod.yml` 四服务，**只有 Caddy 发布宿主机端口**：

| 服务 | 镜像 | 端口 | 关键配置 |
| --- | --- | --- | --- |
| mysql | `mysql:8.0`（save/load 带过去） | 不发布（数据初始化时临时 `docker exec`） | `--innodb_buffer_pool_size=128M --performance_schema=OFF --max_connections=50`；volume；healthcheck |
| python | 自建 `text2sql-python`（python:3.11-slim 基底） | **不发布**（§1.1 链路前提） | `uvicorn agent.server:app --workers 1`；env_file；mem_limit 512m |
| java | 自建 `text2sql-java`（eclipse-temurin:17-jre 基底） | 不发布（仅 Caddy 容器网络可达） | `JAVA_TOOL_OPTIONS=-Xmx512m -Xms128m -XX:MaxMetaspaceSize=128m`（JVM 容器感知默认开启）；mem_limit 640m |
| caddy | `caddy:2-alpine` | **80/443** | Caddyfile + 前端 dist 挂载；`caddy_data` 卷存证书；mem_limit 128m |

Caddyfile（全文， 生产可直接用）：

```caddyfile
sql.shanghl.club {
    encode gzip
    handle /api/* {
        reverse_proxy java:8080 {
            flush_interval -1        # SSE 关键：逐字节立即冲刷，禁缓冲
        }
    }
    handle {
        root * /srv/www
        try_files {path} /index.html # 前端 history 路由回退

    }

```

集成预演：上线前先在**开发机 Docker Desktop** `docker compose -f docker-compose.prod.yml up`（临时把 java/python 端口发布到 localhost）全链路冒烟，把 compose 配置错误消灭在本地，不消耗服务器往返（Windows/Linux 差异仅剩路径分隔符与性能）。

### 5.2 内存预算表（逐项核对 ≤1.5G + swap 兜底）

| 组件 | 预算 | 依据与手段 |
| --- | --- | --- |
| MySQL 8.0 | **≤450MB** | buffer pool 128M（37 万行库文件 200-300MB，W2 §1.5 已论证够用）+ 连接线程栈 + 代码路径；`performance_schema=OFF` 回收其常驻开销；`max_connections=50` 封顶线程内存 |
| Python（uvicorn+fastembed+chroma） | **≤450MB** | bge-small-zh ONNX 模型 ~100MB + onnxruntime + Chroma（28 片忽略）+ uvicorn 单 worker ~30MB；LLM 客户端缓存 16 实例 KB-MB 级 |
| Java | **≤550MB** | 堆 512m 上限 + Metaspace 128m 上限 + 线程栈；RSS 实测通常为堆上限的 70-90%，640m 容器上限兜住 |
| Caddy | ~30MB | 官方 alpine 镜像空载 |
| **服务合计** | **≈1.48GB** | |
| OS 内核 + 页缓存余量 | ~0.5GB | 2G 物理 − 服务合计；页缓存被挤压时靠 swap |
| **swap** | **2GB, swappiness=10** | 兜底而非依赖；OOM 前最后一道闸（§7 风险 3） |

每个服务加 `mem_limit`（上表数值）+ `memswap_limit`：任何单服务失控只 OOM 自己，不拖死整机。**T4 验收 = 暖机后 `docker stats --no-stream` 实测回填本表**（实测值记入 `docs/experiment-log.md`，这就是简历里"2C2G 资源预算"的数字来源）。

### 5.3 HTTPS：Caddy（否决 nginx+certbot）

| 维度 | Caddy（选定） | nginx + certbot |
| --- | --- | --- |
| 证书签发/续期 | **全自动**（首次启动向 Let's Encrypt 签，到期前 30 天自动续，零配置） | certbot 容器/定时器 + nginx reload 联动，多一套会"静默失败"的运维件 |
| 续期失败后果 | 几乎不存在这类故障模式 | **续期静默失败 = 网站某天突然不可用**——个人服务器没人盯着，这是最贵的故障模式 |
| SSE | `flush_interval -1` 一行 | `proxy_buffering off` + `proxy_http_version 1.1` + 超时三件套，易漏配 |
| 内存 | ~30MB | ~10MB（差异无意义） |
| 学习/简历 | 反向代理概念与 nginx 完全同构，讲得清 | nginx 本身是简历常见词 |

结论：**2核2G 个人服务器选 Caddy**——赢在"证书生命周期零运维"，而 nginx 的优势（极致性能、生态）在个位数并发下无意义。用户若坚持 nginx（简历考虑），备选路径 `nginx + certbot（--standalone，systemd timer 每天续 + 部署后手动验证一次）`，Caddyfile 各行都有 nginx 等价写法，迁移成本半天以内。前置条件：子域名 A 记录已生效、服务器安全组放行 80/443。

### 5.4 发布流程（离线镜像交付，W2 国内网络教训的落地）

**原则：服务器上不做任何"拉取/下载"，一切产物在开发机构建后 scp 过去。**

```
① 开发机构建：
   - docker build 三镜像（python / java / 前端 dist 直接 scp 无镜像）
     —— Dockerfile 内 pip/maven 全部走国内源（清华 pypi / 阿里 maven），只影响开发机构建速度

   - 前端 npm run build → dist/
   - mysqldump --databases app mart > data-init.sql（与开发机数据逐字节一致 = 评测可复现）
   - 打包 data/chroma_db/ 与 data/rag_corpus/（索引不在服务器重建，§0.2）
② scp/rsync 全部产物 → 服务器 /opt/text2sql/（rsync 断点续传，大文件必备）
③ 服务器：docker load < images.tar.gz；手工放置 .env.prod（不在 ②的包里生成，见 §5.5）
```

## 6. 评测与同构

### 6.1 论证：上线后评测数字仍有效

1. **评测对象没变**：W3 基线测量的是 Python 核心（检索注入 + prompt 组装 + Agent + SQL 工具）的系统级表现；W4 在其外面包了传输层（Java 网关 + FastAPI 包装）。被测系统与 W3 是同一份代码路径。

4. **W6 消融的可比性**：W6 将在 W4 重构后的代码上跑消融，与 W3 基线对比的前提正是第 1-3 条；对照锚点就是 §6.2 的固定题 injected_chunks 一致性记录。

### 6.2 同构验收（T2 的硬闸门）

1. **固定题对照**：EV-003、EV-017、EV-029 三题（覆盖陷阱/多表/口径），重构前后各跑一次 `--limit` 模式，断言 `injected_chunks` 与 `retrieval_query` 与 W3 `detail_baseline_full_*.json` 中对应记录**逐元素相等**（检索全链路确定性，W3 §6 风险 6 已论证同 query 必同注入——所以这里必须全等，不等即回归）。

## 7. 风险与应对

| # | 风险 | 影响 | 应对与回退 |
| --- | --- | --- | --- |
| 1 | **SSE 断连/用户中途停止**：客户端断连后 Java 侧写出异常、Python 生成器取消；key 已在途的请求如何收场 | 历史记录残缺、连接悬挂 | Java 捕获 `ClientAbortException` → 停止读上游（关 InputStream 传导断开）→ 仍按 status=3 落库（§2.5 步骤 6）；Python 生成器 `GeneratorExit` 自然退出（§9.2-5 实测验证无僵尸线程）；前端 abort 后标记"已停止"。key 本身随请求结束即弃（Java 不缓存明文），无残留风险 |
| 2 | **JWT 过期中断流对话**：access 2h，用户挂着页面过期后发起对话 | 401 打断体验 | 前端三层：本地 exp 预检 + 剩 <5min 先刷新（§4.3）+ 401 拦截器静默刷新重放；流一旦建立不受过期影响（鉴权只在建流时）；流最长 120s 远小于 token 粒度。refresh 7d 过期才需要重新登录 |
| 3 | **2G 内存 OOM**：实测 RSS 超预算（JVM/ONNX 是大头） | 整机卡死或容器互杀 | mem_limit 各服务封顶（§5.2）+ swap 2G swappiness=10；T4 实测回填，超预算时的回退顺位：① JVM 降到 -Xmx384m（四张表个位数并发够用）② fastembed 换 DashScope API（W2 风险 1 同路，检索层接口已抽象）③ MySQL buffer pool 96M |
| 4 | **国内拉镜像/网络**（W2 教训）：服务器 Docker Hub 拉不动、pip 超时 | 部署卡死 | §5.4 离线交付：一切产物开发机构建 save→scp→load，服务器零拉取零下载；chroma_db 拷贝不重建（避开 HuggingFace 下载）；基础镜像国内源预先 pull 后再 save |
| 5 | **HTTPS 证书/备案**：Caddy 签发失败（80/443 未放行、DNS 未生效）；**服务器在境内且域名未备案时 80/443 会被拦** | demo 无法公网访问 | 部署前检查单：DNS A 记录生效（dig）→ 安全组放行 → 再起 Caddy；境内未备案的应对在 §10 开放问题 5 由用户确认（境外服务器直接可用；境内需备案或临时非标端口） |
| 6 | **主密钥丢失/泄漏**：换机器部署忘迁 `BYOK_MASTER_KEY` | 全部用户 key 不可解 → 用户重录 | 丢失可接受（无数据损失，§1.4）；泄漏按 §1.4 运维手册处理；`key_version` 列预留轮换 |
| 7 | **并发下共享单例的正确性**：InMemorySaver / Chroma / fastembed 在多线程 SSE 下是否安全（现状全部单线程使用） | 交叉污染会话或崩溃 | §9.2-5/6 并发冒烟前置验证；InMemorySaver 内部有锁（langgraph 实现），Chroma 查询线程安全——但**实测确认，不引用文档断言**；最坏回退：FastAPI 侧加全局信号量把真正进入 agent 的并发压到 1（演示规模性能可接受） |
| 8 | **会话内存不持久**：InMemorySaver 重启丢上下文，"那 10 月呢"跨重启失忆 | 体验降级（历史页仍可查全文） | W4 明示为限制不做持久 checkpointer（需求 P0 未含）；多轮追问仅在单次部署周期内有效，写进 README 已知限制 |
| 9 | **Java→Python 头传递在异常路径泄漏**：错误响应/调试页回显请求头 | key 泄漏进响应 | Spring 默认不回显头；`server.error.include-*` 全部保持默认（不 include）；§1.5 规则 9 的 grep 验收兜底 |
