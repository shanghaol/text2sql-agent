## 一、做了什么（W5 全景）

四条主线 + 一个清理项：

```
安全加固：sql_tools.py 的校验层整体升级
  正则黑名单（W1）──退役──► sqlglot AST 白名单（R1-R6）+ legacy 逃生门
  执行超时：max_execution_time=10s（服务端）+ read_timeout=15s（驱动兜底）
```

## 二、为什么这么做（六个决策的完整论证）

### 2.1 为什么正则黑名单要"整体退役"而不是"保留做预检快路径"？

W1 以来写明的两个已知缺陷：字符串字面量误杀（`WHERE status='update'`）、子查询 LIMIT 漏判。sqlglot AST 校验把两个都消除了（实测）。**被否的"双轨预检"方案**：正则预检会把字面量误杀原样带回新链路（预检拒了就永远走不到 AST——升级目的落空）；性能上正则 0.01ms vs AST 0.33ms，在 7.4s 端到端 P95 面前都是噪声。**被否的"彻底删除"**：保留一个版本周期的 `TEXT2SQL_SQLGUARD=legacy` 逃生门——新校验若有设计未预料的误杀，一键切回正则恢复服务（分钟级事故恢复能力），W6 删。

**面试一句话**：升级校验时最危险的不是新校验有 bug，而是"新旧双轨带来的两套拒绝语义"——同一条 SQL 可能因预检/复检给出不同理由，排查成本远超 0.2ms 的性能差。

### 2.2 AST 校验的规则集设计：为什么是"白名单+小黑名单"而不是"大黑名单"？

R1 唯一语句（parse() 列表长度）→ R2 根节点白名单（Select/Union/Except/Intersect——**一条规则兜住全部写操作**：Insert/Update/Delete/Drop 在根节点层面就不可能通过）→ R3 树扫描锁读（FOR UPDATE 藏在 Select 根里，必须树扫）→ R4 INTO 拦截 → R5 五函数小黑名单（LOAD_FILE/SLEEP/BENCHMARK/GET_LOCK/RELEASE_LOCK——"数据分析零用处+明确攻击面"）→ R6 LIMIT 判定。

三个关键取舍（面试可讲）：
1. **校验用 AST、执行用原文**（不重新生成 SQL）——往返重建会丢注释、规整字面量格式，"模型写的"与"执行的"出现文本差异会让审计对照变困难。
2. **R2 不含 exp.Command**——sqlglot 不认识的语句回退为 Command，语义等同未知，宁可拒绝（只读账号也会拒它）。
3. **函数用小黑名单不用大白名单**——GROUP_CONCAT 被否禁用（合法分析函数+慢的根源由超时兜底+group_concat_max_len 天然限长）；误杀率不可控的大白名单直接违反"不误杀现有合法查询"的兼容红线。

### 2.3 执行超时：为什么是"服务端+驱动"双层而不是 Python 线程超时？

Python **无法安全取消**正在阻塞 socket read 的 pymysql cursor——线程级超时只能放弃等待，查询在 MySQL 端继续跑。所以主防线必须是 MySQL 原生 `max_execution_time`（服务端真终止、真释放资源）；`read_timeout` 只兜"结果传输卡死/服务器假死"的边角。覆盖面矩阵见设计 §2.1——**每道防线覆盖的阶段不同，缺一不可**。

实测锚点：10.1 秒的笛卡尔积查询被服务端终止 → errno 3024 → 模型收到"请缩小时间范围"的可读文案（自我修正闭环对超时同样成立）。

### 2.4 HITL 为什么暂停在 Python 工具层？（方案 A vs B 的架构论证）

**方案 B（Java 拦截 tool 事件）是假暂停**：SSE 下行是单向只读流——Java 看到事件时 Python 端工具**已经执行完、模型已经在继续生成**。Java 要"叫停"只能断开整轮（状态作废重来）。方案 A 借助 LangGraph 原生中断：checkpoint 停在"模型已产出 tool_call、工具未执行"——批准后 `Command(resume)` **原地续跑**，不重跑检索、不重答。

实测要点（都有回归测试）：中断时 messages 流自然结束；载荷在 `get_state().tasks[0].interrupts[0].value`；resume 必须是 `{"decisions": [...]}` dict（裸 list 会 TypeError）；同轮多条 SQL 时 decisions 与 action_requests 等长对齐——**approve=批第 1 条、其余未过目 SQL 一律拒（安全不变量：绝不执行未经确认的 SQL）**。

**面试一句话**：HITL 的暂停状态必须与被暂停的对象同层（工具执行、LangGraph 状态、LLM 客户端都在 Python）——跨语言对账四个状态三处存放，重启/断连/并发的边界每种都要处理，复杂度会吃掉整个功能。

### 2.5 为什么点赞样本要过六道门槛 + 手动 dry-run？（自举的克制度）

**点赞 ≠ 正确**——用户可能为"看起来像答案"的错误结果点赞（口径算错但数字合理），自动入库会把错误示范写进每次检索都可能命中的语料，**污染是静默且全局的**。六道门槛（点赞/执行成功/有 SQL/过自家安全校验/长度合规/双层去重）+ dry-run 人工过目 = 这条链路唯一的人工质量闸。**被否"点赞即自动追加"**：频率低（个位数/周）自动化收益为零；语料版本必须可控（W6 消融"除被测变量外一切固定"的前提）；回滚 = git revert 一个 md 文件。

**实测验证的去重阈值**：语义判重的比较口径经过实测修正——**整片判重的向量被 SQL 与说明稀释**（改写 0.60-0.72 与不同题 0.55-0.60 几乎重叠），改为问字段对问字段后分布拉开（同文 1.0 / 改写 ≥0.81 / 不同题 <0.78），0.92 恰落保守空档。**联调实锤**：文本层拦住 QA-003 同文、语义层拦住"少个问号"变体（0.9711）——两层互补各司其职。

### 2.6 为什么 INTERNAL_TOKEN 空值在生产要 fail-open 改 fail-fast？（审查 P1-a）

原实现：空 token = 跳过校验（本机调试便利）。审查指出：**该变量丢失时启动无告警，nginx 会把 /api/internal/** 反代到公网**——任何人可调。修复：生产 profile 空值启动失败（与 JWT_SECRET 同语义）+ nginx `deny /api/internal/` 纵深防御。**同款教训的姊妹条**：X-Forwarded-For 首值可伪造（审查实测 12 次登录绕过限流）→ 改读 nginx 注入的 X-Real-IP。

**面试一句话**：安全配置的默认值必须 fail-safe——"便利的默认"在生产就是漏洞；而"可伪造的输入"（XFF 首值）永远不能作为安全决策的依据。

## 三、面试考点（四件套）——本周的新弹药类型：安全工程

### 3.1 "你的 SQL 校验怎么做的？正则够吗？"（NL2SQL 安全必考第一题）

**参考答法（90 秒口语稿）**：
> 四层防线：只读账号（DBMS 内核）→ 会话只读 → **sqlglot AST 语义白名单** → 执行超时。AST 层的规则：parse 后根节点白名单（一条规则兜住全部写操作）+ 树扫描锁读/INTO + 五函数黑名单。关键取舍有三：① 校验用 AST、执行用原文（往返重建会丢注释破坏审计对照）；② 多语句检测用 parse() 列表长度（parse_one 不抛错而是包 Block）；③ 函数用小黑名单不用大白名单（GROUP_CONCAT 禁了属于功能阉割，慢由超时兜底）。升级过程也是教材：正则的两个已知缺陷（字面量误杀/子查询 LIMIT 漏判）被 AST 消除，且 45 条现有 SQL 全过零误杀——**兼容红线先于功能上线验证**。

**结合项目的加分句**：
> "最刁钻的攻击面是 `SELECT ... INTO OUTFILE`——它以 SELECT 开头且 mysql 方言下是 ParseError，AST 层天然拒绝但错误语义不精确；而 `SELECT ... INTO @var` 是合法语法会产生 exp.Into 节点，专门一条规则拦截。两种形态、两种拒绝路径，全覆盖。"

**可能的追问**：
- "sqlglot 本身有性能开销怎么办？"→ 实测 median 0.33ms，是端到端 P95 的万分之五；纯 Python 无二进制。
- "sqlglot 不认识的语法？"→ 回退为 exp.Command 节点，白名单一票否决——未知即拒绝。
- "升级 sqlglot 版本怕行为漂移？"→ 区间锁 + 行为锁定测试（拒绝/放行/追加三类用例作为升级回归闸）。

### 3.2 "HITL 怎么实现的？中断后怎么恢复？"（Agent 工程高频新题）

**参考答法（口语稿）**：
> 用 LangGraph 原生中断：middleware 配置 interrupt_on 指定 execute_readonly_sql 需审批。中断时 checkpoint 停在"模型已产出 tool_call、工具未执行"，SSE 流自然结束，我探测 interrupt 后发 pending_approval 事件（含 SQL 和审批 ID）给前端渲染审批卡。批准 → `Command(resume={"decisions":[...]})` 原地续跑——**不重跑检索、不重答**，resume 轮复用停车轮的 prompt 上下文保证连续。拒绝 → 工具收到带中文引导的 ToolMessage，模型转为询问用户意图。同轮多条 SQL 时 decisions 与 action_requests 等长对齐，安全不变量：**绝不执行未经确认的 SQL**（批第 1 条、其余一律拒）。

**结合项目的加分句**：
> "暂停点选在 Python 工具层而不是 Java 网关——SSE 下行是单向流，网关看到事件时工具已经执行完了，那不是暂停是掐死。**暂停状态必须与被暂停的对象同层**，LangGraph 的 interrupt/checkpoint 机制原生支持。"

**可能的追问**：
- "审批等待期间用户又发新问题？"→ 409 引导先处理审批卡。不选"自动拒绝旧审批再答新问题"——resume reject 会多一次 LLM 调用并混入答非所问文本。
- "服务重启审批丢了？"→ 与 InMemorySaver 同等级的已知限制（重启即失），文档化；批准时收到 approval_not_found 引导重新提问。
- "为什么不用编辑后执行（edit 决策）？"→ middleware 原生支持，但前端要做 SQL 编辑器——W7 范围。

### 3.3 "点赞数据怎么利用的？怎么防污染？"（RAG 进阶题）

**参考答法（口语稿）**：
> 点赞是唯一的质量信号，但点赞 ≠ 正确。六道门槛：点赞 + 执行成功 + 有 SQL + 过自家安全校验（G4 防止教模型写出会被拒的 SQL）+ 长度合规 + 双层去重。去重是双层的：文本归一精确匹配挡住完全相同，语义余弦 0.92 挡住改写变体——阈值经过真实数据标定（同文 1.0 / 改写 ≥0.81 / 不同题 <0.78，0.92 落空档）。触发是**手动 dry-run**：点赞即自动追加的污染是静默且全局的，dry-run 强制人过目每条样本的门槛结论与相似度。入库后 git 版本化——W6 消融"除被测变量外一切固定"的前提就是语料可冻结。
> 联调实锤：文本层拦住 QA-003 同文（语义相似度 1.0），语义层拦住"少个问号"变体（0.9711）——两层互补、缺一不可。

**可能的追问**：
- "点踩数据呢？"→ 将来做负例分析（模型常错什么），不进正例库。
- "阈值 0.92 怎么定的？"→ 真实数据标定：判重口径做了双分布实测（改写与不同题的空档在 0.77-0.81），0.92 在保守侧——宁可漏收不可错收。

### 3.4 "你们的生产部署和回滚方案？"（工程成熟度题）

**参考答法（口语稿）**：
> 2 核 1.87G 单机、已有宝塔 nginx 和另一生产站点——方案是原生共存：nginx 按 server_name 分流，两个服务各一个 systemd 单元（MemoryMax 封顶——失控只 OOM 自己）。证书 certbot 自动续期。部署原则：**服务器零构建零拉取**——jar/dist/语料全部开发机构建 rsync 过去（国内拉取是 W2 教训）。数据库迁移有守护脚本（查 information_schema 无该列才 ALTER，幂等）。每个环境变量文件都结构性排除站点级 LLM key（BYOK）。
> 回滚三层：jar 可回滚（releases 目录留版本）、语料可回滚（git revert 一个 md）、数据库可回滚（切换脚本的冷备 datadir 保留在案）。

**可能的追问**：
- "内存怎么分配的？"→ 逐项记账：MySQL 450 + Python 450 + Java 550 + nginx 30 ≈ 1.48G + swap 2G；部署验收动作是 free 实测回填而不是照抄设计。

### 5.1 实验一：AST vs 正则的对抗测试（体会误杀消除）

- **验证目标**：亲眼看 W1 的两个已知缺陷被 AST 消除
- **操作**：对同一组 SQL 分别跑 legacy 与 ast 模式的 validate：`WHERE status='update'`（正则误杀/AST 放行）、`SELECT * FROM (SELECT ... LIMIT 5) t` 加 enforce（正则漏追加/AST 判定准确）
- **预期现象**：ast 模式下字面量关键字通过校验、子查询 LIMIT 被正确追加；legacy 模式下复现误杀
- **思考题**：为什么"宁可错杀"的正则在 W1 是合理选择而在 W5 被替换？（答案在"防线数量"的变化：W1 只有正则一道代码防线，误杀是安全冗余；W5 有了 ro 账号+会话只读+超时三道兜底，误杀从"安全冗余"变成"纯可用性损害"）

### 5.2 实验二：触发 10s 超时（亲眼看到服务端终止）

- **验证目标**：max_execution_time 的真实终止行为 + errno 3024 可读化
- **操作**：构造一条超 10s 的查询（如 `SELECT COUNT(*) FROM orders a JOIN orders b` 无连接条件的笛卡尔积）经工具执行
- **预期现象**：约 10s 后返回"SQL 执行超时（超过 10 秒被数据库终止）。请缩小时间范围…"——且 MySQL 端 `SHOW PROCESSLIST` 中查询已消失（真终止，非客户端放弃）
- **背后机制**：服务端 SET SESSION 对该连接的每条 SELECT 生效；errno 3024 映射为中文引导
- **思考题**：为什么不用 Python 线程超时？（无法安全取消 in-flight cursor——查询在 MySQL 端继续跑，资源照样耗尽）

### 5.3 实验三：HITL 的批准/拒绝双路径

- **验证目标**：中断-恢复状态机的两条路径
- **操作**：开 HITL → 问"上个月GMV" → 审批卡批准；再问一次 → 点拒绝
- **预期现象**：批准 → SQL 执行 → 正常回答 → 历史 status=1；拒绝 → 模型**用中文询问你想怎么调整**（不是报错）→ 历史 status=3 + approval_rejected
- **背后机制**：resume 的 decisions 决定工具收到的 ToolMessage 内容——模型据此分支
- **思考题**：拒绝后模型为什么不会自己换一条 SQL 再执行？（那条路径同样要审批——middleware 对每条 execute_readonly_sql 都拦）

### 5.4 实验四：自举 dry-run 的去重观察

- **验证目标**：双层去重的互补性（文本层/语义层各拦什么）
- **操作**：对同题不同问法的历史各点赞一次（"上个月的GMV" / "上个月 GMV 是多少"），跑 --dry-run
- **预期现象**：第一条被文本归一拦（与 QA-003 完全相同），第二条文本层放过但语义层拦（相似度 ≥0.92）
- **思考题**：如果阈值降到 0.85 会怎样？（改写变体 0.81-0.90 会被误判重复——语料多样性受损；这就是 0.92 取保守侧的理由）
