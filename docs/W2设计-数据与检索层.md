## 1. MySQL 数据集设计

### 1.1 单实例双库落地

**决策**：一个 MySQL 8.0 实例里 `CREATE DATABASE app` 与 `CREATE DATABASE mart`。W2 只建 `app` 库不建表（W4 Java 后端启动时自己建自己的表），Agent 一切查询只发生在 `mart`。

理由：需求 §5 已确认"2核2G 单实例省内存"——两个实例意味着两份 buffer pool 和两个常驻进程，在本机和服务器的内存预算里都是最贵的浪费。双库隔离已经足够：账号权限按库授予（§1.3），`app` 与 `mart` 互不可见。

被否掉的备选：
- **两个 MySQL 实例**（业务/分析彻底隔离）：多一份内存 + 两套备份运维，2G 服务器装不下，收益为零（当前无并发负载隔离需求）。
- **SQLite 继续当分析库**：需求已确认 MySQL，且 SQLite 的 `strftime` 方言、无用户权限体系、无网络访问，会让"四层安全"里的只读账号一层直接缺失。

安装形态（开发机 Windows 11）：**推荐 Docker Desktop 跑 `mysql:8.0`**（与 W8 部署形态完全一致，迁移零差异），备选 MySQL 8 Community 原生安装。无论哪种，连接信息全部走 `.env`（§4.2），代码不感知安装方式。此点在 §7 列为开放问题（涉及用户机器装不装 Docker）。

### 1.2 驱动与连接选型

**决策**：SQLAlchemy 2.x Core（Engine + `text()`）+ **PyMySQL** 驱动，连接串 `mysql+pymysql://user:pwd@host:3306/mart?charset=utf8mb4`，`connect_args={"connect_timeout": 5}`，`pool_pre_ping=True`。

理由：
- **PyMySQL 是纯 Python 实现**，Windows 上 `pip install` 零编译。否决 mysqlclient（C 扩展，Windows 需要 MSVC 构建环境，摩擦最大）；否决 mysql-connector-python（功能等价，但 SQLAlchemy 文档与社区示例的主流组合是 PyMySQL，出问题好搜）。
- **要 SQLAlchemy 这一层的原因是连接池**：Agent 每轮回答会调用 2-5 次工具，每次都新建 TCP + 认证握手浪费 10-50ms；W4 起 SSE 并发请求共用一个池也线程安全。教学类比：这就是 Java 侧 HikariCP 的角色，用户可以无缝理解。
- PyMySQL 8.0 默认认证插件 `caching_sha2_password` 需要 **`cryptography` 包**，必须显式加进 requirements（这是最常见的安装后报错，提前写进依赖，§4.5）。

版本标注：`sqlalchemy>=2.0,<3`、`pymysql>=1.1` 为方向性约束，**具体可用版本编码前在 venv 里实测锁定（§8）**。

### 1.3 只读保证（三层防线，从代码外到代码内）

MySQL 没有 SQLite 的文件级 `mode=ro`，替代方案按防线从强到弱：

| 防线 | 机制 | 拦住什么 |
| --- | --- | --- |
| 第一层：**只读账号（主防线）** | `CREATE USER 'text2sql_ro'@'%'; GRANT SELECT ON mart.* TO ...`，无任何其他权限 | 一切写操作、DDL、临时表创建（无 CREATE 权限连 `CREATE TEMPORARY TABLE` 都不行）、对 `app` 库的任何访问。**权限在 DBMS 内核层执行，代码任何 bug 都绕不过** |
| 第二层：**会话只读（辅助）** | Agent 的 SQLAlchemy Engine 挂 `connect` 事件监听，每个池化连接建立时执行一次 `SET SESSION TRANSACTION READ ONLY` | 就算将来有人误把高权限账号配进 `.env`，会话级只读仍拦住普通表写入。设一次随连接池复用，成本为零 |
| 第三层：**W1 代码校验（保留）** | `validate_readonly_sql` 黑名单 + 首关键字检查，逻辑不变 | 在 SQL 出手前就给出**中文可读拒绝原因**，让模型自我修正——这是 F2 的需求，前两层只会报英文错误码，模型体验差 |

**为什么账号为主、会话为辅**：账号权限是最小权限原则的落地，面试可讲的"正确答案"；会话只读防的是"配置错误"这类运维事故，属于纵深防御的便宜加层。单独依赖会话只读不够（`transaction_read_only` 对部分边界场景的覆盖依赖版本行为，且换个连接就失效）；单独依赖账号又拿不到中文拒绝原因。

**W1 黑名单需要的 MySQL 特有扩充**（放进 T4 工单，逻辑照旧整词匹配）：

```
新增：FOR UPDATE、FOR SHARE、LOCK IN SHARE MODE、INTO OUTFILE、INTO DUMPFILE、CALL
```

理由：`SELECT ... FOR UPDATE` 在 MySQL 里是合法的**锁读**（SQLite 没有这个语法所以 W1 没防）；`SELECT ... INTO OUTFILE` 以 SELECT 开头、能写服务器文件系统——这是 SQLite 黑名单完全覆盖不到的 MySQL 特有攻击面。原有 SQLite 关键字（PRAGMA/VACUUM/ATTACH 等）保留不删：MySQL 下这些词本来也不是 SELECT 开头，留着无害，测试断言也还在用它们。

**W5 预留（W2 不做）**：执行超时用 MySQL 原生 `SET SESSION max_execution_time`（毫秒，仅作用于 SELECT）实现，W2 在 `sql_tools.py` 留注释占位即可。

### 1.4 mart 库完整 DDL

**建模决策**：
- 六实体 + 两张冗余列：`orders` 冗余 `order_amount`/`item_count`（订单头汇总），`refunds` 冗余 `order_id`。这是数仓"宽度换查询"的常规手段——订单级统计（GMV、订单量、客单价）**不必 JOIN 明细表**就能答，同时保留明细表做商品级分析。命名采用 `order_amount` 而非 `amount`，与需求文档 §3 F2 的示例（"相近的列是 order_amount"）一致。
- 否决"完全三范式、不冗余"：每次订单统计都要三表 JOIN，W1 的 3 表已证明模型写长 JOIN 易错；冗余列让单表问题/多表问题分层，评测集也更有梯度。
- `status` 用 ENUM 而非 VARCHAR：值集固定且 DDL 自带文档。否决 VARCHAR+CHECK（MySQL 8.0.16+ 也支持）：等价但啰嗦；ENUM 加状态要 ALTER，对固定数据集无所谓。
- 时间列用 DATETIME 而非 TIMESTAMP：DATETIME 无 2038 问题、不受时区转换干扰，纯分析场景更省心。
- 保留外键：数据一致性由 InnoDB 强制（生成脚本出错立即暴露），且外键关系出现在 `SHOW CREATE TABLE` 里，是模型理解 JOIN 路径的免费线索。导入时 `SET FOREIGN_KEY_CHECKS=0` 关检查提速、导完恢复（标准做法，§1.8）。

完整 DDL（落盘为 `data/schema.sql`，含双库创建；表内顺序即导入顺序）：

```sql
-- ============================================================
-- data/schema.sql —— W2 分析库建表脚本（MySQL 8.0）
-- 执行者：data/generate_dataset.py --init（用管理员账号，读 .env）
-- 只读账号 text2sql_ro 的创建也在脚本里做（密码读 .env，不写死在 SQL 文件）
-- ============================================================

CREATE DATABASE IF NOT EXISTS app  DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
-- app 库：W2 只建不填。W4 Java 后端使用（用户/历史/反馈），表由 Java 侧建。

CREATE DATABASE IF NOT EXISTS mart DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE mart;

-- ------------------------------------------------------------
-- 1. users 用户表（20,000 行）
-- ------------------------------------------------------------
CREATE TABLE users (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户 ID',
    name          VARCHAR(64)     NOT NULL COMMENT '姓名（Faker zh_CN 生成）',
    gender        ENUM('男','女') NOT NULL COMMENT '性别',
    city          VARCHAR(32)     NOT NULL COMMENT '城市（受控加权列表，见 §1.7）',
    province      VARCHAR(32)     NOT NULL COMMENT '省份（与 city 一一对应，非独立抽样）',
    registered_at DATETIME        NOT NULL COMMENT '注册时间（恒早于其全部订单）',
    PRIMARY KEY (id),
    KEY idx_users_registered_at (registered_at),
    KEY idx_users_city (city)
) ENGINE=InnoDB COMMENT='用户表';

-- ------------------------------------------------------------
-- 2. products 商品表（2,000 行）
-- ------------------------------------------------------------
CREATE TABLE products (
    id        BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '商品 ID',
    name      VARCHAR(128)    NOT NULL COMMENT '商品名（虚构品牌+类目词+属性词模板拼接）',
    category  VARCHAR(16)     NOT NULL COMMENT '一级类目（数码/家居/服饰/美妆/食品/母婴/运动户外/图书，共 8 类）',
    brand     VARCHAR(32)     NOT NULL COMMENT '品牌（每类目 4-5 个虚构品牌，避免撞真实品牌）',
    price     DECIMAL(10,2)   NOT NULL COMMENT '原价（元）。简化：不做调价历史',
    listed_at DATE            NOT NULL COMMENT '上架日期（恒早于数据期起点）',
    PRIMARY KEY (id),
    KEY idx_products_category (category),
    KEY idx_products_brand (brand)
) ENGINE=InnoDB COMMENT='商品表';

-- ------------------------------------------------------------
-- 3. orders 订单主表（100,000 行）—— 表头，含两列冗余汇总
-- ------------------------------------------------------------
CREATE TABLE orders (
    id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '订单 ID',
    order_no     CHAR(18)        NOT NULL COMMENT '业务订单号（SO+yyyyMMdd+8位序号），全局唯一',
    user_id      BIGINT UNSIGNED NOT NULL COMMENT '下单用户 → users.id',
    status       ENUM('pending','paid','shipped','completed','cancelled','refunded')
                                 NOT NULL DEFAULT 'pending'
                                 COMMENT '订单状态：pending待支付/paid已支付/shipped已发货/completed已完成/cancelled已取消/refunded已全额退款',
    order_amount DECIMAL(10,2)   NOT NULL COMMENT '订单应付金额（元）= SUM(订单项 sale_amount)，冗余列',
    item_count   INT UNSIGNED    NOT NULL COMMENT '订单件数 = SUM(订单项 quantity)，冗余列',
    created_at   DATETIME        NOT NULL COMMENT '下单时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_orders_order_no (order_no),
    KEY idx_orders_user_id (user_id),
    KEY idx_orders_status (status),
    KEY idx_orders_created_at (created_at),
    CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users (id)
) ENGINE=InnoDB COMMENT='订单主表（表头）';

-- ------------------------------------------------------------
-- 4. order_items 订单明细表（约 150,000 行）—— 一行 = 订单里一种商品
-- ------------------------------------------------------------
CREATE TABLE order_items (
    id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '明细 ID',
    order_id      BIGINT UNSIGNED NOT NULL COMMENT '所属订单 → orders.id',
    product_id    BIGINT UNSIGNED NOT NULL COMMENT '商品 → products.id',
    quantity      INT UNSIGNED    NOT NULL COMMENT '购买数量（1-5）',
    unit_price    DECIMAL(10,2)   NOT NULL COMMENT '成交单价（元）= ROUND(products.price × discount_rate, 2)，下单时快照',
    discount_rate DECIMAL(3,2)    NOT NULL COMMENT '成交折扣率（1.00/0.95/0.90/0.85/0.80 加权），解释同商品成交价差异',
    sale_amount   DECIMAL(10,2)   NOT NULL COMMENT '行小计（元）= unit_price × quantity',
    PRIMARY KEY (id),
    KEY idx_order_items_order (order_id),
    KEY idx_order_items_product (product_id),
    CONSTRAINT fk_items_order   FOREIGN KEY (order_id)   REFERENCES orders (id),
    CONSTRAINT fk_items_product FOREIGN KEY (product_id) REFERENCES products (id)
) ENGINE=InnoDB COMMENT='订单明细表（一行=订单里一种商品）';

-- ------------------------------------------------------------
-- 5. payments 支付表（约 89,000 行）—— 一笔成功订单恰一条
-- ------------------------------------------------------------
CREATE TABLE payments (
    id       BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '支付 ID',
    order_id BIGINT UNSIGNED NOT NULL COMMENT '对应订单 → orders.id（唯一）',
    amount   DECIMAL(10,2)   NOT NULL COMMENT '实付金额（元）= orders.order_amount（简化：无运费/优惠券）',
    method   ENUM('微信','支付宝','银联') NOT NULL COMMENT '支付方式',
    paid_at  DATETIME        NOT NULL COMMENT '支付成功时间（≥ 订单 created_at，隔数分钟至数小时）',
    PRIMARY KEY (id),
    UNIQUE KEY uk_payments_order (order_id),
    KEY idx_payments_paid_at (paid_at),
    CONSTRAINT fk_payments_order FOREIGN KEY (order_id) REFERENCES orders (id)
) ENGINE=InnoDB COMMENT='支付流水（成功支付一条；pending/cancelled 订单无记录）';

-- ------------------------------------------------------------
-- 6. refunds 退款表（约 9,300 行）
-- ------------------------------------------------------------
CREATE TABLE refunds (
    id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '退款 ID',
    payment_id  BIGINT UNSIGNED NOT NULL COMMENT '对应支付 → payments.id',
    order_id    BIGINT UNSIGNED NOT NULL COMMENT '冗余订单 ID（= payments.order_id，免 JOIN 直接统计）',
    amount      DECIMAL(10,2)   NOT NULL COMMENT '退款金额（元，≤ 对应支付金额；= 全额时订单状态置 refunded）',
    reason      VARCHAR(64)     NOT NULL COMMENT '退款原因（质量问题/七日无理由/物流问题/错拍不想要/其他，加权）',
    refunded_at DATETIME        NOT NULL COMMENT '退款完成时间（≥ 支付时间 + 数小时，≤ 数据期终点）',
    PRIMARY KEY (id),
    KEY idx_refunds_payment (payment_id),
    KEY idx_refunds_order (order_id),
    KEY idx_refunds_refunded_at (refunded_at),
    CONSTRAINT fk_refunds_payment FOREIGN KEY (payment_id) REFERENCES payments (id)
) ENGINE=InnoDB COMMENT='退款记录（一单至多一条；部分退款订单状态仍为 completed）';
```

**索引设计逻辑**（站在分析查询角度）：分析查询的主过滤条件是**时间**（趋势/同比/环比 → 各表时间列单列索引）、**状态**（口径过滤 → `status`）、**维度外键**（JOIN 驱动 → user_id/product_id/order_id/payment_id，InnoDB 外键本来就要求索引）。每表 2-3 个二级索引封顶，不做复合索引——10 万行级的 `WHERE status IN (...) AND created_at >= ...` 走 `created_at` 范围扫描再过滤，实测预期亚秒级（W2 交付的 smoke 断言 ≤2s，§4.6）。复合索引（如 `(status, created_at)`）留到 W6 真出现慢查询再加，并作为面试素材（"我知道什么时候该加"）。一次性导入场景索引写入开销可忽略。

### 1.5 行数规模与推算依据

| 表 | 行数 | 推算依据 |
| --- | --- | --- |
| users | **20,000**（精确） | 要让平均每人约 5 单（100,000 ÷ 20,000），对应个人消费者在电商平台的年下单量级；同时 2 万行用户表让"复购率/新客"类问题有统计意义。若只给 5,000 用户则人均 20 单，复购率会高到失真 |
| products | **2,000**（精确） | 8 类目 × 250 个；平均每商品年销约 50 件（订单 10 万 × 件均 1.5 ÷ 2000），是"腰部商品"的合理热度，动销率/类目对比有区分度 |
| orders | **100,000**（精确） | 需求文档指定"约 10 万订单"，取整 100,000 便于断言与报告表述 |
| order_items | **≈150,000**（派生） | 每单商品种数分布：1 种 60% / 2 种 30% / 3 种 10% → 期望 1.5 种/单 → 100,000 × 1.5 |
| payments | **≈89,000**（派生） | status 分布：completed 65% + shipped 9% + paid 7% + refunded 8% = 89% 有支付记录（pending 3%、cancelled 8% 无支付） |
| refunds | **≈9,300**（派生） | 全额退款 = refunded 状态 8% = 8,000 条；部分退款 = completed 订单的约 2% ≈ 1,300 条 |
| 合计 | **≈37 万行** | 库文件含索引预估 200-300MB，InnoDB 默认 buffer pool（128M）即可承载，2核2G 轻松 |

**规模校验**：37 万行对 MySQL 是玩具级数据（单表百万行才需要开始关注），10 万行订单全表扫描在 2 核机器上亚秒级——"10 万订单"是**给评测和面试叙事用的体量**，不是性能压力。这个判断写明，防止后面有人"为了性能"过度设计。

**派生行数不精确断言**：users/products/orders 三表精确断言（=），order_items/payments/refunds 用区间断言（如 `85,000 ≤ payments ≤ 93,000`），因为随机抽样派生的行数天然波动。哪些精确哪些区间在 §4.6 断言清单里逐条列出。

### 1.6 时间跨度设计

**决策**：数据期为 **2025-10-01 00:00:00 → 2026-09-30 23:59:59，整整 12 个自然月**，锚定常量 `DATA_START` / `DATA_END` 写死在生成脚本里（不是"以今天倒推"，快照日期固定才可复现）。

理由：
1. **同比**需要往前看整 12 个月——2026 年任何月份的同比都有数（对照 2025 年同期）。
2. **环比/月度趋势**有 12 个数据点，画趋势、算环比才有内容；月度订单量带季节权重（见下），趋势题有真实信号。
3. **"上个月"无歧义**：数据截止 2026-09-30，而当前日期是 2026-10 月——"上个月 = 2026-09"是完整闭合的月份，评测集里所有"上个月"类问题有唯一正确答案。若数据滚到"最近 12 个月直到今天"，9 月不完整，"上个月 GMV"就没有稳定金标。
4. **相对时间口径必须显式声明**：数据是静态快照，Agent 如果拿 `NOW()`（真实的 2026-10-08）算"近 7 天"必然查到 0 行。因此系统提示词里静态注入一行"数据截至 2026-09-30，相对时间（今天/本月/近 N 天）以 2026-09-30 为基准"（§4.3），few-shot 金标 SQL 也用 `DATE_SUB('2026-09-30', ...)` 示范（§2.4）。被否掉的备选"让 NOW() 动态可用"（定期追加数据）——W2 的目标是数据层稳定供评测，动态追 加是维护负担且破坏可复现。

**月度订单量权重**（体现电商季节性，让"为什么 11 月订单最高"成为可分析的真问题）：

| 月份 | 2025-10 | 2025-11 | 2025-12 | 2026-01 | 2026-02 | 2026-03 | 2026-04 | 2026-05 | 2026-06 | 2026-07 | 2026-08 | 2026-09 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 权重 | 7.5% | **13%**（双11） | 9% | 8% | 6.5%（春节淡） | 8% | 7% | 7.5% | **12%**（618） | 7% | 7% | 7.5% |

（合计 100%；月内日期均匀分布——周末/时段波动属过度设计，明确不做。）

### 1.7 数据生成策略

**工具**：`Faker`（locale=`zh_CN`）+ Python 内置 `random`，固定种子 `--seed 42`（同时设 `random.seed` 与 `Faker.seed`，整条链路可复现：同种子 → 逐字节相同的 CSV）。

**各字段生成方式与质量控制**：
- `users.name`：Faker `name()` 中文姓名（20,000 个，生成后抽查前 50 行人工过目——Faker 偶有生僻组合，见 §6 风险 2）。
- `users.city/province`：**不用 Faker.address**（它自由生成地名，会让"各城市订单分布"失去业务含义）。用受控加权列表约 20 城（北京/上海/广州/深圳/杭州/成都/武汉/南京/重庆/西安/长沙/郑州/苏州/青岛/宁波/无锡/厦门/沈阳/昆明/大连），头部 6 城权重合计约 45% 保证 GROUP BY 有明显长尾；province 由 city 映射表带出，不是独立抽样。
- `users.gender`：男 51% / 女 49%。
- `products.name`：**模板拼接**"品牌 + 类目词 + 属性词"（如"云杉 数码 降噪蓝牙耳机"），品牌每类目 4-5 个虚构名。不用 Faker 自由文本——商品名要能按类目语义检索和阅读。`price` 按类目给价格带（数码 199-7999、美妆 39-599、图书 19-99 等），使各类目客单价天然有差异。
- `orders`：每用户订单数走**重尾分布**——先给每用户抽活跃参数 λ（对数均匀分布截断），再抽泊松，效果约 35-40% 用户仅 1 单、头部 1% 用户 >30 单，均值 ≈5。**为什么刻意重尾**：均匀分布下复购率会趋近 100%（人人复购）和全 1 单分布下趋近 0% 一样没意思；重尾让复购率 ≈70-80%、ARPU 分位数有区分度，评测题答案稳定。
- 订单时间：先按 §1.6 月权重抽月，月内均匀抽时刻；且 `created_at ≥ 该用户 registered_at + 1 天`。用户注册时间窗口取 2024-01-01 → 2025-08-31（保证人人有至少 1 个月可下单窗口，"注册早于下单"勾稽天然成立）。
- `status`：按目标比例加权抽样（completed 65% / shipped 9% / paid 7% / refunded 8% / cancelled 8% / pending 3%），**并受订单年龄约束**——completed 需下单 ≥7 天前、shipped ≥2 天、refunded ≥10 天、refund 未走完的老订单不能是 refunded；不满足年龄的自动降级到 pending/paid/cancelled。没有这条规则会出现"9 月 29 日下单 9 月 30 日已完成"的穿帮数据。
- `order_items`：每单商品种数按 60/30/10 抽 1/2/3；商品在类目内加权热销（幂律，避免均匀到没有爆款）；`quantity` 1-5 偏小值。
- `payments.method`：微信 55% / 支付宝 35% / 银联 10%。
- `refunds.reason`：质量问题 30% / 七日无理由 25% / 物流问题 20% / 错拍不想要 15% / 其他 10%；**部分退款设计**：发生退款的行为分两类——60% 全额退款（订单 status → `refunded`）、40% 部分退款（退 20%-90%，订单 status 保持 `completed`）。这个设计**故意**制造"退款订单数"的两个合法口径（§2.3 退款率条目的陷阱题依据）。

**数据一致性勾稽规则**（生成器必须满足，测试逐条断言，§4.6）：

| # | 规则 |
| --- | --- |
| R1 | `orders.order_amount` = 该单所有 `order_items.sale_amount` 之和（按分精确相等） |
| R2 | `orders.item_count` = 该单所有 `quantity` 之和 |
| R3 | `order_items.sale_amount` = `ROUND(unit_price × quantity, 2)`；`unit_price` = `ROUND(products.price × discount_rate, 2)` |
| R4 | `payments.amount` = `orders.order_amount`；有支付记录的订单**恰一条**支付 |
| R5 | pending / cancelled 订单**无**支付记录 |
| R6 | `refunds.amount` ≤ 对应 `payments.amount`；`amount = payments.amount` ⇔ 订单 `status='refunded'`；部分退款订单 `status='completed'`；一单至多一条退款 |
| R7 | 时间链：`registered_at < created_at ≤ paid_at ≤ refunded_at`，且全部落在数据期内 |
| R8 | 状态-年龄约束（见上）；状态与支付/退款记录的存在性互斥完备（R5 与 R4 的反面） |

### 1.8 生成与导入流程

`data/generate_dataset.py` 一条命令走完全程，三步分离但一个入口：

```
python data/generate_dataset.py --seed 42 --load
  ① 生成：写 6 个 CSV 到 data/dataset/（users.csv ~2.4MB、order_items.csv ~14MB 等，合计约 35MB；
     .gitignore 忽略该目录——CSV 是派生物，入库后即可删）
  ② 建库：用管理员账号（.env 的 MYSQL_ADMIN_*）执行 schema.sql 内联的建库建表逻辑 + 创建只读账号
     （CREATE USER ... IDENTIFIED BY 读 env；幂等：先 DROP TABLE 按外键逆序再建）
  ③ 导入：SET FOREIGN_KEY_CHECKS=0 + 关 autocommit，PyMySQL executemany 每批 5000 行，
     每表一个事务，完成后恢复外键检查并打印各表行数摘要
```

- **为什么中间落 CSV** 而不是直接 INSERT：① 生成慢（Faker 抽姓名、随机数）导入快（批量 INSERT），分离后重导不重算；② CSV 可以人工抽查数据质量（审"剧情"是否合理）；③ 出问题时定位是"生成错"还是"导入错"。被否掉的备选"直接 executemany 边生成边插"：省一步但复现性和可审查性都差。
- **为什么 executemany 而不是 LOAD DATA INFILE**：`LOAD DATA LOCAL INFILE` 需要服务端开 `local_infile=1`，Docker/云环境下默认关闭，是个经典坑；executemany 批 5000 行导 37 万行预估 **1-2 分钟**，够快且零配置。（生成阶段预估 **1-3 分钟**，瓶颈在 Faker 抽中文姓名和逐单随机；两项均为估计，编码时实测后把真实数字写进脚本输出。）
- 导入结束内置自检：逐条执行 §4.6 的断言清单（T1 先做脚本内置校验，T5 再补成 pytest 门控用例），任何一条不过直接报错退出——**坏数据不允许静默入库**。
- 幂等性：重复执行 `--load` 先清表再导，结果与首次一致（种子固定 + 全量重建）。

### 1.9 SQLite → MySQL 方言差异对 Agent 的影响

这张表同时服务两个目的：① 提示词要明确告诉模型"你写的是 MySQL 方言"（§4.3）；② 错误可读化要覆盖这些差异触发的报错（§4.1）。

| 差异点 | SQLite（W1） | MySQL（W2 起） | 对 Agent 的影响 |
| --- | --- | --- | --- |
| 日期格式化 | `strftime('%Y-%m', col)` | `DATE_FORMAT(col, '%Y-%m')` | **最高频差异**。模型训练语料两种方言都有，必须提示词点名 + few-shot 示范，否则strftime 报错率会很高 |
| 当前时间 | `date('now','-1 month')` | `CURDATE()` / `NOW()` / `DATE_SUB(..., INTERVAL n DAY)` | 相对时间题的主流写法完全不同；且本项目要用数据锚点 `'2026-09-30'` 替代 NOW()（§1.6） |
| 系统表 | `sqlite_master` | `information_schema.TABLES` / `SHOW TABLES` | `list_tables` 工具改造点（§4.1） |
| GROUP BY 严格性 | 宽松（可 SELECT 非聚合列） | 默认 `ONLY_FULL_GROUP_BY`，报 1055 | 模型偶尔写出的"宽松 GROUP BY"在 SQLite 能跑、MySQL 报错——错误可读化要把 1055 翻译成人话（报错原文很长，截断到 300 字符再给提示） |
| 字符串拼接 | `\|\|` | `CONCAT()` | 低频，few-shot 不示范则报 1064 |
| LIMIT | `LIMIT n OFFSET m` | 相同 | 无需处理，明示兼容即可 |
| 数值返回 | TEXT/REAL → str/float | DECIMAL → `Decimal`、DATETIME → `datetime` | 工具结果格式化时 `str()` 天然可读（Decimal 输出 `123.45`、datetime 输出 `2025-11-03 14:22:01`），无需特判，但 W2 测试要覆盖 |
| 建表自增 | `INTEGER PRIMARY KEY AUTOINCREMENT` | `BIGINT UNSIGNED AUTO_INCREMENT` | 只影响 DDL 文档展示，Agent 只读不建表 |

### 2.2 schema 文档（6 份）

每张表一份 markdown，**内容模板**（6 份统一结构，机器按整文件切一片）：

```markdown
# 表：orders（订单表）

## DDL
（完整 CREATE TABLE 语句原文，含全部 COMMENT）

## 列说明
| 列 | 类型 | 业务含义 | 示例 |
| id | BIGINT | 订单 ID | 100001 |
| ... | ... | ... | ... |

## 示例数据（3 行，来自库中真实数据）
（SELECT * FROM orders LIMIT 3 的真实导出结果）

## 关联关系
- orders.user_id → users.id（多对一：一笔订单属于一个用户）
- orders.id ← order_items.order_id（一对多：一笔订单含 1-3 条明细）
- orders.id ← payments.order_id（一对一：有支付记录的订单恰一条支付）
- orders.id ← refunds.order_id（一对零或一）

## 该表能回答的典型问题
- 每月订单量趋势？各状态订单占比？哪些用户下单最多？

## 注意事项
- 统计"支付成功的钱"不要直接 SUM(order_amount)——pending/cancelled 订单没有支付，
  应 JOIN payments 用 SUM(amount)。
- status='refunded' 仅表示"已全额退款"；部分退款的订单状态仍是 completed（见口径文档"退款率"）。
```

- **为什么每表一份整文件不切分**：表结构是强内聚单元（列名和列含义拆开就失去意义），按表切与需求文档 §8 面试考点"F3 切分策略：表结构按表切"一致。单文件约 600-900 汉字。
- **已知代价（写明，不是疏忽）**：bge-small-zh-v1.5 输入上限 512 token，单文件超出部分会被**向量路截断**——但 BM25 路索引的是完整原文（Chroma `documents` 存全文），混合检索恰好兜住这个截断。W6 消融可对比"每表 1 片 vs 2 片"，W2 先按 1 片走最简单的路。这正是一个可讲的 chunking 权衡案例。
- "3 行示例数据"**必须来自导入后的真实查询**而非手写：所以 T2 语料工单在 T1 导入完成之后执行（§5 顺序依赖），并作为 T2 验收项（防手写示例与真实数据不一致，模型学错格式）。

### 2.3 业务口径文档（11 条）

每条目固定四段结构，条目间用 `## 指标：<名>` 分隔（这也是切分边界）：

```markdown
## 指标：GMV（成交总额）
**定义**：统计期内成功支付的订单金额总和。
**精确计算口径**：SELECT SUM(payments.amount) ... WHERE 支付时间在期内。
**常见误用/陷阱**：① 不能 SUM(orders.order_amount) 不加状态过滤——pending/cancelled 订单没付款；
② GMV 不冲减退款（退款口径看"净销售额"）。
**关联列**：payments.amount、payments.paid_at
```

11 条清单（**≥3 条与 schema 列严格对应**，是 W3 口径陷阱评测题的命题依据；"关联列"字段即对应关系声明）：

| # | 指标 | 定义一句话 | 陷阱要点（对应评测陷阱） | 关联列 |
| --- | --- | --- | --- | --- |
| 1 | GMV | 支付成功订单金额总和 | SUM(order_amount) 不滤状态 = 错；不冲减退款 | payments.amount / paid_at |
| 2 | 净销售额 | GMV − 退款金额 | 与 GMV 混用是典型错答 | payments.amount、refunds.amount |
| 3 | 客单价 | GMV ÷ **支付订单数**（DISTINCT order_id 去重） | 分母用订单总数（含未支付）或用户数 = 错（后者是 ARPU） | payments.amount / order_id |
| 4 | ARPU | GMV ÷ 统计期在册用户总数 | 与客单价（ARPPU）混淆 | payments.amount、users.id |
| 5 | 复购率 | 期内下单 **≥2 次**的用户 ÷ 期内下单用户 | 把"买 ≥2 件"当复购（件数≠次数）；期间不锁定 | orders.user_id / created_at |
| 6 | 退款率（双口径） | 金额口径 = SUM(refunds.amount)/SUM(payments.amount)；订单口径 = 有退款记录订单数 ÷ 支付成功订单数 | **orders.status='refunded' 会漏掉部分退款订单（其状态仍是 completed）——必须查 refunds 表**；两口径数值不同且都合法，回答必须报口径 | refunds.amount / order_id ↔ orders.status |
| 7 | 同比 / 环比 | 同比 =（本期−去年同期）÷去年同期；环比 =（本期−上期）÷上期 | 本期为 0 除零；自然月边界用 DATE_FORMAT('%Y-%m') | 各表时间列 |
| 8 | 支付转化率 | 支付成功订单 ÷ 全部订单（含 pending/cancelled） | 分母漏掉未支付状态 = 虚高 | orders.status ↔ payments |
| 9 | 动销率 | 期内有售出的商品数 ÷ 在售商品总数 | 分母口径要声明（本项目无下架概念，= 全部商品） | products.id ↔ order_items.product_id |
| 10 | 连带率（件单比） | SUM(quantity) ÷ 订单数 | 与客单价（金额口径）混淆 | order_items.quantity ↔ orders.id |
| 11 | 新客数 / 新客占比 | 期内**首次**下单用户数及其占比 | 与"新增注册用户"混淆（注册 cohort ≠ 首单） | orders.user_id / created_at、users.registered_at |

条目 1/3/6 是硬性对应的口径陷阱命题点（GMV↔payments.amount vs orders.order_amount；客单价分母；退款率 vs orders.status）。每条 80-150 字，全文档约 1200 字。

### 2.4 few-shot 问答对（11 条）

格式（`qa_pairs.md`，机器按 `### QA-xxx` 分隔切分）：

```markdown
### QA-001
**问**：2026 年 3 月每天的订单量是多少？
**金标 SQL**：
SELECT DATE_FORMAT(created_at, '%Y-%m-%d') AS order_date, COUNT(*) AS order_count
FROM orders
WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01'
GROUP BY order_date ORDER BY order_date;
**说明**：时间过滤用左闭右开区间，避免 BETWEEN 在边界时刻的归属歧义。
```

首批 11 条按评测五类覆盖（单表 / 多表 JOIN / 聚合统计 / 时间窗口 / 口径陷阱），**金标 SQL 全部遵守 §2.3 口径**，示例要点：时间一律左闭右开；相对时间以 `'2026-09-30'` 为锚（QA-007 显式示范 `DATE_SUB('2026-09-30', INTERVAL 6 DAY)`）；退款必查 refunds 表（QA-004）；日期格式化必用 DATE_FORMAT（QA-001/007）。

### 3.1 Chroma collection 与索引参数

```python
client = chromadb.PersistentClient(path=str(REPO_ROOT / "data" / "chroma_db"))   # 绝对路径
collection = client.get_or_create_collection(
    name="rag_corpus",
    configuration={"hnsw": {"space": "cosine", "ef_construction": 200}},
)
```

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `space` | `cosine` | 文本语义相似度标准选择；bge 输出归一化向量。**默认是 l2，不显式设是新手第一大坑**（Chroma 文档坑清单 #2） |
| `ef_construction` | 200 | 建图质量，官方建议值；28 条语料其实毫秒级建完，取推荐值不留隐患 |
| `ef_search` | 不调（默认 100） | 28 条语料 HNSW 近似退化为近全量比对，调参无意义；W6 语料上千条后再谈 |
| `path` | 绝对路径（config 用 `REPO_ROOT` 拼接） | 坑清单 #1：相对路径换启动目录即"数据丢失" |
| client 实例 | 模块级单例 | 坑清单：一个进程只建一次，多实例冲突 |

**重建策略：删 collection 全量重建，否决增量 upsert。** 理由：① 28 片重建 <1s，增量毫无收益；② 增量 upsert **清不掉已删除/改名的旧片**（id 是确定性的，改名后旧 id 残留成为检索幽灵），全量重建天然自愈；③ "语料更新时 rebuild() 一次"本就是实战文档给出的语义。触发方式：语料 md 有改动后手动跑 `python -m agent.rag.build_index`（W5 接反馈闭环后改为 👍 入库时触发）。

**坑清单落实对照**（来自《Chroma 实战》§7，编码 Agent 逐条自查）：#1 绝对路径 ✓；#2/#3 显式 cosine、不指望 get_or_create 升级配置 ✓；#4 重建不用 add ✓；#5 metadata 标量、空值用 `""` ✓；#6 `n_results` 用 `min(top_k_each, 该类型条数)` 兜底 ✓；#8 版本锁 `chromadb>=1.5.5,<2` ✓；#10 worker=1 是 W8 部署议题，此处仅备忘。

### 3.2 Embedding 细节

- 模型 `BAAI/bge-small-zh-v1.5`（512 维），fastembed 本地 ONNX，`embeddings=` / `query_embeddings=` **始终显式传入**（实战文档"三个理解点"第 2 条：不传会加载 Chroma 内置默认模型，维度对不上直接报错）。
- **查询侧加 bge 指令前缀**`"为这个句子生成表示以检索相关文章："`，文档侧不加——实战文档坑清单 #9 建议 W6 统一口径，本设计**从 W2 就统一**（实现封装进 `embedder.embed_query()` 一行，后续不再是实验变量）。
- `embedder.py` 把 fastembed 包成极薄接口 `embed(docs: list[str]) -> list[list[float]]` / `embed_query(q: str) -> list[float]`，并把**该接口作为可注入依赖**传给 HybridRetriever——测试注入确定性假向量，不依赖模型下载（§4.6）。
- fastembed 是否支持 `query_embed` 便捷方法/离线缓存目录参数，**编码前验证（§8）**，不支持就手动拼前缀字符串。

### 3.3 jieba 自定义词典

BM25 路的分词质量直接决定关键词召回（实战文档 §4.3 第 5 条）。`jieba_dict.py` 在检索模块加载时统一执行 `jieba.add_word`，词表三类：

1. **表名（6）**：`users` 不用加，但 `order_items`、`order_payments` 类下划线复合词必须显式加——jieba 对含下划线的英文串是否保持整词**取决于其内部正则的切分行为，编码前必须实测（§8）**，并给每个词写一条 `lcut` 断言测试，行为变了测试立刻红。
2. **高频列名**：`order_amount`、`created_at`、`paid_at`、`refunded_at`、`user_id`、`product_id`、`sale_amount`、`discount_rate`。
3. **指标中文名与缩写**：`GMV`、`ARPU`、`客单价`、`复购率`、`退款率`、`动销率`、`连带率`、`支付转化率`、`同比`、`环比`、`新客`。常用词 jieba 多半认识，但 add_word 幂等且零成本，显式声明保证分词结果**可复现**（BM25 测试依赖稳定切分）。

### 3.4 HybridRetriever 接口与检索参数

按实战文档 §4.2 骨架，W2 细化为以下接口（内部实现 = 骨架代码 + §3.1/§3.3 的兜底，编码 Agent 不重设计）：

```python
class HybridRetriever:
    def __init__(self, collection, embedder, k: int = 60): ...
    def rebuild(self) -> None: ...                       # 全量拉语料重建 BM25 分组索引
    def search(self, query: str, doc_types: list[str] | None = None,
               top_k_each: int = 20, top_n: int = 8) -> list[RetrievedChunk]: ...

@dataclass
class RetrievedChunk:
    id: str; doc_type: str; title: str; text: str; rrf_score: float
```

相对骨架的三处明确化：
1. `search` 返回结构化对象而非裸 dict（W3 评测的 Recall@K 直接消费 `id`/`doc_type`）。
2. `doc_types=None` 时不过滤、全类型参与检索——Agent 主链路就是全类型（模型需要同时看到表结构+口径+示例），按类型过滤保留为评测/调试能力。
3. RRF 平局按 `(−score, id)` 排序保证**可复现**（实战文档 Q&A 第 4 条明确要求）；BM25 路按 doc_type 分组建索引、每个类型独立排名参与融合——同一片文档在两个 BM25 组都被命中时得分叠加，这是骨架的既定语义，保持一致。

**检索流程参数**（建议值，**全部标注 W6 消融再调**）：

| 参数 | 建议值 | 理由 |
| --- | --- | --- |
| BM25 路 topK（`top_k_each`） | 20 | 骨架默认；28 片语料下相当于"每类型取全部"，融合由 RRF 分数自然排序。K 太小融合不出"两路都认可"的候选 |
| 向量路 topK（`n_results`） | `min(20, 过滤后条数)` | 与 BM25 对称；min 兜底防 contiguous 报错（坑 #6） |
| RRF `k` | 60 | 骨架默认；平滑排名差距的标准起点 |
| 最终注入条数（`top_n`） | **8** | 见下 |
| 查询侧指令前缀 | 固定加 | §3.2，W6 不再作为变量 |

**top_n=8 的理由**：语料 28 片（6+11+11），一次分析型提问理想情况需要 2-4 张表文档 + 1-2 条口径 + 1-2 条示例，8 条覆盖典型需求；再多则注入 token 膨胀（每片 80-150 字 × 8 ≈ 1000 字，尚可控；12 条就接近 2000 字）且尾部相关度已很弱。**W6 消融计划：top_n ∈ {5, 8, 12}、k ∈ {10, 60}、有无 BM25 路对比**——这组实验本身就是简历数字来源，W2 只需保证参数全部收口在 config 常量（§4.2），不散落在代码里。

### 3.5 prompt 注入格式与 W1 替换方案

`core/agent.py` 的系统提示词从"W1 全静态"改为"**静态骨架 + 动态参考资料**"两段：

```
你是一名电商数据分析助手……（角色定位，不变）

【数据库】
- MySQL 8.0，库名 mart，只读。SQL 必须用 MySQL 方言（日期用 DATE_FORMAT/CURDATE/DATE_SUB，
  禁止 SQLite 的 strftime/date('now')；字符串拼接用 CONCAT）。
- 库中数据表一览：users（用户表，2万行）/ products（商品表，2千行）/ orders（订单主表，10万行）
  / order_items（订单明细，15万行）/ payments（支付，8.9万行）/ refunds（退款，9千行）。
- 数据范围为 2025-10-01 至 2026-09-30 的静态快照：用户问"今天/本月/近 N 天"等相对时间时，
  一律以 2026-09-30 为"今天"计算。

【参考资料】（由检索层按当前问题动态注入，按相关度排序，共 N 条）
--- [1] 表结构 · 订单表 orders ---
（chunk 全文）
--- [2] 业务口径 · GMV（成交总额） ---
（chunk 全文）
--- [3] 示例问答 ---
问：……
SQL：……
说明：……

【行为规则】
1. 写 SQL 前先依据【参考资料】中的表结构和业务口径；资料未覆盖时用 list_tables 工具探查。
2. 只生成 MySQL 方言的只读 SQL（SELECT/WITH 开头），任何写操作都会被拒绝。
3. 所有金额单位是元。回答口径类问题时说明所用口径（如"按支付成功金额计"）。
4. 回答必须基于工具返回的真实结果；查不到就如实说明，不要编造。

```

三个设计点：
- **W1 内嵌 DDL 段整体删除**，替换为动态【参考资料】；但**新增常驻"表一览"6 行**（表名+一句话+行数量级）。理由：检索是概率性的，若某次没召回任何 schema 片，模型至少知道"库里有哪 6 张表"可以调 `list_tables` 兜底，不会幻觉出不存在的表。这是"动态检索 + 静态底线"的双保险。
- 行为规则第 1 条从 W1 的"先 list_tables 再写 SQL"改为"先查参考资料，list_tables 降级为兜底"——检索命中时省一次工具往返。
- 口径声明进规则第 3 条：口径陷阱题（退款率双口径）不仅靠语料，还在提示词层面要求模型自报口径，W3 评测时这一条对错答率的影响可以直接观察。

### 3.6 多轮问题的检索 query 处理

已知短板：checkpointer 让 Agent 记得"那 10 月呢？"的上下文，但**检索层拿到的裸 query "那 10 月呢？"检索不出任何东西**（W1 的多轮能力救不了检索）。

W2 方案（够用且简单）：检索 query = **thread 内上一条用户消息 + 当前消息**的拼接（main.py 从 checkpointer 取最后一条 HumanMessage）。代价是引入一点噪声（长问题拼接稀释关键词），收益是"那 10 月呢"能带着"上个月 GMV"的语境召回口径和时间写法。W3 评测若发现噪声伤害单轮检索精度，再升级为指代改写（让模型先改写 query，属 P1 增强），W2 不做。标注：此为已知妥协，W3 复核。

- `SYSTEM_PROMPT` 拆为 `build_system_prompt(context_block: str) -> str`：静态骨架（§3.5 的【数据库】+【行为规则】）+ 动态【参考资料】块参数化。W1 内嵌 DDL 删除。
- `build_agent(system_prompt: str)` 参数化；**checkpointer 提为模块级单例**，每请求重建 agent 时传入同一 checkpointer，多轮记忆跨请求不丢。为什么"每请求重建"而非"启动时建一次"：`create_agent` 的 system_prompt 是构造参数，动态注入最直接的实现就是每轮用新 prompt 组装（组装成本是微秒级的，模型客户端连接可复用）；备选方案"每轮 prepend 一条上下文消息"会污染 checkpointer 里的对话历史，影响多轮语义，否决。
- 检索器初始化：模块级懒加载单例（fastembed 模型加载一次约几秒，进程生命周期内复用）。
- **编码前验证（§8）**：`create_agent` 重复调用 + 共享 checkpointer 的组合行为（记忆连续性、工具注册）需写一个冒烟测试确认。

### 4.4 `agent/main.py`

需要动，但最小改动：① 启动 preflight——MySQL 连通性（用只读账号发一条 `SELECT 1`）与 Chroma 索引存在性检查，失败时给中文排查指引（"请先运行 python data/generate_dataset.py --load"/"请先运行 python -m agent.rag.build_index"），代替 W1 只查 API key 的单点预检；② 每轮用户输入后先调 `retriever.search(...)`（§3.6 的 query 拼接），组装 system_prompt，再进入原有 stream 循环；③ banner 版本号 W1→W2。对话主循环、流式打印、异常兜底逻辑一律不动。

8. 状态-年龄：不存在 `created_at > '2026-09-23' AND status='completed'` 类穿帮（7 天年龄规则）
9. 月度 sanity：每月订单量 > 5000 且 2025-11 为最大月（季节权重生效）
10. 工具端到端：`list_tables` 返回 6 表；`execute_readonly_sql("SELECT COUNT(*) FROM orders")` 含 100000；坏列名返回含"SQL 错误"的可读中文；`DELETE` 被拒且数据不变
