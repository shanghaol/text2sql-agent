# 第一幕：开场（前 30 秒定生死）

## Q1 "介绍一下你这个项目"（30 秒版）

**口语稿**：
> 我做了一个中文自然语言数据分析系统：用户说"上个月 GMV 多少"，单 Agent 通过混合检索拿到表结构和业务口径，生成只读 SQL 查 37 万行电商数据，流式返回带口径声明的结果。技术栈是 LangChain + DeepSeek + Java 网关 + Vue3，已上线。最有特点的是两件事：一是 BYOK——用户自带 LLM Key，服务端结构性不留站点级密钥；二是**用 9 组单变量消融量化了每个组件的贡献**——RAG 整体 +12.7pp，few-shot 路最大单项 −16.7pp，rerank 是负结果没上线。27 天从设计到上线，约 550 项测试。

**要点**：30 秒内必须出现"上线""量化""负结果"三个词——分别证明工程完成度、实验能力、诚实文化。

## Q2 "为什么做这个项目？"（动机题，防"为做而做"）

**口语稿**：
> 三个目的：一是 12 月实习投递需要一段有量化验证的 AI 工程经历——"会用 LangChain"在 2026 年已经不是加分项，我用消融实验把每个组件的贡献拆到了 pp 级；二是我的技术栈是 Java 后端，这个项目让我用 Spring Boot 承载 AI 工程的工程化层（鉴权/审计/密钥），验证了"Java 工程化 + Python 大脑"的分工在我身上可行；三是我想练一个完整的方法论——不是让 AI 写代码，而是为它设计决策框架、质量门和诚实约束。

**追问**："27 天完成 8 周的量，是不是偷工减料？"→ 用测试账本回（550+ 项）+ 排障深度回（四段根因链）+ 审查回（六轮独立审查）。

# 第二幕：简历条目逐条拷打（每条 2-4 个追问）

## B1 双服务架构 + 四层安全防线

**Q "为什么 Java 和 Python 分开？一个服务不行吗？"**
> 语言贴近职责：Java 是我最强栈，鉴权/限流/审计/密钥加密是它的主场（HikariCP/Security/jjwt 生态）；Python 有 LangChain 生态。分离还带一个安全收益：解密后的 key 只在内网头里走一跳（127.0.0.1 loopback），Python 容器不发布端口，暴露面最小。代价是多一跳内网延迟（本机 <1ms）和一套 SSE 代理透传——值得。
> **这也是国内大厂的真实分工**——"Python 做大脑、Java 做工程化"。

**Q "四层防线具体是什么？每一层拦什么？"**
> ① DB 只读账号（text2sql_ro，仅 SELECT ON mart.*）——权限在 DBMS 内核，代码任何 bug 绕不过，实测 INSERT 报 1142；② 会话级 `SET SESSION TRANSACTION READ ONLY`，挂在连接池 connect 事件——防"误把高权限账号配进配置"的运维事故；③ sqlglot AST 白名单——根节点白名单一条规则兜住全部写操作，加树扫描锁读/INTO、五函数黑名单；④ `max_execution_time=10s` 服务端真终止。**每层拦的事故类型不同**：账号层是权限边界，超时层是资源边界，AST 层给模型中文可读拒绝（前两层只会报英文错误码，模型拿到没法自我修正）。

**追问**："AST 层怎么实现的？会不会误杀？"→ 40 组对抗 SQL 实测全拦（CTE 包写、子查询锁读、UNION 半写、注释混淆）；34 条金标 + 11 条 QA SQL 零误杀；ParseError 附原文供模型修正。升级原因也有数据：正则的两个已知缺陷（字面量误杀/子查询 LIMIT 漏判）被 AST 消除。

## B2 混合检索 RAG + 自进化语料

**Q "为什么用混合检索？纯向量不行吗？"**
> 消融数据：纯向量 −2.0pp。BM25 的独特价值在精确 token——但比预期小（W2 预期"保命"，实际只贡献 2 个点）。真正的发现是 **few-shot 路才是最大单项**：去掉 −16.7pp（>3σ），示例层从 52% 崩到 9%。这改变了我的优化认知：示例的价值不止"提供可套模板"——远例层也掉了 13 个点，说明示例还隐式教学了 SQL 风格与时间写法。

**Q "怎么防止用户点赞污染语料？"**
> 六道门槛 + 双层去重 + **手动 dry-run 人工过目**。核心判断：点赞 ≠ 正确，自动入库的污染是静默且全局的（错误示范会被每次检索命中）。回滚 = git revert 一个 md 文件。阈值（语义 0.92）经真实数据标定：改写 ≥0.81、不同题 <0.78，0.92 落空档。

**Q "自举闭环跑过真实数据吗？"**
> 闭环代码与门槛全就位并经 35 项测试；线上真实点赞样本截至 W8 清理时为零（demo 早期无真实用户）——**这是诚实的数据点而非缺陷**：自举的入口、质量门、版本化纪律全部就绪，等真实流量。清理脚本同时防了测试点赞样本污染样本池。

## B3 评测与消融（必考总题）

**Q "你的准确率数字怎么来的？可信吗？"**
> 判定器 v2.1：金标与模型 SQL 都真库重放、比较结果集（同义 SQL 判对、文本比对会误伤）；判定逻辑变更时**离线复判历史**（132 次零翻转）。可信度三重背书：① 1274 条消融记录被独立审查**真库全量重放复算，零翻转**；② 每行 detail 记 corpus_commit + 全部实际生效参数（发现并修掉一个 rrf_k 硬编码谎报隐患）；③ 三级分层（示例/近例/远例）让数字可拆解不糊弄。

**Q "E 行 +4.6pp 为什么在简历里降格了？"**
> 逐 run 波动 32/24/38%，Δ≈1σ 未超运行方差——独立审查要求降格为"方向性观察"。**统计学对简历工程的纠偏**：主数字（RAG +12.7pp ~2.5σ、few-shot −16.7pp >3σ）显著成立，边际效应必须带方差口径。

**Q "rerank 为什么是负的？详细讲。"**（负结果深挖，答好极加分）
> 三行：全量重排 −4.0pp；配额修正 −10.0pp；纯顺序对照 −6.0pp。Recall 拆解：rerank 把 schema 召回提到 83.9%（+31pp，它干了它的活）但 glossary 被挤掉。**修正过程**：W6 的机制假说（口径片被挤出→答错）被自家明细复核推翻——被挤掉的题有片时也没答对，真正的注入变化主项是示例片稀释。C 行（成员不变纯顺序对照）−6.0pp 证明**顺序扰动本身伤生成**——与构成无关的独立通道。终稿：不启用，代码留档。

**追问**："会不会是 rerank 模型不行？"→ C 行证明与模型无关的顺序重排也伤——换模型仍要过这关；且预算内两个负结果后继续试错期望收益为负。
**追问**："实现过程中踩过什么坑？"→ 两段：首版 C 行把池内全部 schema 片前置（构成也变了）——自查发现偏离预注册定义，修正重跑而非拿偏离版冒充；离线选片函数与运行时实现是两份代码导致语义漂移（一致性核对抓到）——教训"离线标定必须 import 运行时函数"。

## B4 BYOK 密钥管理

**Q "用户的 Key 放哪？怎么防泄漏？"**
> 六跳链路：前端只存掩码 → HTTPS body → Java 免费幂等校验（GET /models）→ AES-256-GCM 落库（IV 每次随机——GCM 的 IV 复用是灾难性错误）→ 对话时解密走内网头 → 即用即弃。验收动作是**可执行的**：grep 全部日志 "sk-" 恒为 0。服务端结构性不留站点级 Key（env.prod 生成脚本核对 DEEPSEEK 计数 = 0）。

**追问**："主密钥丢了？"→ 已存 key 全部不可解，用户重录即可——无数据损失；泄漏 → 清表+通知重录。轮换留了 key_version 列位。
**追问**："审查真发现问题了吗？"→ 两轮：密钥泄漏面穷举通过；但抓到过 **XFF 首值伪造绕过限流**（实测 12 次登录全 401 从不 429）——修复为 nginx 注入 X-Real-IP + Java 只信它 + 服务绑定 127.0.0.1，生产复测伪造头第 13 次 429。**"审查发现→实测复现→修复→生产验证"完整闭环**。

## B5 BYOK 之后的成本与滥用

**Q "用户 Key 之外，你的站方成本和滥用风险呢？"**
> 站方成本 ≈ 0（无 LLM 调用、检索全本地）。滥用防四道：对话 10 次/分/用户、全局并发 4（2 核 CPU 的物理真相）、key 校验 5 次/分、登录 10 次/分/IP——**实弹验证过绕过面**：XFF 伪造被修复（见上）。数据面无写风险（只读账号）。

## B6 上线与部署

**Q "2 核 2G 怎么跑这么一套东西？"**
> 逐项记账：MySQL 450M + Python 450M + Java 550M + nginx 30M ≈ 1.48G + swap 2G 兜底；每个服务 MemoryMax 封顶——**失控只 OOM 自己不拖死整机**。MySQL 从 5.7 升级 8.0（相册平台同机共存，数据逐表核对一致）。排障四段全有根因链：h2c 升级头、模型缓存 %TEMP%、env 变量名跨服务冲突、Pinia 响应性丢失。

> ⚠️ 以下区域是**本项目没覆盖**的通用八股，面试可能问到但答案不来自这个项目。策略：与项目相关的迁移说迁移，无关的诚实说"项目没涉及，我的理解是…"。

# 第四幕：场景设计题（用项目经验答新场景）

**Q "设计一个客服智能体，你会怎么做？"**
> 迁移四层防线（只读视图 + AST 白名单 + 超时 + 审批升级为敏感操作卡）、迁移 BYOK（客服场景站方持 key 更合理，但密钥管理链路复用）、迁移消融方法（先建评测集再上线——我的教训是"评测先于优化"）。**差异点诚实说**：客服需要多轮澄清与情绪处理，我的项目是单轮分析——澄清机制我只做了 409 引导，完整设计要重新做。

**Q "如果数据量到 1 亿行，你的系统哪里先崩？"**
> 按层说：① SQL 层——AST 白名单不管数据量，但无索引的全表扫会撞 10s 超时（这是特性不是 bug，超时文案引导加过滤）；② 检索层——语料片数增长后 top-8 竞争加剧（F 行已证明挤出现象），需要 rerank+配额或两阶段检索；③ MySQL——buffer pool 与索引设计要重做。**这就是消融实验的另一半价值：它给了容量规划的地图。**

# 附：临场三原则

1. **每个数字带口径**（"26.7%，50 题三层分层，3 runs 均值，判定 v2.1"）——口径脱口而出 = 真做过
2. **负结果主动讲**（rerank 双轮消融）——把"失败"变成"实验设计能力"的证据
3. **不知道就说不知道，然后说你知道什么**（"这个项目没涉及，我的理解是 X，依据是 Y"）——诚实文化从对话延伸到面试
