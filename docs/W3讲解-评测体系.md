# W3 讲解：评测体系（教学四件套）

> 交付时间：2026-10-10 ｜ 对应需求文档 W3 里程碑 + 《W3设计-评测体系.md》
> 本周的本质：**你从"做了一个系统"升级为"能证明这个系统有效"**——这是"会用 LangChain"和"会做 AI 应用"的分水岭，也是面试必考题"Agent 怎么评估效果"的完整弹药库。

## 一、做了什么（W3 全景）

```
eval/dataset/eval_v1.jsonl（30 单轮）+ eval_v1_multiturn.jsonl（4 多轮）
        │  每条：question + 金标SQL + ordered + expected_chunks + standard_wrong
        ▼
eval/run_eval.py（runner：与线上 main.py 逐点同构）
        │  每题：检索注入 → build_agent → invoke → 提取 tool_calls 里的 SQL
        │  评分：金标 SQL 与模型 SQL 都由评测器重放 → 比较结果集
        ▼
eval/judge.py（纯函数判定：规范化 / 容差 / 多集合 / 文本回退 / 错答三档分类）
        ▼
eval/reports/  report_*.md（四指标汇总+声明段）+ detail_*.json（逐题全量明细）
```

**最终基线数字（主行 = 全系统 top_n=8 × 3 runs = 90 次运行）**：

| 指标 | 主行（含 RAG） | 对照行（top_n=0） | RAG 贡献 |
|---|---|---|---|
| SQL 级执行准确率 | **41.1%** | 6.7% | +34.4pp |
| 答案级准确率（含文本计算） | **64.4%** | 43.3% | +21.1pp |
| Recall@8 | 57.6%（glossary/qa 100%，schema 51.9%） | 0 | — |
| 多轮 4 题 | SQL 级 16.7% / 答案级 **91.7%** | — | — |

过程数字：冒烟抓到 EV-001 命题缺陷（31 行超工具截断）；基线首跑 32.2% 经解剖升级判定体系到 v2；170→201 测试；总成本约 82 万 token/轮次（缓存命中 87%）。

## 二、为什么这么做（七个关键决策的完整论证）

### 2.1 为什么评测"系统"而不是"裸 LLM"？（同构原则）

评测管线的每一行组装代码与 main.py 相同（设计 §2.3 有逐点对照表）。**证据**：实验二实测，去掉检索注入，同一道"上个月 GMV"的答案从 9 月变成 8 月——注入与否直接改变答案，所以"测出来的数字"强依赖"测的是哪个配置"。评测器若与线上有一处不同构，所有优化对比都失去基准。runner 顶部 docstring 写了"同构契约"：以后每次改 main.py 的每轮流程，必须同步评审评测管线。

### 2.2 为什么执行准确率比"SQL 文本相似度"优？

金标 SQL 和模型 SQL **各自在库里执行、比较结果集**。好处一：同义 SQL 判对——EV-028 实测，模型用 `>= '2026-09-01' AND < '2026-10-01'`，金标用 `DATE_SUB('2026-09-30', INTERVAL 29 DAY)`，SQL 长得完全不同但结果集相同，都判对（文本相似度会把前者判死）。好处二：**天然抗措辞抖动**——temperature=0 的服务端非确定性主要影响措辞，执行准确率只对"实质 SQL 不同"敏感。代价：要求金标 SQL 本身正确（T1 真库核对兜底）且题目可单条 SQL 表达（EV-001 教训，见 2.7）。

### 2.3 为什么金标只存 SQL 不存"期望结果值"？

如果把期望结果（比如 16,029,955.34）写死在评测集里，判定时要解决"DECIMAL 格式化成什么样才算相等"——手写必错。两边**同规则重放**后，类型规范化问题自动消失：不存在第三方的期望格式。死值只保留在陷阱题的 standard_wrong（错答模式分类用，那里比较的是单值）。

### 2.4 为什么容差是 max(0.005, 1e-3·相对)？

两个诉求的交集：① 吸收 ROUND 位数差异（模型写 ROUND(x,2)、金标写 ROUND(x,4) 不该判死——4 位小数的最大相对误差 ≈6.5e-4，1e-3 覆盖）；② **不放行陷阱错答**——所有登记陷阱与金标的差异都在 20% 量级（26.5%/39%/46%），月份偏移差 100%，容差比陷阱间距小三个数量级。有回归测试锁：0.0775 vs 0.0886 判不等、16,029,955.34 vs 20,280,681.72 判不等。

### 2.5 为什么要双层指标？（W3 最大发现，面试重点）

基线首跑（v1 判定，只认最后一次 SQL）只有 32.2%，解剖 61 个 fail 发现大量这种形态：**最后一次工具调用返回中间成分，最终答案在文本层计算**——EV-025 实测：SQL 返回两个月的数据行，文本算出环比 77.50% 与金标完全一致，却被判 fail。这不是模型错，是 Agent 相对纯 text2SQL 的能力增量：**多步取数 + 文本计算**。

v2 改成双层：SQL 级（严格口径，简历主数字）+ 答案级（单行单列金标允许从最终回答文本里匹配数值，% 形态自动换算）。**两者的差值 = 文本计算弥补单条 SQL 表达局限的部分（本基线 23.3 个点）**。修完 v1→v2 主行从 32.2% 修正到 41.1%/64.4%——教训：**评测器自己也要被审计，否则优化故事建立在误判上**。

### 2.6 为什么 expected_chunks 标"答对的必要知识集"而不是"预测会命中什么"？

Recall@K 只有和准确率**建立归因链条**才有意义：明细里"expected 缺失且判 fail"的题 = "检索失灵导致答错"的直接证据。所以标注规则是"缺失即大概率答错"的片才标（表文档必标、口径陷阱题标 glossary、只有实验二实证过"缺失即错"的 EV-003 才标 qa_pair）——把 qa 片普遍标进去会稀释信号（qa 片短、关键词强，几乎题题命中）。基线数据验证了这个设计的解释力：**schema 片 Recall 只有 51.9%，而 multi_join 题（全靠 schema 片）SQL 级仅 33.3%**——"召回弱→JOIN 错"的因果链直接指向 W6 优化方向。

### 2.7 为什么"答案行数 ≤ 工具截断上限 20"成了命题纪律？

冒烟 2 题抓到：EV-001 原题答案 31 行（3 月每天一行），模型 seq1 写了**正确的**整月查询 → 被工具 LIMIT 20 截断 → seq2 自作聪明改查"3 月 16-31 日"规避 → 最终 SQL 与金标语义不符。**工具约束是系统行为的一部分**：评测题必须在与线上一致的约束下"可被单条 SQL 正确回答"，否则测的是"模型对抗截断的策略"。修复：改题 15 行 + 命题纪律新增此条 + EV-016/018/024（恰好 20 行）登记为观察对象。

## 三、面试考点（四件套）——"Agent 怎么评估效果"的完整弹药库

### 3.1 "你的 Agent 效果怎么评估？"（必考总题，90% 概率被问）

**考察意图**：区分"跑过 demo"和"工程化做过 AI 应用"的分水岭题。答出分层指标+对照+消融三层结构即优秀。

**参考答法（90 秒口语稿）**：
> 我建了一套三层评测：① **评测集** 30 条单轮 + 4 条多轮，覆盖五类（单表/多表 JOIN/聚合/时间窗/口径陷阱），每条带金标 SQL 和"必要知识片"标注；② **判定**用执行准确率——金标 SQL 和模型 SQL 都在库里重放、比较结果集，而不是比 SQL 文本（同义写法判对）；因为发现 Agent 常用"SQL 取数+文本计算"两步作答，又加了答案级指标兜底；③ **对照**：跑了一行无 RAG 的消融（top_n=0），RAG 的贡献是 SQL 级 +34.4 个百分点（6.7%→41.1%）。
> 数字：SQL 级 41.1%、答案级 64.4%，三次运行取均值，报告里区分了"有 few-shot 示例的题"69.7% 和"泛化题"24.6%——这个断层就是后续优化空间。

**结合项目的加分句**：
> "评测体系自己在第一轮就抓到了两个问题：一道命题缺陷（答案 31 行超过工具 20 行显示上限，模型被截断反馈带偏）和一个判定缺陷（文本计算被系统性低估）——**评测先于优化，命题质量先于数字**。"

**可能的追问**：
- "怎么防止评测集泄漏？"→ 语料里的 11 条金标 QA 同时是 few-shot 示例——这是**有意的系统级设定**（few-shot 自举是功能），报告声明了口径，并把 30 题分层报告（示例命中 69.7% vs 泛化 24.6%）；W6 消融会量化 few-shot 的单独贡献。
- "30 条够吗？"→ v1 够出基线和方向，统计上每类 5-7 条能暴露大问题；W6 扩到 50 条时管线零改动（schema 按 50 条设计）。**数字的置信度靠 runs 次数和分层结构补**。

### 3.2 "执行准确率是什么？为什么不用文本比对 SQL？"（高频追问）

**参考答法**：
> 执行准确率（Execution Accuracy）是 NL2SQL 领域的标准指标：金标 SQL 和模型 SQL 各自在数据库执行，**比较结果集是否一致**——一致即对，不管 SQL 写法。我选它的三个理由：① 同义 SQL 判对（JOIN 顺序、别名、等价时间写法不该影响判定，实测 EV-028 两种完全不同的写法结果相同都判对）；② 抗措辞抖动（temperature=0 的非确定性主要在措辞层）；③ 不需要"SQL 语义等价"这种没法可靠计算的判断。
> 代价与兜底：要求金标 SQL 本身正确（我每条都在真库核对过）且题目能被单条 SQL 表达——我第一版评测集就有道题答案 31 行超过工具显示上限，模型被截断反馈带偏，这种题在命题阶段就要排除。

**追问**："结果集怎么比？行序呢？"→ 行多重集合比较（排序后逐位，正确处理重复行）；金标注 ORDER BY 的题（TOP-N 类）人工标注为有序、逐位比；数值用容差 `max(0.005, 千分之一相对)` 吸收 ROUND 位数差——容差比陷阱错答的间距小三个数量级，不会放行错答。

### 3.3 "基线才 41%，是不是太低了？"（诚实回应题，答好极加分）

**考察意图**：压力题。看你是护短、慌乱，还是把低分拆解成结构性的认知。

**参考答法（口语稿）**：
> 41% 要拆开看三个维度，每个都有明确解释和对应的优化手段：
> ① **分层看**：有 few-shot 示例的题 69.7%，纯泛化题只有 24.6%——45 个点的断层说明泛化能力是主要短板，优化方向是扩充示例库和提升 schema 检索；
> ② **归因看**：Recall@8 里口径片和示例片都是 100%，**schema 片只有 51.9%**，而最弱的 multi_join 题（33.3%）全部依赖 schema 片——"检索召回弱 → SQL 写错"的因果链是完整的，W6 的 rerank 和表文档切分消融就打这里；
> ③ **口径看**：41.1% 是 SQL 级严格口径；答案级（Agent 常用"SQL 取数+文本计算"两步作答）是 64.4%。**基线低不是坏事——它是 W6 消融的对照原点，每个优化项的贡献都要靠这个原点度量。**
> 另外这个 41% 经历过一次判定审计：v1 判定只认最后一次 SQL，把"SQL 取数+文本计算"的行为判了 fail，解剖后升级成双层指标——评测器自己也进了回归测试。

**可能的追问**：
- "那你的优化计划？"→ 已登记：schema 召回（rerank/切分）、few-shot 扩库、top_n 消融 {5,8,12}——每个改动跑同一评测集出贡献数字。

### 3.4 "temperature=0 为什么结果还不一样？"（一手量化数据题）

**参考答法**：
> temperature=0 只消除采样温度这一层随机性；服务端的批处理、MoE 路由、硬件非确定性仍会带来输出波动。我有实测：30 题跑 3 遍，overall 从 30.0%/43.3%/50.0% 波动，**4 道题三次结果不一致**（如 EV-030 退款率姊妹题 fail-fail-pass）。应对是：① 执行准确率天然抗措辞抖动（只对实质 SQL 差异敏感）；② 多次运行取均值；③ 翻转题标 flaky 人工复盘——不机械取众数，因为"判定边界问题"和"模型真实不稳定"的处置不同。

### 3.5 "评测集怎么构造的？怎么防数据污染？"

**参考答法**：
> 五类配比 6/7/7/5/5，每条八字段 schema（问题/金标 SQL/有序性/必要知识片/标准错答登记）。命题纪律：① 答案行数 ≤ 工具截断上限（第一版有道 31 行的题，冒烟就抓了）；② 有歧义的口径在题面钉死（"金额口径""下过单的用户"）；③ 金标真库核对 + TOP-N 边界平局检查；④ 标准错答必须实测登记——错答模式分 trap/valid_alt_gloss/other 三档，"踩陷阱"和"答了另一个合法口径"分开统计，否则会误判优化方向。
> 污染问题的诚实回答：11 条评测题同时是 few-shot 示例——这是系统功能（自举）而非泄漏，报告声明了口径并分层统计；真正防的是新题与示例雷同，命题时时间窗/维度/指标全部错开。

### 3.6 "RAG 的价值怎么量化？"（你的独家数字）

**参考答法**：
> 消融对照：同一评测集，top_n=0（无任何检索注入）vs 全系统。SQL 级 6.7% → 41.1%（+34.4pp），时间窗和陷阱题从 0% 起死回生。更有意思的是失败形态的对比：无 RAG 时模型错得"原始"（找不到表、不知道有口径）；有 RAG 后经典陷阱（比如用 status 算退款率漏掉部分退款）一个都没踩——检索注入的不只是知识，还有意图消歧的锚定。

### 3.7 "Recall@K 是什么？你的检索短板在哪？"

**参考答法**：
> Recall@K = 应该被召回的知识片有多少进了 top-K。我的评测集每条标注"必要知识片"（缺失即大概率答错），判定注入列表与它的交集。基线：整体 57.6%，**分语料类型看 glosary/qa 全中、schema 片只有 51.9%**——而 multi_join 题准确率最低（33.3%）且全依赖 schema 片，归因链闭合。优化手段：rerank、调 top_n、表文档切分方式消融——每个手段跑同一评测集出贡献数字。

## 五、动手实验（五要素）

### 5.0 工具速查

```bash
.venv/Scripts/python -m eval.run_eval --rerun EV-030 --runs 1 --tag mytest        # 复跑单题
.venv/Scripts/python -m eval.run_eval --limit 3 --runs 1 --tag quick              # 前 3 题快跑
```
明细 JSON（eval/reports/detail_*.json）是逐题全量档案：SQL 调用序列/注入片/判定/延迟/token 都在。

### 5.1 实验一：亲手复现"非确定性"

- **验证目标**：亲眼看到 temperature=0 的服务端波动（3.4 题的一手体验）
- **操作**：`--rerun EV-030 --runs 3 --tag flaky_check` 跑两遍（共 6 次运行）
- **预期现象**：基线里 EV-030 是 fail/fail/pass——你的复跑大概率还会出现结果不一致；对比每次的 SQL（明细里有全文），找"哪里不同导致了翻转"（常见：口径选择在两可之间摇摆）
- **思考题**：如果不波动意味着什么？（可能模型对这题其实很确定，基线时的 fail 来自当次的服务端负载或缓存状态——非确定性研究没有简单答案，有数据比有结论重要）

### 5.2 实验二：验证"注入消歧"的因果（复现实验二的系统级版本）

- **验证目标**：EV-003 答对是因为 qa_003 被注入——把因果链亲手摸一遍
- **操作**：inspect_chain 跑 `上个月的 GMV 是多少`，确认注入含 `qa_pair:qa_003` 且答案为 9 月；然后临时把 `RETRIEVER_TOP_N` 设 0 再跑
- **预期现象**：top_n=0 时大概率答成 8 月（16,164,482.43）——与基线对照行一致
- **思考题**：qa_003 的金标 SQL 用的是锚点写法吗？如果不是，它靠什么消歧？（靠问答对的"问-答"对应关系本身——这提示 few-shot 的价值不止 SQL 写法示范）

### 5.3 实验三：错答模式人工归类（参与错答库生长）

- **验证目标**：理解 failure_mode 分类体系，亲手归类"other"
- **操作**：打开 detail_baseline_full_v2 JSON，挑 3 个 failure_mode="other" 的 fail 题，对照金标 SQL 逐行 diff 模型 SQL，判断错答成因（选错表？分母错？时间窗偏移？）
- **预期收获**：你会发现"other"里有可归类的新模式（比如把占比答成小数、把净销售额算成两个独立数）——把发现登记回 eval_v1.jsonl 的 standard_wrong，**错答模式库就靠这个机制生长**
- **思考题**：为什么要把"答了另一个合法口径"（valid_alt_gloss）和"踩陷阱"（trap）分开统计？（混在一起会误判优化方向：前者靠 glossary 检索改进，后者靠 schema/示例——归因错了优化就打偏）

### 5.4 实验四：算自己的 token 账

- **验证目标**：把报告里的抽象数字换成钱的感觉
- **操作**：报告给出单题均值 input 8,446 / output 659 / cache_read 7,947。打开 DeepSeek 价目页算：单题成本 = input×单价 + output×单价（注意缓存命中部分价格更低）；再乘 90 次（主行）估算全量
- **预期收获**：能回答"你的系统单次查询成本多少"这种工程面追问；顺手理解"为什么 cache_read 占 87%"——**Agent 多轮调用每轮重发全部历史，前缀缓存是 Agent 成本优化的第一杠杆**（面试聊降本时的一手数据）

## 六、审查战果（独立审查子 Agent，2026-10-10）

**总结论：无 P0/P1，数字可信。** 审查方式值得学：56 个构造对抗/边界用例实测判定器 + **独立重放金标与模型 SQL 复算全部汇总数字**（不是看报告，是自己再算一遍）。

**确认可信的证据链**：41.1%/64.4% 的产出链路（金标核对 → 同构 runner → 判定器 → 汇总统计）全部独立复现；21 个 text pass 逐条人工审计无巧合误命中；对照行/多轮/v1 口径数字全部复算一致；32 个 SQL 级 fail 逐题重放确认真不一致（"登记陷阱零命中"属实，非分类器漏报）。

**5 个 P2（均不影响本基线数字，登记在案）**：
1. 无序多重集合比较的排序键用 Decimal 字符串序，构造场景下可假 fail（方向是**低估**，本基线未触发）——W6 扩题前改数值化分桶
2. 文本回退对"年份类小整数金标"有巧合误命中面（当前 34 题金标无碰撞，21 个 text pass 逐条审计通过）——W6 扩题避开
3. **引用纪律**：23.3pp 差值里的 text pass 少数样本的最终答案并非由最后一次 SQL 推出——面试表述用"文本层最终答案命中"，别说成"全部由最后一次 SQL 计算"
4. verify_gold 一处错答值来源标注不实（值出自实验日志而非 qa_verification）——已修正措辞
5. "缓存命中 87%" 补了分母声明（占 input 94.1% / 占总 token 87.3%）

**最值钱的审查发现**（面试可讲）：审查方独立重放发现 EV-030 某次运行的最终答案 8.86% 并非由最后一次 SQL 算出（最后一次算的是 10.79%）——判定符合"只看最终回答"的规格且全序列留痕可审计，但它提醒我们：**答案级指标的语义是"最终回答命中"，不是"计算过程正确"**——两个指标各测各的，混着讲会被抓。
