## 二、为什么这么做（六个决策的完整论证）

### 2.1 为什么先用既有明细再分析，而不是直接设计修复实验？

300 条 W6 明细已在手，逐题复核零成本。结果**改写了修复方案的前提**：原假说（glossary 挤出→口径题答错）的 SQL 因果链在 run 级不成立（EV-029 有片时 0/3），真正的注入变化主项是 few-shot 示例片（−37.6%）。若直接按原假说设计实验，验证的会是一个与数据不符的机制——钱花了，结论却是错的。

**方法论**：负结果的处置顺序 = ① 复核归因（用已有数据）→ ② 修正假说 → ③ 离线标定 → ④ 预注册 → ⑤ 花钱实验。**每一步都可能推翻上一步**，这五步本身是可交付的方法论。

### 2.2 为什么配额选片可以离线穷举，rerank 调 LLM 参数不行？

**配额是重排结果之上的确定性选片函数**——同样输入必然同样输出，无随机、无采样。所以它的全部变体（主案 + 4 变体）可以在离线层零成本穷举，LLM 只需要验证离线最优的那一个。这与"调 LLM 侧参数必须全量跑"的成本结构完全不同。

**注意边界**：这个手法依赖"确定性"。执行时抽检发现 EV-008 的 rerank 尾序有微抖动（API 对近平 tie 的微差）——但 top-8 **集合**稳定、配额只关心类型构成，缓存判定可用。确定性假设本身也要抽检（§8-1），这就是验证清单第 1 条存在的原因。

### 2.3 为什么主案被离线否决是好消息而不是坏消息？

主案 floor=1 的离线预演 J1 失败——根因是"类型内排序劫持"（EV-029 池里有别的 glossary 片分数更高，floor 槽位被占）。这发生在花一分钱 LLM 之前。若没有离线标定：150 次跑完发现没救回 glossary，再回头查原因——**一次完整的实验预算换一个本可离线发现的问题**。

**方法论**：检索层实验的成本结构 = "离线可穷举的选片规则" + "必须实跑的生成侧效应"两类。先把第一类在离线层做完，LLM 预算只花在第二类。

### 2.4 为什么 C 行首跑偏离预注册后要修正重跑，而不是用 20.0% 的结果？

首版 C 实现"把池内全部 schema 片前置"——构成也变了（偏离预注册的"成员不变"定义）。拿它冒充 C 行结果 = 报告了一个未预注册的实验。**两次返工全程留痕**（rerank 返回元组被当 dict、下标空间错位；schema 前置改变构成），最终实现对齐预注册后才重跑。

**方法论**：预注册实验的**执行忠实性**与数字本身同等重要——"我跑的就是我预注册的那个实验"需要实现层面的证明，否则消融数字的纪律在最后一步失守。

### 2.5 为什么 rerank 的顺序扰动会伤生成？（机制层，开放问题之一）

C 行（成员与基线逐片相同、仅 schema 片内部重排）= −6.0pp：顺序扰动独立成立为伤害通道。候选机制（W8 复盘，不临场下结论）：rerank 语义分与 RRF 多路融合分的信号不同——重排后示例片与 schema 片的相对位置改变，可能干扰模型对"哪些资料支撑哪个结论"的引用模式。**注意这是一个候选解释，不是结论**——W7 的判别实验区分了构成/顺序两通道，但没有进一步区分顺序伤害的内部机制。

### 2.6 为什么 W5 遗留的"多 action 逐条审批 UI"降级为文案而不是实现？

三层协议改动（前端卡片重做 + Java decisions 列表化 + 等长校验）≈2-3 天联调，挤占 W7 主线。而真实多 action 轮是低频路径（模型重试/复合查询才触发），且被拒 SQL 若仍需要，**链式审批卡已覆盖该场景**（拒绝 → 模型重新发起 → 新审批卡）——只是多一次交互。做的三件事：chat.js 覆写修复（真实 bug：两条同名完成事件覆写同一条指示行，气泡展示被拒 SQL）、降级文案把"批 1 拒余"对用户透明化、逐条 UI 记 backlog。

## 三、面试考点（四件套）

### 3.1 "你说 rerank 没用，怎么证明的？"（负结果深挖的总题）

**参考答法（90 秒口语稿）**：
> 三行消融：全量重排 −4.0pp；按类型配额修正 −10.0pp；纯顺序对照（注入选集与基线逐片相同、仅 schema 片内部重排）−6.0pp。三行全负且方向一致——rerank 在我的 28 片语料与 top-8 注入预算上，任何形式都净负。
> 机制上拆两条通道：顺序扰动独立伤生成（C 行证明，构成不变也掉 6 个点）；构成变化叠加（FQ-cap 修了 glossary 反而更差，因为 qa 示例片被进一步稀释——而 few-shot 是我消融里最大的单项贡献者 −16.7pp）。
> 工程决策：不启用，配额代码留档为"验证过的修复尝试"。

**可能的追问**：
- "会不会是 rerank 模型不行？"→ 可能，但 C 行证明与模型无关的重排顺序本身也伤——换成更强 rerank 模型仍要过"顺序扰动"这一关；且预算内已验证两个负结果，继续试错的期望收益为负。
- "你的样本量够吗？"→ 每行 150 次（3 runs），E 行教训后所有 Δ 都带方差口径；C 行 −6.0pp 约为 1σ+，定性为"方向性"——**负结果叙事同样不夸大**。

### 3.2 "预注册是什么？为什么要做？"（方法论题）

**参考答法**：
> 跑实验之前把预期方向、判据阈值、分支走向写成冻结文档，跑完后不得改写（修正须新增附注）。三个作用：① 防 p-hacking——"跑完再看数据说话"会诱使人加跑有利实验；② 预算上界可控——分支树把"再试一版"的冲动写死为条件触发；③ **预注册被自家数据修正也是可交付的发现**——我的主案（floor=1）在离线预演就被否决，这个"被修正"的过程比"修好了"更能证明实验纪律。
> 实操：预注册写在 experiment-log 的独立段，LLM 实验开始之前落盘 commit。

**可能的追问**：
- "你的预注册被修正过吗？"→ 两次：① W6 的机制假说被自家明细复核修正（glossary 挤出降级为次要通道）；② W7 主案被离线标定否决（类型内排序劫持）。两次都换了假说再跑，且修正原因全部留痕。

### 3.3 "离线标定是什么意思？"（检索实验工程题）

**参考答法**：
> 关键观察：**配额是重排结果之上的确定性选片函数**——无随机、无采样、无阈值。所以全部变体可以在离线层用同一份池排序穷举（零 LLM 成本），LLM 只验证离线最优。50 题池提取 17 秒，6 变体扫描秒级，省下的是整行 150 次全量跑。
> 前提是**确定性要抽检**（rerank API 对近平 tie 有微抖动——实测 top-8 集合稳定、尾序有相邻交换，判定可用）；以及离线选片函数与运行时实现必须是同一份语义——我的一致性核对第一次就抓到了漂移（运行时少了 glossary/qa 的 cap，glossary 没救回），对齐后逐项一致。

**可能的追问**：
- "如果选片规则涉及 LLM 调用呢？"→ 那就不能离线穷举，退化为"每变体一小批冒烟 + 全量只跑最优"——成本结构变了，纪律不变（预注册照做）。

### 3.4 "W5 的遗留你怎么处理的？为什么逐条审批 UI 不做？"（工程判断题）

**参考答法**：
> 四项遗留按价值重估：chat.js 覆写 bug（真实缺陷，修）；openApproval 缺 threadId 交叉校验（1 行修）；死变量/docstring 纠偏（顺手）；**逐条审批 UI 不做**——真实多 action 轮是低频路径，三层协议改动 2-3 天，且被拒 SQL 走链式审批卡已覆盖，降级文案把既有兜底对用户透明化即可。ECharts 与 MCP Server 同样给了"不做"结论：ECharts 是门面不是区分项，MCP 封装与最强的安全叙事冲突（MCP 直调绕过 HITL 审批卡）。
> **克制是设计要求**：遗留项的"顺延 W7"标注是候选不是承诺，W6 已用行动证明遗留项要按价值重估。

## 五、动手实验（五要素）

### 5.1 实验一：亲手复跑确定性抽检

- **验证目标**：理解"离线穷举的确定性前提"为什么需要验证
- **操作**：同一问题跑两次 `search(rerank_pool=16, reranker=rr)`，比对完整 16 序与 top-8 集合
- **预期现象**：多数题逐位一致；个别题尾序有相邻交换（rerank API 对近平 tie 的微差），top-8 集合稳定
- **思考题**：如果 top-8 集合不稳定，离线标定还能用吗？（不能——需要多次取众数序或换确定性 rerank 实现；配额的覆盖集锚定依赖"基线行为可复现"）

### 5.2 实验二：三行注入构成的 diff（理解通道分离）

- **操作**：读三份 detail JSON（baseline_50 / rerank_bge / rerank_quota），对每题统计注入片的 doc_type 构成，画三行对比
- **预期现象**：F 行 qa 4.4→2.7；FQ 行 glossary 回升但 qa 1.98；schema 三行递增（1.3→3.0→3.1）
- **思考题**：F 行 schema +130% 为什么没带来提升？（schema 片的边际信息量递减——第 2、3 个 schema 片重复覆盖同一张表的相邻信息；这解释了为什么"召回更多"与"答得更对"脱钩）

### 5.3 实验三：openApproval 的越权面验证

- **操作**：本地双服务，用 A 账号的 token 带 B 账号 historyId + 伪造 threadId 调 /api/chat/approval
- **预期现象**：409 approval_not_found（threadId 交叉校验拦截）——且响应不泄露"该行存在于其他会话"
- **思考题**：为什么错误码复用 APPROVAL_NOT_FOUND 而不是专门的"会话不匹配"？（不泄露行是否存在于其他会话——越权面的信息一致性）

### 5.4 实验四：负结果叙事的复述练习

- **操作**：对照 experiment-log W7 段，不看文档口头讲一遍"负结果 → 再分析 → 假说修正 → 离线标定 → 预注册 → 判别实验 → 机制排除"全链路，录音回听
- **验收**：五分钟能讲完且每步有数字；讲不清的环节回对应文档
- **价值**：这套叙事是"实验设计能力"的直接展示——简历第二部分第二段的最强支撑
