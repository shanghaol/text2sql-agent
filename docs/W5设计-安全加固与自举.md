### 0.3 设计总原则（延续 W2-W4）

1. **公共函数签名不破坏**：`validate_readonly_sql` / `enforce_limit` / `prepare_turn` 对外签名不变，只换实现（CLI / 评测 / 测试零改动或最小改动）。
2. **拒绝原因必须中文可读、能引导模型自我修正**（F2 硬性需求）：新校验层的每条拒绝路径沿用"拒绝执行：<原因>。<修正引导>"句式。
3. **评测可比性优先**：W6 消融要在 W5 代码上复现 W3 基线数字，凡是影响检索/注入/行为的改动都必须可关、可解释、可回退。
4. **演示规模下的克制**：不引入新服务、不引入数据库新表（能加列不加表）、能用进程内状态就不用持久化组件——2C2G 与单 worker 是硬约束。
5. **不确定的 API 不编造**：§8 列出编码前验证清单；本设计阶段已实测的结论标注"实测"，其余标注"待验证"。

## 1. sqlglot AST 白名单（替换正则黑名单）

### 1.1 选型确认与实测依据

选型：**sqlglot 30.x，`sqlglot.parse(sql, dialect="mysql")`**。

| 关注点 | 实测结论（2026-10-11，sqlglot 30.22.0，临时 venv） |
| --- | --- |
| 安装 | 纯 Python、零运行时依赖；清华源安装正常。requirements 增加 `sqlglot>=30.20,<31`（区间锁定，版本升级行为漂移由 pytest 用例锁，见 §6 风险 5） |
| 解析入口 | `parse()` 返回语句列表；`parse_one()` 单条便利封装。**多语句不会被 parse_one 抛错**，而是包成 `exp.Block`；`parse("SELECT 1; SELECT 2")` 返回长度 2 的列表——**多语句检测直接用 `parse()` 的列表长度** |
| 空语句 | `""` / `"   "` / `";"` / `"-- 注释"` 均解析为 `[None]`（长度 1 但首元素为 None）——空检查=首元素 is None |
| 语句类型 | `SELECT`/`WITH...SELECT` 根节点都是 `exp.Select`；UNION/EXCEPT/INTERSECT 根节点分别是 `exp.Union`/`exp.Except`/`exp.Intersect`；INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/SET @x/TRUNCATE 分别是 `exp.Insert`/`exp.Update`/`exp.Delete`/`exp.Drop`/`exp.Create`/`exp.Alter`/`exp.Set`/`exp.TruncateTable`；**CALL/GRANT/REPLACE 等 sqlglot 不认识的语法回退为 `exp.Command`（根白名单一票否决）** |
| 字符串字面量误杀 | `WHERE status = 'update'` 中 'update' 是 `exp.Literal`，树中无 `exp.Update` 节点——**W1 已知误杀实测确认消除** |
| LIMIT | `root.args.get("limit")` 只反映**最外层**查询：`SELECT * FROM (SELECT ... LIMIT 5) t` 的根无 limit；`SELECT * FROM orders LIMIT 10` 的根有；注释里的 LIMIT 不算；`exp.Union` 根同样有 limit 参数——**子查询漏判实测确认消除** |
| 锁读 | `FOR UPDATE`/`FOR SHARE`/`LOCK IN SHARE MODE` → 树内 `exp.Lock` 节点（根仍是 Select，必须树扫描） |
| INTO | `SELECT COUNT(*) INTO @c FROM t` → 树内 `exp.Into` 节点；`INTO OUTFILE/DUMPFILE` 在 mysql 方言下**直接 ParseError**（天然拒绝） |
| 函数 | `LOAD_FILE(...)`/`SLEEP(...)` 解析为 `exp.Anonymous`，`.name` 保留源码大小写（比对须 `.upper()`）；`GROUP_CONCAT` 是 `exp.GroupConcat` |
| 语法错误 | 抛 `sqlglot.errors.ParseError`，报错为英文技术体（如 `Required keyword: 'expression' missing for <class ...Mul>`）——**必须包装中文，原文拼接供模型参考** |
| 注释/分号 | 尾随单个分号、`/* */` 与 `-- ` 注释均正常解析；优化器 hint `/*+ MAX_EXECUTION_TIME(5000) */` 可解析（不误杀） |
| 中文字面量/反引号 | `WHERE city = '杭州'`、`` SELECT `order` FROM `orders` `` 正常解析 |
| 性能（开发机） | 典型评测 SQL：median 0.22ms / p95 0.32ms / max 0.70ms（服务器 2C 预计 2-3 倍，仍 <2ms；T1 验收时回填） |
| 金标兼容 | **45 条 SQL（34 条金标：30 单轮 gold_sql + 4 多轮 final_gold_sql；11 条 QA 语料 SQL）全部解析为 `exp.Select`，零失败** |

> ⚠️ sqlglot 解析不认识的语句时会向自己的 logger 发 "contains unsupported syntax. Falling back to parsing as a 'Command'." 提示（实测出现在控制台，warnings 模块捕获不到——走 logging）。处置：`logging.getLogger("sqlglot").setLevel(logging.ERROR)`（一行，T1 落地；具体 logger 名以 §8-⑯ 验证为准）。

### 1.2 决策：正则黑名单退役（不留双轨校验），保留一个版本周期的逃生门

**决策**：`validate_readonly_sql` / `enforce_limit` 的内部实现整体替换为 AST 版；正则黑名单、首关键字检查、正则多语句检查全部退出主链路。**不**采用"正则做预检快路径、AST 做精校验"的双轨方案。同时保留旧实现一个 W5 周期作为环境变量逃生门（见下）。

理由（被否备选：正则预检 + AST 复检）：

1. **预检快路径会把已知误杀原样带回新链路**。`WHERE note = 'please update this'` 会被正则预检直接拒绝，永远走不到 AST——升级的核心目的（消除误杀）就落空了。
2. **性能上不存在"快路径"需求**。正则 ~0.01ms vs sqlglot ~0.22ms，都在 7.4s 的端到端 P95（W3 实测，其中 SQL 执行占小头、LLM 往返占大头）面前是噪声。为省 0.2ms 引入两套拒绝语义（同一条 SQL 可能因预检/复检给出不同理由）是负收益。
3. **ParseError 不需要正则兜底**。sqlglot 解析不了的 SQL，MySQL 也执行不了——不存在"解析失败但合法"的可执行查询，无需回退到文本匹配。
4. **逃生门**（对"彻底删除"备选的修正）：新校验上线后若线上出现设计未预料的误杀，`TEXT2SQL_SQLGUARD=legacy` 可切回正则实现恢复服务（旧函数保留、标注 deprecated，W6 删除）。成本是一个 env 分支 + 旧函数存量一个版本周期；收益是线上事故的分钟级恢复能力。默认值 `ast`。

与现有防线的关系：**mode=ro 只读账号与会话只读不动**（架构红线：权限在 DBMS 内核层，代码任何 bug 绕不过；新校验只是把"第三层"从文本匹配升级为语义理解，防线层级数不变，仍是三层 + §2 超时成为第四层）。

### 1.3 AST 校验规则集（`agent/tools/sql_guard.py`）

新模块 `agent/tools/sql_guard.py`，对外暴露与旧函数同签名的 `validate_readonly_sql(sql) -> tuple[bool, str]` 与 `enforce_limit(sql, default_limit=20) -> str`。校验按序执行，命中即返回：

| # | 规则 | 实现要点 | 拒绝文案（中文可读 + 自我修正引导） |
| --- | --- | --- | --- |
| R1 | 唯一语句 | `stmts = sqlglot.parse(sql, dialect="mysql")`；`len(stmts) != 1 or stmts[0] is None` → 拒绝（None=空/纯注释，len>1=多语句） | 空：沿用现状文案"拒绝执行：SQL 为空或只包含注释。请提供一条 SELECT 查询语句。"；多语句：沿用"拒绝执行：一次只能执行一条 SQL 语句（检测到语句中间的分号）。请去掉多余的语句，一次只执行一条查询。" |
| R2 | 根节点白名单 | `isinstance(stmts[0], (exp.Select, exp.Union, exp.Except, exp.Intersect))`，否则拒绝。**一条规则兜住全部写操作**：Insert/Update/Delete/Drop/Create/Alter/Set/TruncateTable 直接不匹配；CALL/GRANT/REPLACE 等未知语句回退为 `exp.Command` 也不匹配；多语句的 `exp.Block` 在 R1 已拦 | "拒绝执行：只允许 SELECT 查询语句（含 CTE/UNION），不允许 <语句类型>。本工具对数据库只有只读权限，请改写为只读查询后重试。"（<语句类型> 从节点类名映射为 INSERT/UPDATE/DELETE 等人话，未知类型显示节点名） |
| R3 | 锁读拦截 | 树扫描 `stmts[0].find(exp.Lock)` 非空 → 拒绝（FOR UPDATE / FOR SHARE / LOCK IN SHARE MODE） | "拒绝执行：检测到锁读语法（FOR UPDATE / LOCK IN SHARE MODE）。本工具只做数据分析查询，不需要也不允许加锁，请去掉锁子句后重试。" |
| R4 | INTO 拦截 | 树扫描 `stmts[0].find(exp.Into)` 非空 → 拒绝（`SELECT ... INTO @var`；INTO OUTFILE/DUMPFILE 在 R2 之前已被 ParseError 拦下，见 §1.5） | "拒绝执行：检测到 INTO 子句（SELECT ... INTO 可向服务器写文件或导出变量）。请去掉 INTO 子句后重试。" |
| R5 | 禁用函数 | 树扫描所有 `exp.Func`，`f.name.upper() ∈ {"LOAD_FILE", "SLEEP", "BENCHMARK", "GET_LOCK", "RELEASE_LOCK"}` → 拒绝（决策理由见 §1.7） | "拒绝执行：检测到禁用函数 <函数名>。数据分析场景不需要文件读取（LOAD_FILE）或延时/锁函数（SLEEP/BENCHMARK/GET_LOCK），请去掉后重试。" |
| R6 | LIMIT 判定 | `stmts[0].args.get("limit")` 为空 → 外层无 LIMIT（供 `enforce_limit` 使用，见 §1.6） | 非拒绝路径，不产出文案 |

设计取舍说明：

- **不重新生成 SQL 执行**。AST 只用于校验与判定，真正执行的是**原文**（仅摘尾分号）。理由：sqlglot 往返重建（`ast.sql(dialect="mysql")`）虽保真度高，但会丢注释、规整字面量格式——"模型写的"与"执行的"出现文本差异会让 F2 自我修正与审计对照变困难；且重建引入了不必要的方言转换风险。**校验用 AST、执行用原文**是本设计的固定原则。
- **不做深度/复杂度限制**（如 CTE 层数、JOIN 数上限）。分析场景合法查询的复杂度上界不可预知（QA-009 复购率已是两层嵌套）；复杂度问题的实际后果是慢查询，由 §2 执行超时兜底，比在语法层武断设限更合理。
- **R2 的白名单集**刻意不含 `exp.Command`：Command 是 sqlglot 的"不认识"兜底，语义上等同于未知语句，宁可拒绝（只读账号也会拒它）也不能放行未知形态。

### 1.5 错误语义（F2 自我修正保持）

ParseError 的包装规则：`"拒绝执行：SQL 无法解析（语法错误）。请对照 MySQL 方言检查拼写与子句顺序（日期函数用 DATE_FORMAT/DATE_SUB，不能用 SQLite 的 strftime）。解析器报错：<ParseError 原文截 300 字符>"`。

- 原文保留的原因：与 `_humanize_db_error` 的既有惯例一致——模型靠报错原文里的位置信息（`Line 1, Col: N`）定位改错；
- **INTO OUTFILE 的落地形态**：实测它在 mysql 方言下是 ParseError 而非可识别节点，用户看到的将是"语法错误"而非"写文件"——文案引导里已包含方言提示，模型重试时通常会去掉非法子句；R4 覆盖的 `INTO @var` 给出专门的 INTO 文案。这是可接受的精度损失（两种路径都拒绝成功，只是拒绝理由的针对性不同）。

### 1.6 enforce_limit 的 AST 版

```python
def _prepare(sql: str, default_limit: int = 20) -> tuple[str, bool]:
    # 1) AST 判定：R1-R5 全过之后，root.args.get("limit") 为空 → 需要追加
    # 2) 追加目标 = 原文摘尾分号 + rstrip；若摘完后结尾是行注释（"-- ..." 无换行收尾的极端情况），
    #    用 _strip_comments() 清掉该副本的注释再追加（_strip_comments 保留，仅服务于追加副本；
    #    had_limit 的判定永远来自 AST，与注释无关）
    # 3) had_explicit_limit = root.args.get("limit") 非空（供"恰好 20 行可能被截断"提示沿用）
```

- UNION 根追加语义正确性：MySQL 中 `SELECT ... UNION SELECT ... LIMIT 20` 的 LIMIT 作用于整个联合结果——与 AST 判定（Union 根的 limit 参数）口径一致（实测 Union 根的 limit 参数随语句存在与否正确变化）。
- **行为变化即修复项**（写进 T1 验收与 experiment-log）：子查询 LIMIT 场景从"漏追加"变为"追加"；`/* LIMIT 5 */` 注释场景同修复。

### 1.7 函数白名单 vs 黑名单：决策为小黑名单，GROUP_CONCAT 放行

**决策**：R5 用**黑名单**（5 个函数），不做全函数白名单；`GROUP_CONCAT` 允许。

| 备选 | 结论 | 理由 |
| --- | --- | --- |
| 全函数白名单（只允许聚合/日期/字符串等白名单内函数） | **否** | 分析场景的合法函数面太宽（窗口函数、条件聚合、JSON 函数都可能被问到）；白名单误杀率不可控，直接违反"拒绝规则不能误杀现有合法查询模式"的兼容红线。且模型输出被 DeepSeek 对齐为常规分析 SQL，出现 `LOAD_FILE` 之类本就是异常输出，黑名单足以覆盖 |
| 黑名单含 `GROUP_CONCAT`（慢函数担忧） | **否** | ① 它是合法且常见的分析函数（"列出每个城市的商品名"这类问题天然用它），禁掉属于功能阉割；② 慢的根源是大分组下的字符串拼接，其代价被 §2 执行超时兜住，比语法层禁用更对症；③ MySQL 的 `group_concat_max_len`（默认 1024）天然限制了结果膨胀，内存风险有限；④ 当前 34 条金标与 11 条 QA 语料虽未用它，但它是模型面对"拼串"类问题的合理解法，禁用会把这类问题逼向不可解 |
| 黑名单清单 | `LOAD_FILE`（读服务器文件）、`SLEEP`、`BENCHMARK`（延时 DoS）、`GET_LOCK`、`RELEASE_LOCK`（命名锁，可制造跨会话挂起） | 五个都是"数据分析零用处 + 明确攻击面"的函数；`text2sql_ro` 无 FILE 权限本身就能拦 LOAD_FILE，AST 层拒绝是纵深防御 + 给出比 MySQL 1045 更可读的错误 |

## 2. SQL 执行超时

### 2.1 方案选型

**决策：MySQL 原生 `SET SESSION max_execution_time`（主防线）+ PyMySQL `read_timeout`（客户端兜底），两者都挂在连接层，业务代码零改动。**

| 备选 | 结论 | 分析 |
| --- | --- | --- |
| A. `SET SESSION max_execution_time=<ms>`（MySQL 8 原生，仅作用于 SELECT） | **采用（主）** | ① 服务器端终止——真正杀掉查询、释放 DB 资源，而非客户端单方面放弃；② 挂在 `sql_tools._attach_session_read_only` 的同一个 connect 事件里，与"会话只读"一行相邻，池化连接一次性设置、复用零成本；③ 我们的语句被 R2 白名单限定为纯 SELECT，"仅 SELECT 生效"的限制恰好不构成覆盖缺口 |
| B. Python 侧线程超时（`threading.Timer` / `concurrent.futures` 超时取消） | **否** | Python 无法安全取消正在阻塞 socket read 的 pymysql cursor——线程级"超时"只能放弃等待，查询在 MySQL 端继续跑（资源照样耗尽），且被弃线程与连接池的回收时序会产生悬挂连接。要真正终止必须另开连接发 `KILL QUERY <id>`，为演示项目引入"查询 ID 登记 + 第二连接"的复杂度，不值 |
| C. 每条 SQL 注入优化器 hint `/*+ MAX_EXECUTION_TIME(n) */` | **否（记录备查）** | 精度到语句级，但要改写 SQL 文本（与 §1.6"执行用原文"原则冲突），且 hint 容易被模型模仿产生嵌套混乱；会话级设置已覆盖同一能力 |
| D. SQLAlchemy 方言层 `execution_options` 超时 | 并入 A（等价实现的另一写法） | 本质还是落到驱动/服务端机制；A 的 connect 事件写法与会话只读对称，更贴现状 |

**覆盖面矩阵**（三道客户端/服务端机制各管一段）：

| 阶段 | `max_execution_time`(服务端) | `read_timeout`(驱动) | `connect_timeout=5`(已有) |
| --- | --- | --- | --- |
| 连接建立 | 不适用 | 不适用 | 覆盖 |
| SELECT 执行 | **覆盖（主防线）** | 兜底 | |
| 结果集传输 | 不覆盖（执行完才传） | 覆盖 | |
| 非 SELECT 语句 | 不适用 | 兜底 | （AST 白名单已禁，防御纵深） |
| 网络/服务器假死 | 不适用 | 覆盖 | |

`read_timeout` 的定位说明：它是 socket 级读超时，触发后 pymysql 抛错但**服务端查询仍在跑**——所以它只兜 `max_execution_time` 覆盖不到的边角（结果传输卡死、服务器假死），主防线必须是 A。两者取值的留痕：`read_timeout = MYSQL_MAX_EXECUTION_MS/1000 + 5`（服务端先超时 5 秒余量，让 3024 可读文案优先于驱动层超时出现）。

### 2.2 超时值与理由

**推荐：`max_execution_time = 10000`（10 秒），`read_timeout = 15`（秒）。** 可经 env `MYSQL_MAX_EXECUTION_MS` 调整（§9-3 待用户拍板）。

理由：

1. **下界由"最大合法查询"钉住**：W3 实测金标中最重的复购率类查询（两层嵌套扫 15 万行 order_items）在开发机毫秒级完成；服务器 2C 共享（同机还有 JVM 384M + 宝塔 nginx + MySQL）按 10 倍劣化估计也在 1s 内。10s ≈ 合法查询上界的 10 倍，误杀风险极低。
2. **上界由体验与资源钉住**：单次对话最多 1-3 次工具调用，10s 超时意味着最坏情况用户在 ~40s 内拿到"超时 + 缩小范围"的可读答复，而不是挂在无限查询上；2G 内存机器上跑飞的查询会拖垮同机的 Java 与宝塔，服务端主动终止是保护整个 demo 的开关。
3. W3 的 P95 7.4s 是**整轮问答**（含 LLM 往返）的延迟，不是单条 SQL 的执行时间——用它定 SQL 超时是口径错误，故不取 8s 这类"贴着 P95"的值。

### 2.3 错误可读化（模型能自我修正）

`_humanize_db_error` 新增两条映射：

| 错误形态 | 识别 | 文案 |
| --- | --- | --- |
| 服务端超时 | pymysql errno **3024**（`Query execution was interrupted, maximum statement execution time exceeded`） | "SQL 执行超时（超过 10 秒被数据库终止）。请缩小时间范围（如把全年改查最近 30 天）、减少聚合粒度或增加过滤条件后重试。" |
| 驱动层读超时 | `OperationalError` 且无服务端 errno、message 含 `timed out`（形态待 §8-⑩ 验证） | "查询等待超时，请缩小时间范围或增加过滤条件后重试。"（不承诺服务端已终止——语义留给服务端防线） |

超时发生时与其它 SQL 错误同路径：可读文案返回给模型 → 模型改写 SQL 重试或如实告知用户——F2 自我修正闭环对超时同样成立。

## 3. HITL：SQL 执行前人工确认

### 3.1 需求与总体链路

需求原文（P1）："默认自动执行，可开启'SQL 执行前人工确认'"（用户级设置）；教学文档 7.2 HumanInTheLoopMiddleware 的实战用例。

链路：前端设置项（默认关）→ 对话流中 Agent 生成 SQL 后**暂停** → 前端展示 SQL + 批准/拒绝 → 批准后继续执行并给最终回答。关闭开关时链路与 W4 完全一致。

### 3.2 架构决策：暂停点 A vs B

**决策：方案 A——暂停点在 Python 工具层（借助 LangGraph 中断机制），Java 只做透传与落库，不做语义拦截。**

| | 方案 A：Python 工具/编排层暂停（推荐） | 方案 B：Java 代理层拦截 tool 事件 |
| --- | --- | --- |
| 暂停语义 | **真暂停**：LangGraph 在工具执行前中断，checkpoint 停在"模型已产出 tool_call、工具未执行"，批准后原地续跑 | 假暂停：Java 旁路解析（ChatProxyService.handleData）确实能看到 `tool` 事件并抓到 sql，但 SSE 下行是单向只读流——Java 没有任何协议手段让 Python 的 agent "停下来等审批"；扣下事件时 Python 端工具已经执行完、模型已经在继续生成 |
| 要做到"真暂停"Java 需要什么 | 不需要额外东西 | 必须 Java 主动断开上游连接"叫停" agent——那不是暂停而是掐死整轮，状态作废重来；或者在 Java 侧重放请求——意味着 Java 要持有 SQL、还原 agent 上下文、重新驱动模型，等于在 Java 复刻半个编排器 |
| 状态归属 | 审批的本质是"暂停一次工具执行"；工具执行、LangGraph 消息状态（checkpointer）、LLM 客户端全部在 Python，**暂停状态与被暂停的对象同层**，无跨语言一致性难题 | pending SQL 在 Java、消息状态在 Python、解密 key 在 Java、checkpointer 在 Python——四个状态三处存放，重启/断连/并发的边界每种都要跨语言对账 |
| 对现有契约的侵入 | 新增 1 个下行事件（`pending_approval`）+ 1 个上行端点；Java 的旁路解析对未知事件本来就"仅透传"（handleData 的 default 分支） | 看似不动 Python，实际要把"是否需要审批"的判定（用户设置）、"审批结果"的传递（回调/重放）、"历史如何落库"全部塞进代理层，侵入面更大 |
| 面试叙事 | "为什么 HITL 放工具层？"——工具执行与中断状态同层，LangGraph 的 interrupt/checkpoint 机制原生支持；Java 保持"工程化网关"定位（鉴权/限流/落库），不碰语义 | 无法自圆：网关拦截了事件却拦不住执行，讲不清"暂停"二字 |

### 3.3 实现载体：HumanInTheLoopMiddleware（实测）

不手写"进程内暂停 + token 重放"的土制协议，直接用需求点名、教学文档 7.2 对应的官方实现（项目 venv 版本已确认存在）：

```python
from langchain.agents.middleware import HumanInTheLoopMiddleware

middleware = [HumanInTheLoopMiddleware(
    interrupt_on={"execute_readonly_sql": {"allowed_decisions": ["approve", "reject"]}},
    # description 用 callable 定制中文描述（含 SQL），供前端卡片与审计；
    # 不给 edit/respond 决策——编辑 SQL 超出 W5 范围（写进 §9-1 备选）
)]
agent = create_agent(model=..., tools=[...], system_prompt=..., checkpointer=...,
                     middleware=middleware)   # hitl=False 时不传 middleware 参数（与 api_key 同款条件传参）
```

实测确认的行为（2026-10-11，langchain 1.4.3 + langgraph 1.2.x）：

1. `list_tables` 不在 interrupt_on 里 → 自动放行（只有 SQL 执行需要审批，查表目录无需打扰用户）；
2. 中断发生时 `stream_mode="messages"` 的流**自然结束**（messages 流不携带 interrupt 事件），此后用 `agent.get_state(config).tasks[0].interrupts[0].value` 取到载荷 `{"action_requests": [{"name", "args", "description"}], "review_configs": [...]}`——**待审批 SQL 在 `action_requests[0].args["sql"]`**；
3. 恢复必须用 `agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config)`——resume 是**带 `decisions` 键的 dict**（裸 list 会 `TypeError`）；
4. `{"type": "reject", "message": "<中文引导>"}` 会让工具收到一条 ToolMessage：`User rejected the tool call for `execute_readonly_sql` with reason: <中文引导>`，模型据此继续用中文回应；
5. approve/reject 续跑完成后 `state.next` 为空，同 thread 可正常继续多轮（checkpointer 状态干净）。

### 3.4 状态机与事件契约（新增部分）

```
[提问] POST /api/chat
  → Python: prepare_turn(hitl=True) → stream(messages)
      → delta / tool 事件照常（AIMessage 完整收尾时 tool 事件带 sql，Java 旁路照常捕获）
      → 到达工具执行点：LangGraph 中断，stream 自然结束
  → Python: get_state 检测到 interrupt → approval.register(thread_key, sql, question,
      context_block=format_context_block(pt.injected_chunks)) 得 approvalId
      → SSE 发 pending_approval {approvalId, sql} → 流结束（不发 done）
  → Java: 旁路捕获 pending_approval → query_history 落 status=4（待审批，含 question/generated_sql/token/latency）
      → 注入 pending_saved {historyId}（前端存下，供批准后原地更新该行）
      → 并发闸照常在流结束时释放（审批等待期间不占用并发额度）

[批准] POST /api/chat/approval {threadId, approvalId, decision:"approve"}
  → Python: approval.pop(approvalId)（原子取出+TTL 校验）
      → 用 entry.context_block 重建 agent（§3.5 恢复轮口径，不重跑检索）
      → agent.invoke(Command(resume={"decisions":[{"type":"approve"}]}), config)
      → SSE: meta → delta…（模型拿到执行结果后作答）→ done{tokens,latencyMs,generatedSql} → saved
  → Java: 按请求携带的 historyId **原地 UPDATE** 原 status=4 行：status=1、answer_text、
      latency_ms/token_in/token_out 取两段之和（读原行累加后写回）

[拒绝] 同上，decision:"reject"
  → resume {"type":"reject","message":"用户拒绝了这条 SQL。请不要执行或改写它，直接询问用户希望如何调整（时间范围、指标口径、过滤条件）。"}
      → 工具收到拒绝 ToolMessage → 模型用中文询问用户意图 → delta → done → saved
  → Java: UPDATE 原行 status=3（用户中断/拒绝语义）、error_code="approval_rejected"

[过期/丢弃] TTL 5 分钟：前端卡片置灰"已过期"；线程收到新提问时若仍有未决审批 → 409 pending_approval_exists
  （引导先处理卡片，§3.10 降级路径）
```

事件契约增量（向后兼容）：

| 事件/端点 | 方向 | data | 消费方 |
| --- | --- | --- | --- |
| `pending_approval` | Py→Java→FE | `{approvalId, sql}` | 前端渲染审批卡；旧前端 applyChatEvent 的 default 分支忽略（不崩，但看不到卡片——见 §6 风险 6） |
| `pending_saved` | Java→FE | `{historyId}` | 前端把 historyId 存进审批卡 |
| `POST /api/chat/approval`（Java）/ `POST /agent/chat/approval`（Py） | FE→Java→Py | `{threadId, approvalId, decision}` | 走 JWT 鉴权（与 /api/chat 同款），Java 读 key 解密、带 `X-User-Id`/`X-User-LLM-Key`/`X-Internal-Token`/`X-User-HITL` 转发 |

新错误码（Java ErrorCode + errors.js 文案映射）：`approval_not_found`（已消费/服务重启）、`approval_expired`（TTL）、`pending_approval_exists`（该 thread 已有未决审批时又发新问题，409）。

### 3.5 状态管理：pending 注册表（内存 dict + TTL）

新模块 `agent/core/approval.py`（进程内单例，单 worker 前提与 Chroma/fastembed 一致）：

```python
_pending: dict[str, dict] = {}        # approvalId -> {thread_key, sql, question, context_block, created_at}
_by_thread: dict[str, str] = {}       # thread_key -> approvalId（反查"该会话是否已有待审批"）
_lock = threading.Lock()
PENDING_TTL_SECONDS = 300

def register(thread_key, sql, question, context_block) -> approvalId
    # 同 thread 已有待审批 → 抛 PendingApprovalExists；
    # context_block 是停车那一轮 format_context_block 的产物——resume 重建 agent 时原样复用，
    # 保证系统提示词与停车轮**逐字节一致**（见下方"恢复轮的组装口径"）
def pop(approvalId) -> entry | raise(NotFound/Expired)   # 原子取出（锁内 pop，双击/并发第二次必 NotFound）
def find_by_thread(thread_key) -> entry | None            # 新提问到达时的未决检查
```

- **TTL=5 分钟**：与"用户看完一条 SQL 做个决定"的节奏匹配；过期项在 `pop` 与 `find_by_thread` 时惰性清理（不引入定时线程）。
- **进程内 dict 的边界（文档化为已知限制）**：单 worker 已由部署锁定；Python 服务重启丢 pending → 前端批准时收到 `approval_not_found` → 提示"服务已重启，请重新提问"。与 InMemorySaver 的会话记忆同属"重启即失"的既有等级，不为演示项目引入 Redis。
- **恢复轮的组装口径**（不做检索重跑）：approve/reject 轮**不走 prepare_turn**——resume 不是新问题，重新检索反而有"previous_human_message 拼接出 `q\nq` 重复 query"的口径瑕疵与语料漂移风险。做法：`pop` 取回 entry 后直接 `build_agent(build_system_prompt(entry.context_block), api_key=..., middleware=...)` + `invoke(Command(resume=...), config={"configurable": {"thread_id": thread_key}})`。LangGraph 的 model 节点在 resume 后会用**当前 agent 实例的 system prompt** 重新喂给模型，复用停车轮的 context_block 即保证提示词连续（§8-⑦ 验证覆盖）。这不违背 W4"prepare_turn 唯一组装点"原则——该原则约束的是**问题轮**的三方同构，resume 轮是新增的第四种调用形态，与它共享 build_agent/build_system_prompt 构件。
- **拒绝语义**（写进 §3.4 状态机）：模型收到的拒绝消息是引导性中文（"请询问用户意图"），实测确认模型随后以中文回应——用户拒绝不会让 agent 报错或自作主张换一条 SQL 再执行（那条路径同样要审批）。

### 3.8 用户级开关的存储与传递

- 存储：`user` 表加列 `hitl_enabled TINYINT NOT NULL DEFAULT 0`。不加新表的理由：单开关、用户维度、无扩展诉求——加表是过度设计。
- 迁移方式：`schema-app.sql` 是幂等 `CREATE IF NOT EXISTS`，对已存在的表不会补列；MySQL 8.0 不支持 `ADD COLUMN IF NOT EXISTS`。采用**部署脚本守护迁移**：`deploy/w5_migrate_user_settings.sh` 在服务器上先查 `information_schema.columns`，无该列才执行 `ALTER TABLE app.user ADD COLUMN hitl_enabled TINYINT NOT NULL DEFAULT 0`（幂等可重复执行；§8-⑮ 验证）。`schema-app.sql` 同步加列定义（新环境直建）。
- 传递：Java 在 `open()` 与审批代理里读用户行 → 注入 `X-User-HITL` 头 → `prepare_turn(question, thread_key, api_key=..., hitl=...)` → `build_agent` 条件注入 middleware。**开关是请求域的**（每请求由头决定），Python 侧无全局态——多用户各自开关互不影响，BYOK 每请求 key 的同款模式。

### 3.9 与评测 / CLI 的关系（默认关的论证）

- `prepare_turn(..., hitl=False)` 默认值 + `build_agent` 不传 middleware 参数 → **CLI（agent/main.py）与评测（run_eval.py）的调用代码一行不改**，组装行为逐字节等价（W4 §6.2 同构验收结论保持成立）。
- 开关只经 HTTP 头到达 Python——CLI 与评测根本不发这个头，即使想开也没有表达审批交互的通道（CLI 无 SSE/无前端），设计上不给 CLI 提供 HITL 入口。
- 评测红线：`run_eval` 全程 hitl=False → 不可能出现中断挂起 → Replayer/判定逻辑零感知。
- W4 §6.2 的三道同构验收（固定题 injected_chunks 全等 + prompt 快照 + eval smoke）在 T2 收尾时**必须复跑**——确认 HITL 改造没有波及组装路径。

### 3.10 降级路径与边界情况

| 情况 | 处理 |
| --- | --- |
| 审批等待期间同一 thread 又来新问题 | Python 端 `approval.find_by_thread` 命中未决项 → 新请求 409 `pending_approval_exists`（前端提示先处理审批卡）。**不**选"自动拒绝旧审批再答新问题"：resume reject 会触发一次模型回应（额外 token + 混入上一问的答非所问文本），交互更混乱；409 语义最清晰 |
| TTL 过期且用户不再理会 | 停车的 interrupt 留在 checkpointer（内存，量级 = 一条消息链，演示规模可忽略）；该 thread 下一次提问命中 409 → 用户唯一的解法是处理卡片（已置灰）→ 点拒绝走 §3.4 reject 路径解锁。若希望彻底自动化：新提问遇到**已过期**未决项时，Python 先 `resume reject("用户未响应审批，已取消该 SQL")` 让模型简单收尾、随后处理新问题（同一条 SSE 流内先后两段）——**作为可选增强记录，W5 默认不做**（多一次 LLM 调用换一个罕见场景的自动化，不划算） |
| 审批流中途客户端断连 | 与现有断连守卫同路径：Java 按 status=3 落库 + UPDATE；Python 的 resume 请求不会发生，interrupt 停车原状（下轮提问按未决项处理） |
| 双击"批准" | `approval.pop` 锁内原子取出，第二次请求 `approval_not_found`（幂等保护） |
| 模型一轮要执行多条 SQL | middleware 的 after_model 一次收集全部待审批 tool_call（实测支持多 action_requests）；前端卡片按条展示逐条批准/拒绝（decisions 列表与 action_requests 等长对齐——T2 联调覆盖两条 SQL 的 case） |

### 4.1 数据流总览

```
用户点赞（feedback.rating=1，W4 已有 upsert）
  → Java 内部接口 GET /api/internal/feedback/samples（新增，X-Internal-Token）
  → agent/rag/absorb_feedback.py --dry-run 预览 / --apply 追加
```

### 4.2 样本供给：Java 内部接口（决策：不走只读账号直查 app 库）

**决策：Java 提供只读内部接口，Python 脚本经 HTTP 拉取。**

| 备选 | 结论 | 理由 |
| --- | --- | --- |
| A. `GET /api/internal/feedback/samples`（新，Java 侧 JOIN） | **采用** | ① `text2sql_ro` 只有 `SELECT ON mart.*`——**读不到 app 库**，这是 W2 以来的权限设计（最小权限），为自举脚本开 app 读权限是倒退；② 复用 InternalController 的成熟鉴权模式（X-Internal-Token 常量时间比较 + limit 封顶），Python 侧用 httpx（openai SDK 依赖树里已有，零新增依赖）；③ 数据主权留 Java：JOIN 条件、字段裁剪、脱敏都在 Java 侧一次做完 |
| B. 脚本持管理员凭据直连 app 库 | 否 | admin 凭据用途扩散（现只给建库脚本）；绕过 Java 意味着质量门槛里的 JOIN/过滤要在 Python 重写一遍，且"Agent 调 Java REST"的架构叙事被自己拆台 |
| C. 手工导出 CSV 喂脚本 | 否（记录为 --from-json 备选） | 一次性手工动作违背"闭环"；保留在脚本的 TODO 不实现 |

接口设计（T3 落地）：`GET /api/internal/feedback/samples?limit=200`，鉴权 X-Internal-Token（**不需要 X-User-Id**——全库样本聚合，管理脚本用途，与现有按用户检索接口的差异写进 Javadoc）；Java 侧 SQL：`feedback JOIN query_history` 过滤 `rating=1 AND status=1 AND generated_sql IS NOT NULL`，按 id 倒序 limit 封顶 200；返回 `{historyId, question, generatedSql, comment, createdAt}` 列表。

### 4.3 质量门槛（六道，防污染语料）

按序过滤，任一不过即剔除（dry-run 输出每条的落选原因）：

| # | 门槛 | 理由 |
| --- | --- | --- |
| G1 | `rating == 1` | 点赞是唯一质量信号；点踩样本将来做负例分析，不进正例库 |
| G2 | `status == 1`（执行成功） | 执行失败的 SQL 没有示范价值 |
| G3 | `generated_sql` 非空 | 没查库的纯聊天回答不构成 SQL 示例 |
| G4 | `validate_readonly_sql` 通过（sql_guard AST） | 保证入库示例与自己家的安全规则自洽——若某条被点赞的 SQL 恰好踩在新规则上（如含 `SLEEP`），把它写进 few-shot 等于教模型写出会被拒绝的 SQL |
| G5 | 问题文本 1~100 字、SQL ≤ 2000 字 | 语料风格与现有 11 条一致；超长问题多为多问复合，作为单示例示范性差 |
| G6 | 双层去重通过（§4.4） | 防膨胀与检索偏置 |

`comment` 的使用：作为补充信息拼进新条目的「说明」行（§4.6），**不作为门槛**（W4 前端没有评论输入框，绝大多数样本 comment 为空）。

### 4.4 去重方案（决策：文本精确归一 + 语义阈值 0.92 双层）

| 备选 | 结论 | 分析 |
| --- | --- | --- |
| 仅问题文本精确匹配 | 不够 | "上个月的GMV"与"上个月 GMV 是多少？"文本不同实为同题，会重复收录 |
| 仅语义相似度 | 不够作为唯一闸 | 阈值以下仍有变体漏网；且新问题与**问题**字段的相似度要和与整片的相似度区分口径，实现复杂化 |
| **双层：文本归一精确匹配（对现有 11 条 + 本批次内）+ 语义阈值（ Chroma 余弦 top1）** | **采用** | 文本层零成本挡住"完全相同"；语义层挡住改写变体。语义层直接复用现有设施：BgeEmbedder 嵌入新问题 → `collection.query(vector, n_results=3, where={"doc_type": "qa_pair"})`——collection 的 HNSW 是 **cosine space**（chroma_store.py 显式配置），Chroma 返回 distance = 1 − cosine 相似度 |

- **阈值：cosine 相似度 ≥ 0.92 视为重复**（即 distance ≤ 0.08）。取保守值：bge-small-zh-v1.5 对完全同文 = 1.0、同题改写通常 ≥ 0.85、不同题通常 < 0.8——0.92 位于"改写"与"不同题"之间的空档偏保守侧，**宁可漏收不可错收**（语料里 11 条示例是精挑的口径示范，混入近似重复示例会稀释检索多样性并带偏 W6 的 Recall 数字）。阈值在 T3 用真实数据标定后回填 experiment-log，允许调整（§9-4）。
- 判重对象：新问题 vs 现有 QA 条目的「问」字段（不是整片文本——金标 SQL 与说明会拉低区分度）；本批次内先两两判重再统一追加。
- dry-run 输出每条的 top1 相似度与命中条目编号（如 `与 QA-003 相似度 0.87 → 保留`），人工过目再 apply。

### 4.5 触发方式：手动 + dry-run 预览（决策）

**决策：手动脚本 `python -m agent.rag.absorb_feedback --dry-run / --apply`，不做点赞即自动追加。**

理由（被否备选：点赞即自动入库）：

1. **点赞 ≠ 正确**。用户可能为"看起来像答案"的错误结果点赞（如口径算错但数字合理），自动入库会把错误示范写进每次检索都可能命中的语料——污染是**静默且全局**的；dry-run 强制人过目一遍样本与相似度，是这条链路里唯一的人工质量闸。
2. **频率低，自动化的收益为零**。演示项目点赞量级是个位数/周；为它做"点赞即触发"的自动链路（还要处理并发重建、失败重试）是纯负收益的复杂度。
3. **语料版本必须可控**。W6 消融要求"除被测变量外一切固定"——自动追加会让语料在评测中途漂移，消融数字失去可比性。手动模式天然形成语料版本点（git commit），experiment-log 可记录"本次评测基于 qa 11+2 片"。
4. 回滚 = git revert 一个 md 文件 + 重建索引，操作简单且可展示（面试叙事：语料治理有版本化纪律）。

### 4.6 QA-012+ 编号与条目格式

- 编号：脚本用 `### QA-(\d+)` 正则解析现有文件最大号，从 **QA-012** 起顺延（补零到三位）。
- 条目格式与现有 11 条逐字段对齐（切分器 `build_index._parse_qa_pairs` 无需任何改动）：

````markdown
### QA-012
**问**：<用户问题原文（规范化空白后）>
**金标 SQL**：
```sql
<generated_sql 原文>
```
**说明**：（自举收录 2026-10-XX，来源：用户点赞问答；用户补充：<comment>）
````

- 「说明」行固定前缀标注自举来源（与人工写的口径说明区分开，方便未来审计语料成色）；有 comment 时附上。
- 追加位置：文件尾。防御逻辑：若文件尾部出现非 QA 前缀的 `## ` 章节标题（对应 `build_index._split_entries` 的终止边界规则——防止把尾注粘进最后一个语料片），插入到该标题之前；当前文件无尾块，此分支为保险。
- metadata/expected_chunks 兼容：新片 metadata 四字段由现有解析器自动生成（`doc_type=qa_pair`、`source_id=qa_012`）；评测集 expected_chunks 只引用 qa_001~011，**新增语料不触碰金标**（§4.7）。

### 4.7 与评测的兼容（金标不动 + 自举命中统计预埋）

1. **静态评测集不受影响**：`eval_v1.jsonl` 的 expected_chunks 引用的 chunk id（`qa_pair:qa_001~011`）在语料追加后依然存在（删除重建只增不减），`load_dataset` 的 valid_chunk_ids 复检照常通过；W3 的分层口径（EV-001~011 = 有同款示例层）是静态定义，不随语料增长漂移。
2. **Recall@8 的诚实声明**：语料从 28 片变 28+k 片后，top-8 注入的竞争加剧，复测 Recall 数字会变化——这不是退化而是检索环境的改变。对策：报告「运行配置」节**新增一行语料片数**（`语料：schema 6 / glossary 11 / qa_pair 11+k`），让任何两次报告可对齐语料版本（additive 改动，旧行为不变）。
3. **自举命中统计（统计口径预埋）**：detail JSON 的 `injected_chunks` 已含完整 chunk id——`run_eval` 报告新增「自举语料命中」条目：`命中自举语料的题：<case id 列表>（注入 qa_012+ 片：qa_012、qa_015…）`，口径 = `injected_chunks ∩ {qa_pair:qa_NNN | NNN ≥ 012}`；**仅当非空才输出该行**，保证 W3 时代报告逐字节可复现。
4. **W6 顺序红线**（写进 experiment-log 与 W6 计划提醒）：W6 消融基线必须在冻结语料快照上跑完，之后才吸收新样本；每次 absorb 后的语料版本（qa 片数 + git commit）记入 experiment-log。

新脚本 `deploy/absorb_corpus.sh`（开发机执行，手动触发；复用 deploy.sh 的 ssh 通道与"服务器零构建"原则的边界说明见下）：


- **为什么在服务器重建而不是开发机重建后拷贝 chroma_db**（被否备选）：① chroma 持久化目录含 sqlite 文件与 HNSW 二进制，跨机拷贝有一致性风险（须停服务拷贝）；② W4 已把 fastembed 缓存固化到服务器（FASTEMBED_CACHE_DIR，教训实录"运行时向 HuggingFace 下载 → 国内网络挂死"已解决），重建是纯本地计算；③ "服务器零构建零拉取"原则针对的是 npm/mvn 级构建产物，2 分钟的 Python 重建脚本属于运维动作，且有 deploy.sh 已有的 ssh 先例。
- **重启必要性**（写进脚本注释防踩坑）：`recreate_collection()` 删除并重建 collection 后，**已运行进程**的 `get_collection()` 单例仍指向旧对象——不重启则该进程检索继续走旧索引（新旧并存到下次重启），这是 W2 坑清单 #3（get_or_create 不升级配置）的变体。
- 评测复测动作：重建后在开发机跑 `eval smoke`（`--limit 2`）确认链路，W6 前跑全量基线并记录语料版本。

## 5. smoke_* 测试账号清理（清理项）

### 5.1 背景与影响评估

- W4 网关冒烟（W4 设计 §6.3）在服务器上注册了冒烟专用账号（`smoke-<ts>` 式命名），每次部署冒烟都会新增；`query_history`/`feedback`/`api_key` 里留着对应测试数据。
- 影响评估：**均为测试数据，无真实用户受损风险**——demo 上线时间短，真实注册用户（如有）的用户名受注册正则 `[A-Za-z0-9_]{4,32}` 约束，**不含连字符**；但若冒烟脚本实际用了下划线命名（`smoke_<ts>`，W4 文档与脚本可能有出入，§8-⑭ 服务器实查确认），与真实用户存在理论撞名可能——因此脚本必须**先 SELECT 展示再 DELETE**，且模式锁定为 `^smoke[-_][0-9]+$`（时间戳后缀纯数字），`smoke_test` 这类手建账号不在自动删除范围（需人工确认后手动处理）。
- 执行时机：T4 部署完成、8 步网关冒烟验收通过**之后**执行一次（清理本身不影响冒烟脚本可重跑——下次冒烟会重新注册）。

### 5.2 删除脚本设计（`deploy/cleanup_smoke_users.sql`）

`app` 库四表**没有物理外键**（schema-app.sql 只建了普通索引），删除顺序按逻辑依赖：feedback → query_history → api_key → user：

```sql
-- 第一步：核对（dry-run，人工确认列表为空 surprises）
SELECT id, username, created_at FROM `user` WHERE username REGEXP '^smoke[-_][0-9]+$';
-- 第二步：按依赖顺序删除（每步回显影响行数）
DELETE f FROM feedback f
  JOIN query_history h ON h.id = f.history_id
  JOIN `user` u ON u.id = h.user_id
 WHERE u.username REGEXP '^smoke[-_][0-9]+$';
DELETE h FROM query_history h
  JOIN `user` u ON u.id = h.user_id
 WHERE u.username REGEXP '^smoke[-_][0-9]+$';
DELETE ak FROM api_key ak
  JOIN `user` u ON u.id = ak.user_id
 WHERE u.username REGEXP '^smoke[-_][0-9]+$';
DELETE FROM `user` WHERE username REGEXP '^smoke[-_][0-9]+$';
-- 第三步：复核（应返回 0）
SELECT COUNT(*) FROM `user` WHERE username REGEXP '^smoke[-_][0-9]+$';
```

- 附带产物：`api_key` 行删除即该冒烟账号的 BYOK 密文一并消失（无明文残留——密文本就是 AES-GCM 密文）；`query_history.generated_sql` 里的冒烟 SQL 一并清除，避免污染自举样本池（§4.2 的 samples 接口按 rating=1 过滤，冒烟点赞样本会命中——先清理后开自举是顺序要求，写进 T4 步骤）。
- 执行方式：服务器 `mysql -u<admin> -p app < cleanup_smoke_users.sql`；不并入 deploy.sh 自动执行（破坏性动作保持手动）。

## 6. 风险与应对

| # | 风险 | 影响 | 应对与回退 |
| --- | --- | --- | --- |
| 1 | **sqlglot 拒绝合法 MySQL 语法**（方言覆盖缺口：某些 MySQL 特有写法解析失败或解析成意外结构） | 合法查询被误杀，模型自我修正循环失败，demo 可用性受损 | 上线前 §1.8 红线验证（34 金标 + 11 QA SQL + 对抗清单）；ParseError 文案附原文，模型可按提示改写；**逃生门** `TEXT2SQL_SQLGUARD=legacy` 一键切回正则实现（旧函数保留一个版本周期）；W6 删除前再评估 |
| 2 | **HITL 停车状态滞留**（用户开了开关又不响应审批；进程重启丢 pending） | 该 thread 被未决 interrupt 卡住（新提问 409）；内存滞留 | TTL 5 分钟 + 前端过期置灰 + 409 提示引导处理卡片；重启丢 pending 与 InMemorySaver 同等级已知限制，文档化；量级演示规模可忽略；§3.10 的"自动 reject 解卡"作为可选增强 |

| 4 | **超时阈值误伤慢查询**（服务器 2C 比 2 倍于开发机的估计更慢；宝塔/同机负载尖峰） | 合法分析查询被 10s 砍掉 | 值走 env 可调（`MYSQL_MAX_EXECUTION_MS`）；3024 文案引导缩小范围（模型可改写重试，损失一次往返而非失败）；T4 部署后用最重金标实测执行时长回填 |

| 6 | **事件契约扩展对旧前端的兼容**（旧构建的页面收到 pending_approval 不认识） | 开了 HITL 的用户在旧前端看不到审批卡，对话"卡住" | 事件是 additive：applyChatEvent default 分支忽略未知事件（现状已验证不崩）；HITL 默认关 + 前端与后端同部署（静态 dist 一次性替换），实际暴露面趋近于零；写进 README 已知限制 |
| 7 | **feedback 样本接口滥用/越权** | 内部接口被探测，泄露用户问题与 SQL | X-Internal-Token 常量时间比较（复用现有模式，生产必配由 W4 设计 §5.5 清单核对）；limit 封顶 200；只读、不返回 user_id 明细；接口只在内网通道被 Python 调用（Python 绑定 127.0.0.1） |
