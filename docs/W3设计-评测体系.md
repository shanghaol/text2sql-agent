### 0.3 设计总原则（延续 W2）

1. **每个决策带理由和被否备选**——评测体系是简历上"怎么评估 Agent 效果"这道必考题的全部素材，设计阶段把"为什么"写死。
2. **评测的是系统，不是裸 LLM**：管线与线上 main.py 完全同构（同样的检索注入），否则测出来的数字不是"这个系统"的数字。实验二已经证明：同构与否直接改变答案（有无 few-shot 注入，"上个月"从 9 月变成 8 月）。
3. **W6 消融是 W3 的下游**：本次设计的明细 JSON、错答模式登记、`--top-n`/`--runs` 参数化，都是为 W6"各优化项贡献拆解"预埋的数据接口。W3 只跑两个格子（全系统 / 无 RAG），但矩阵格式按消融矩阵设计。
4. 不确定的库 API 不编造，统一进 §8 验证清单。

## 1. 评测集设计

### 1.1 五类分配：30 条怎么分

**分配：单表查询 6 / 多表 JOIN 7 / 聚合统计 7 / 时间窗口 5 / 口径陷阱 5。**

| 类型 | 条数 | 占比 | 分配理由 |
| --- | --- | --- | --- |
| 单表查询 | 6 | 20% | 基础能力底线。占比不能太低：单表题若都错，说明系统有系统性问题，数字要能暴露这个；也不能太高，否则基线数字虚高无区分度（单表题预期接近满分） |
| 多表 JOIN | 7 | 23% | 真实分析查询的大头，也是 W1 实验就观察到的易错点（JOIN 路径、去重、GROUP BY 键）。W2 保留冗余列（`order_amount`/`item_count`/`refunds.order_id`）正是为了让"单表可答"与"必须 JOIN"分层，评测集要覆盖这个梯度 |
| 聚合统计 | 7 | 23% | 考"分组工艺"（GROUP BY / HAVING / 占比 / CASE WHEN 拆口径 / 子查询比值），与口径陷阱的边界见下方判定规则 |
| 时间窗口 | 5 | 17% | 数据锚点（2026-09-30）是本项目特有设定，实验二已实证它是失败高发区——但时间题的重灾区其实被口径陷阱类分走了一部分（"上个月"既是时间题也是口径题），所以纯时间类不必占太多 |
| 口径陷阱题 | 5 | 17% | **项目灵魂与面试主素材**（需求 §8："口径陷阱题就是活例子"）。W2 的数据剧情（部分退款设计、GMV 双口径、客单价三分歧）专门为它而造，qa_verification.md 已备好 3 组可分辨的真库数字。但每条陷阱题的命题成本最高（金标 + 两种以上标准错答都要实测登记），5 条已够讲出完整故事，再多边际收益低 |

**类型判定规则**（命题与归类时逐条过，防止归类随意）：

- **单表查询**：金标 SQL 主表仅一张（允许 NOT EXISTS / 标量子查询做谓词），考 SQL 基本功与表理解。
- **多表 JOIN**：金标 SQL 含 ≥2 表 JOIN，考 JOIN 路径与去重。
- **聚合统计**：主要难点在聚合工艺（分组、占比、条件聚合、多步比值），且**不存在"能跑通但口径错误"的有诱惑力错答**。
- **时间窗口**：主要难点在时间条件本身（锚点换算、相对时间、粒度转换、左闭右开）。
- **口径陷阱**：存在一个"听起来直观、能跑通、但业务口径错误"的 SQL，其结果与金标**可分辨**。判定结果依赖"选哪张表 / 哪一列 / 哪个分母"。

### 1.2 评测集文件与 schema

**决策：JSONL**（`eval/dataset/eval_v1.jsonl`，一行一条 JSON 对象）。

被否的备选：
- **CSV**：`expected_chunks`（列表）、`standard_wrong`（嵌套对象）、多行 `gold_sql` 都要发明转义约定，脆弱；
- **Markdown 表格**：机器解析靠正则，30 条还能忍、W6 扩到 50 条是负债；
- **Python 常量文件**：评测集是"数据"不是"代码"，需求 §4 目录把数据划给 `data/`、脚本划给 `eval/`，JSONL 数据文件两头都站得住，且非 Python 工具也能读。

字段 schema（每行一个对象，全字段必填、无默认值——漏填在加载时报错而不是静默跳过）：

```json
{
  "id": "EV-029",
  "question": "2026 年 9 月的净销售额是多少？",
  "question_type": "glossary_trap",
  "gold_sql": "SELECT ROUND(...) AS net_sales FROM payments p WHERE ...",
  "ordered": false,
  "expected_chunks": ["schema:payments", "schema:refunds", "glossary:net_sales"],
  "standard_wrong": [
    {"trap_id": "no_refund_deduction", "description": "答成 GMV（未冲减退款）", "value": "16029955.34"},
    {"trap_id": "orders_amount_basis", "description": "用 orders.order_amount 口径冲减", "value": "19038651.57"}
  ],
  "notes": "口径 2：净销售额 = GMV − 退款，支付按 paid_at、退款按 refunded_at 各自圈期"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | str | `EV-001` 起三位序号，报告/明细/复跑都按它寻址 |
| `question` | str | 提问原文（进 Agent 的问题就是这个字符串，一字不改） |
| `question_type` | enum | `single_table / multi_join / aggregation / time_window / glossary_trap` |
| `gold_sql` | str | 金标 SQL，MySQL 8 方言，遵守 §2.3 口径（左闭右开、锚点 2026-09-30、退款必查 refunds 表） |
| `ordered` | bool | **人工判定**的结果集有序标志：true = 金标结果按顺序逐行比较；false = 多重集合比较。见 §2.4 |
| `expected_chunks` | list[str] | 预期检索片 id 列表，Recall@K 的判定基准。id 必须是 28 片语料里真实存在的 id（`schema:<表名>` / `glossary:<english_id>` / `qa_pair:qa_NNN`），T1 验收含逐条核对 |
| `standard_wrong` | list[object] | 标准错答登记（仅陷阱题非空，其余题为 `[]`）：错答描述 + 实测陷阱值，供错答模式分类（§4.3）。value 存字符串形式，比较时走与结果集相同的规范化 |
| `notes` | str | 考察点 + 判定依据说明，给人看的，管线不消费 |

`ordered` 用人工标注而不是从 SQL 自动检测 `ORDER BY` 的理由：子查询里的 ORDER BY、`GROUP BY` 后的隐式顺序等边界会让自动检测变成一个 SQL 解析小工程；30 条命题时作者本来就清楚"这道题的答案依赖顺序吗"，人工标注零成本且绝对正确。W6 扩题时同样人工标。

### 1.3 W2 的 11 条 QA 如何纳入——"自举污染"还是"合理设定"？

**决策：11 条原样纳入（问法、金标 SQL 与 `qa_pairs.md` 完全一致，不改写），并在报告里显式声明评测口径。**

问题本质：这 11 条既是 few-shot 语料（`qa_pair:qa_001..011` 片）又是评测题——模型检索时可能看到"自己的考题和答案"。这是否污染？

**论证：不是污染，是合理的系统级设定，理由四条：**

1. **评测对象定义决定答案。** 评测的是"RAG 检索层 + Agent"这个完整系统，few-shot 示例库是系统的组成部分（F3 三路语料之一，"few-shot 自举"是需求明文功能）。高频问题命中示例库，是生产系统的**常态运行方式**，不是作弊——评测就该测系统在真实配置下的表现。
2. **实验二提供了反面实证。** `RETRIEVER_TOP_N=0`（无任何注入）时模型把"上个月"答成 8 月（16,164,482.43），而正确答案 16,029,955.34 就在它自己查出的工具结果里——缺的从来不是计算能力，是**消歧锚定**。这说明 few-shot 片对答案的贡献是真实的功能贡献，把它算进系统成绩是诚实的。
3. **被否的备选"改写 11 条措辞以避嫌"**：改写后题目与示例不再字面相同，但语义上仍是"同一道题在语料里有答案"，污染疑虑只是被化妆没有消除；反而丢失了"原题原答可交叉核对"的质量保障（qa_verification.md 的核对记录绑定的是原 SQL），并引入"改写是否改变了难度"的新变量。收益为负。
4. **真正要防的污染在新增 19 条侧。** 新题若与 11 条示例高度相似（同表同指标同窗口），会退化成"考语料里有没有同款"，测量不到泛化。所以 §1.4 的新题命题纪律是：**时间窗、维度、指标与 11 条示例错开**，让一部分题"检索不到同款示例"，靠 schema 片 + 口径片泛化作答。

**两个诚实性配套（写进报告模板，§3.3）：**

- 报告必须标注："W3 基线 = **含 few-shot 自举的系统级数字**"，不得表述为"模型的 NL2SQL 能力"。W6 消融计划里有"去掉 qa_pair 路检索"一格，届时两组数字对比才是"few-shot 自举贡献"的量化。
- 30 条天然形成两个层：11 条"有同款示例的题" vs 19 条"靠泛化的题"，报告**分层报告准确率**——这个对比本身就是面试素材（"few-shot 命中与未命中题的准确率差 X 个点"），且为 W6 消融提供先验。

#### B. 新扩 19 条（EV-012~030）

##### 单表查询（4 条，EV-012~015）

**EV-012** ｜ 2025 年上半年注册的用户有多少？

```sql
SELECT COUNT(*) AS user_count
FROM users
WHERE registered_at >= '2025-01-01' AND registered_at < '2025-07-01';
```
- expected_chunks：`["schema:users"]` ｜ ordered：false ｜ 预期量级 ≈6,000（注册窗口 2024-01→2025-08 共 20 个月，均匀覆盖）
- 考察点：单表时间窗 COUNT 基本功。陷阱预置检查：注册窗口 2025-08-31 截止——若模型想当然拿 `registered_at` 与数据期锚点换算（如查"最近 6 个月注册"）会查到 0 行，本题刻意选一个"注册时间轴与订单时间轴不同"的窗口，测模型是否真的看 schema 片而不是套模板。

**EV-013** ｜ 图书类目下原价最高的 3 个商品是哪些？

```sql
SELECT name, price
FROM products
WHERE category = '图书'
ORDER BY price DESC
LIMIT 3;
```
- expected_chunks：`["schema:products"]` ｜ ordered：true ｜ 预期 3 行，图书价格带 19-99 元
- 考察点：单表 TOP-N 排序（有序判定）。T1 核对时须检查第 3/4 名价格是否相等（平局会让有序判定抖动，相等则换 LIMIT 值或改题，§4.1）。

**EV-014** ｜ 2026 年 5 月各状态的订单分别有多少笔？

```sql
SELECT status, COUNT(*) AS order_count
FROM orders
WHERE created_at >= '2026-05-01' AND created_at < '2026-06-01'
GROUP BY status;
```
- expected_chunks：`["schema:orders"]` ｜ ordered：false ｜ 预期 6 行（6 个状态在月订单 ~7,000 下应全部非零）

**EV-021** ｜ 各退款原因的数量与占比是多少？

**EV-025** ｜ 2025 年 11 月的订单量环比 2025 年 10 月增长了百分之多少？

```sql

      WHERE created_at >= '2025-10-01' AND created_at < '2025-11-01') t1,
```

### 1.5 `expected_chunks` 的定义与标法

**定义：该题若要答对，缺失后大概率答错的知识片**——即"答对的必要知识集"，不是"预测检索会命中什么"。

标法规则：

| 题型 | 必标 | 说明 |
| --- | --- | --- |
| 全部题 | 金标 SQL 涉及的每张表的 schema 片 | 表结构是写 SQL 的硬前提 |
| 口径陷阱题 | 对应 glossary 片 | 口径选择的知识来源 |
| 锚点/相对时间消歧题（EV-003） | 对应 qa_pair 片 | 实验二实证：缺 qa_003 会答错月份——有"缺失即答错"的因果证据才标 qa_pair，不是每题都标 |
| 聚合工艺/纯时间题 | 一般不标 qa_pair | few-shot 有帮助但无"缺失即错"证据，标了会稀释 Recall 的因果含义 |

这样标的好处：Recall 与执行准确率之间能建立**归因链条**——明细 JSON 里"expected 缺失且判 fail"的题，就是"检索失灵导致答错"的直接证据，W6 消融（改 top_n、去 BM25 路）前后这组题的迁移才是有解释力的数字。把 qa_pair 普遍标进去会把这个信号淹没（qa 片短、关键词强，几乎题题命中）。

## 1.7 增补：多轮评测（用户拍板 W3 纳入）

**定位**：单轮 30 条保持不变（基线主数字的口径干净）；多轮单独 4 条（MT-01~04），**独立文件、独立报告节**——多轮和单轮是两种难度，混在一起会污染"30 条基线"这个数字的可比性（W6 扩题时同样分开）。

**文件与 schema**：`eval/dataset/eval_v1_multiturn.jsonl`，每行一个多轮 case：

```json
{
  "id": "MT-01",
  "turns": ["上个月 GMV 多少？", "那环比呢"],
  "final_gold_sql": "SELECT DATE_FORMAT(paid_at,'%Y-%m') AS month, ROUND(SUM(amount),2) AS gmv FROM payments WHERE paid_at >= '2026-08-01' AND paid_at < '2026-10-01' GROUP BY month ORDER BY month",
  "ordered": true,
  "expected_chunks": ["glossary:yoy_mom", "qa_pair:qa_003"],
  "standard_wrong": [{"trap_id": "month_shift_aug", "description": "把'上个月'答成 8 月（锚点字面理解）", "value": "16164482.43"}],
  "notes": "复刻 W2 验收两连问；判定只看最后一轮（q1 是消歧上下文的提供者，不单独判分）"
}
```

- **判定只看最后一轮**：中间轮是上下文提供者，不单独判分（降低金标成本；中间轮是否调了工具作为明细记录供分析）。金标 = 最后一轮的 SQL。
- **thread 同 case 共享**：一个 case 的多轮共用一个 thread_id（每 run 每-case 唯一）——这正是 §3.6"多轮检索 query 拼接"的真实测量场景，W2 遗留的已知妥协这回有了量化数据。
- **4 条命题**（金标全部复用已验证数字，控制新增风险）：
  | id | turns | 最后一轮金标 | 考察点 |
  |---|---|---|---|
  | MT-01 | 上个月 GMV 多少？→ 那环比呢 | 2026-08/09 两月 GMV 有序 2 行（16,164,482.43 / 16,029,955.34，已验证） | 复刻 W2 验收；expected_chunks 含 qa_003（实验二实证的消歧依赖） |
  | MT-02 | 2026 年 6 月的客单价是多少？→ 那 7 月呢 | 7 月客单价（口径 3 同款；精确值 T1 实测回填） | W1"那 10 月呢"模式的题化：月份切换 + 口径保持 |
  | MT-03 | 9 月的退款率是多少（金额口径）？→ 换成订单口径呢 | 0.0886（已验证） | **同指标换口径**——考"对话中听清口径切换"，与 EV-030 静态版互补 |
  | MT-04 | 各支付方式的订单占比是多少？→ 银联的占比是多少 | 银联占比单值（EV-011 已核对 ≈9.96%，精确值 T1 回填） | 从聚合结果中取子集；分母保持全量（题面歧义已在命题时消除） |

**运行矩阵增补**：主行（top_n=8）跑 MT 4 题 ×3 runs；对照行不跑 MT（定性结论已够，省成本）。报告单列"多轮准确率"节。成本增补：24 次调用 ≈ +20%，总预算仍 <¥15 量级。

## 2.7 增补：多轮评测的管线差异

- runner 增 `--multiturn` 数据加载分支：case 有 `turns` 列表时逐轮 invoke（同 thread_id、同 run），每轮照常走检索注入 + build_system_prompt + build_agent；**每轮的检索 query = previous_human_message + 当前轮输入**（与线上多轮完全同构——这正是被测对象）
- 每轮记录明细（injected_chunks / tool_calls / latency / tokens 累计），判定器只吃最后一轮的 SQL
- expected_chunks 的 Recall 判定取**最后一轮**的注入（q1 的注入是"为 q2 铺垫"的副产物，计入会稀释指标）
- 最终轮无可用 SQL → error（同 §2.2 三级规则）

### 2.2 SQL 提取：从 tool_calls 拿 sql

**决策：遍历 invoke 结果 `result["messages"]` 中每条 AIMessage 的 `tool_calls`，取 `name == "execute_readonly_sql"` 的调用的 `args["sql"]`。**

```python
def extract_execute_calls(messages: list) -> list[dict]:
    """按发生顺序收集 execute_readonly_sql 调用：[{seq, sql}, ...]"""
    calls = []
    for msg in messages:
        for tc in (getattr(msg, "tool_calls", None) or []):
            if tc.get("name") == "execute_readonly_sql":
                calls.append({"seq": len(calls) + 1, "sql": tc["args"]["sql"]})
    return calls
```

**论证：**

1. **工具调用参数是结构化的。** inspect_chain.py 已实证（W1 实验 1/2 的消息链记录）：`AIMessage.tool_calls` 是 LangChain 已解析好的 `[{name, args}]` 列表，`args["sql"]` 就是模型发起调用时的完整 SQL 字符串——function calling 协议保证它是合法 JSON 字段，不是要从散文里捞的东西。
2. **被否备选一：从 `AIMessage.content` 正则抽 ```` ```sql ```` 代码块。** 模型可能不按格式输出、正文混着解释文字、一个回答里出现多段 SQL（修正前的和修正后的）、甚至把 SQL 写在表格里——脆弱且要为每种失败模式打补丁。W1 实验 4 还观察到现在会输出"文字说明 + 工具调用"混合消息，正文里的 SQL 和实际执行的 SQL 可能不同——**只有 tool_calls 里的才是真正执行的那条**。
3. **被否备选二：在 `execute_readonly_sql` 工具里加记录钩子（全局变量/日志拦截）。** 为评测侵入生产工具代码，评测与生产耦合；且"读消息历史"方式拿到的信息是钩子的超集（钩子只有 SQL，消息链还有调用顺序与对应结果）。
4. **判定不解析 ToolMessage 文本，评测器重放 SQL**（§2.4）——所以提取侧只需要 SQL 本身，不需要从"共 N 行 | 列名 | 值"的格式化文本里反推结果。

**取哪次调用的规则**（模型常多次调用：探索、试错、修正）——按优先级：

1. **最后一条** `execute_readonly_sql` 调用的 SQL，评测器重放成功 → 用它判定（`sql_source="last"`）。绝大多数题一次调用收尾（实验三：三问均一发命中）。
2. 最后一条重放**报错** → 回看是否存在更早的成功调用，有则取**最后一条成功的**判定（`sql_source="fallback_to_earlier"`），并在明细里保留"以失败调用收尾"标记——这个行为本身是模型自我修正失败的信号，值得统计而非掩盖。
3. 全部失败，或一条都没调（拒答/纯文字回答）→ 判 `error`，`error_msg="no_usable_sql"`。不解析 content 语义去救——拒答本来就该算失败，模型"用自然语言报了个数"更像幻觉而非可验收行为。

**不做的事：** 不限制调用次数、不惩罚多调用（多调用是 Agent 的合法行为，且每题调用次数作为附加指标输出——"自我修正次数"是面试素材）。

### 2.3 与线上 main.py 的同构对照表

runner 每题的执行序列，逐点对照 main.py：

| 步骤 | main.py（线上） | run_eval.py（评测） | 同构性说明 |
| --- | --- | --- | --- |
| 检索 query | `previous_human_message + user_input` 拼接；首轮无历史时 = 当前输入 | 每题新 thread_id，恒为首轮 → query = question 本身 | **同构**：评测全部单轮，恰好等于线上首轮行为；不做多轮题（多轮评测是 W6+ 议题，见 §7） |
| 检索调用 | `retriever.search(query, top_n=RETRIEVER_TOP_N)`，doc_types 缺省全类型 | `get_retriever().search(question, top_n=args.top_n)` | 同一函数同一参数路径；top_n=8 时与线上逐字节一致（检索全链路确定性，§6 风险 6） |
| prompt 组装 | `build_agent(build_system_prompt(format_context_block(chunks)))` | 同一行 | 原样 import，零差异 |
| 会话隔离 | 每次启动一个 thread_id，会话内多轮共享 | `thread_id = f"eval-{case.id}-r{run_idx}"`，每题每 run 唯一 | 隔离粒度比线上更细（每题一会话）——**这是有意的**：跨题污染（前一题的口径、SQL、结果残留影响后一题）会让评测数字不可复现。每题独立 thread_id 后，checkpointer 单例共享但状态互不可见 |
| 调用方式 | `agent.stream(..., stream_mode="messages")` | `agent.invoke(...)` | stream/invoke 的消息状态语义相同（同一 LangGraph 执行），差异只在增量回调；评测不需要打字机，invoke 拿全量消息更简单 |
| 计时 | 无 | `time.perf_counter()` 从 **search 之前**起算到 invoke 返回 | 检索是用户体感的一部分（main.py 里它发生在回答前），计时必须包含 |
| 兜底链 | 检索空 → `_NO_CONTEXT_SECTION` 兜底文案 | 同（build_system_prompt 内部处理） | top_n=0 对照行走的就是线上真实降级路径 |

**为什么必须同构**（再强调一次，这是本设计的第一原则）：实验二重跑已经证明，去掉检索注入，同一道题的答案从 9 月变成 8 月。评测管线若与线上有一处不同构（比如评测时多注入一份表清单、或检索时加了 doc_types 过滤），测出来的就不是"线上这个系统"的准确率，所有 W6 优化对比都失去基准意义。

### 2.4 结果集规范化与判定规则（judge.py）

**核心决策：金标与模型 SQL 都由评测器重放执行，比较两个结果集**——评测集里只存金标 SQL，不存死值金标。

```python
def replay(sql: str) -> list[tuple]: ...
    # 用 sql_tools.get_engine()（同一只读账号 + 会话只读）conn.execute(text(sql)).fetchall()
    # 不套 enforce_limit（判定看逻辑结果集）；行数保护上限 5000，超出截断并标记 oversized
```

被否的备选"评测集里存期望结果值"：DECIMAL 格式化、行序、列数等细节手写必错；金标 SQL 本身就是需求 F5 要求的交付物（"问题-金标SQL"对）；且两边同规则重放让"DECIMAL 该格式化成什么样"这个问题自动消失——不存在第三方的期望格式。死值只出现在陷阱题 `standard_wrong`（错答模式分类用，那里比较的是单值，手写可控）。

**规范化规则**（金标行与模型行走同一函数 `normalize_rows`）：

| 值类型 | 规范化 |
| --- | --- |
| DECIMAL / int / float | 统一 `Decimal(str(v))`（str() 消除 float 尾数噪声；Decimal 接受科学计数法字符串） |
| datetime / date / time | `str(v)`（datetime → `'2026-03-15 14:22:01'`，date → `'2026-03-15'`；`DATE_FORMAT` 返回的本来就是 str） |
| bytes | `decode('utf-8')` |
| None / str | 原样 |

**判定规则**（每题从上到下短路）：

1. 无可用 SQL 或重放报错 → `error`
2. 列数不一致 → `fail`（模型 SELECT 的投影数不对是实质错误）
3. 行数不一致 → `fail`
4. `ordered=true`（金标含顶层 ORDER BY，人工标注）：逐行按位比较；任一位置不同 → `fail`
5. `ordered=false`：两边各行 tuple 化后分别 `sorted()` 再按位比较（等价于多重集合比较，正确处理重复行）→ 不同则 `fail`
6. 全部一致 → `pass`

**数值容差**（吸收 ROUND 位数差异，模型写 `ROUND(x,2)` 金标写 `ROUND(x,4)` 不该判死）：

```
两值相等 ⇔ |a−b| ≤ max(0.005, 1e-3 × max(|a|, |b|))
```

容差论证：相对容差 1e-3 能吸收 4 位小数 ROUND 的差异（最大相对误差 ≈ 6.5e-4），而所有陷阱值与金标的差异都在 20% 量级（26.5% / 39% / 46% / 27%）、月份偏移差 100%——容差比陷阱间距小三个数量级，**不会把陷阱错答放行为 pass**。绝对下限 0.005 吸收纯小数位的直接差。列名（AS 别名）不比较：模型别名千变万化（gmv/total/gmv_amount），比列名会把大量正确答案误杀。

### 2.5 Recall@K 判定

每题记录：`injected_chunks`（本次实际注入的 id 列表，top_n=8）、`expected_chunks`、交集。

| 指标 | 计算 | 回答的问题 |
| --- | --- | --- |
| 逐片 Recall（整体） | `Σ|∩| / Σ|expected|` 全 30 题汇总 | 检索层整体召回质量（简历可写的 Recall@8） |
| 题级命中率（hit rate） | expected **全部**命中的题数 ÷ 30 | "该拿的资料一次拿齐"的比例 |
| 分 doc_type Recall | 按 schema / glossary / qa_pair 分组统计 | 哪一路语料召回弱（口径片没召回 → 陷阱题错的归因） |
| 分题型 Recall | 按五类分组 | 陷阱题的 glossary 召回是重点观察项 |

Recall 只在主行（top_n=8）计算；对照行（top_n=0）注入恒空，Recall=0 是设定使然，报告里只列执行准确率对比。

### 2.6 延迟与 token 采集

**延迟**：每题 wall-clock（§2.3 的计时口径：search 前起、invoke 返回止，含全部工具往返——这是用户体感口径）。汇总输出 mean / median / P95 / max，另给分题型 P95。

P95 计算口径（30 个样本）在 `statistics.quantiles(data, n=20, method='inclusive')` 与手写排序取位之间二选一，编码时定下并在报告里注明口径（小样本分位数定义不唯一，声明即可）——列入 §8 验证清单。报告必须声明：延迟绝对值受评测时网络波动影响，横向（题型间）与纵向（W6 前后对比）才是稳定可比的。

**token**：采集每个 thread 内**全部 AIMessage 的 usage** 后求和。要采的是"计费口径"——Agent 多轮工具调用意味着多次 LLM 请求、每轮重发全部历史，累加才是这次查询的真实成本。

采集位置**标注为编码前验证项（§8 第 1 条），禁止编造字段名**：候选一 `AIMessage.usage_metadata`（langchain-core 的标准化 token 字段，含 input/output/total）；候选二 `AIMessage.response_metadata` 里的 OpenAI 风格 usage。编码第一步用 inspect_chain.py 加一行打印实测哪个存在、多轮工具调用时是否每条 AIMessage 各带一份、缓存命中是否单列——实测后把采集函数固化，文档注释里记下实测结论。若两者都不可用，回退方案是在 runner 里包一层自定义回调从响应原始返回里取（实现成本高一档，先用不上的概率大）。

成本换算：报告输出**原始 token 数**（单题均值 / 总量 / 分题型），不把 DeepSeek 牌价写死进报告生成逻辑（牌价会变，报告要能跨季度复读）；人民币估算作为报告旁注，换算系数手填。

## 3. 运行矩阵与"基线"的定义

### 3.1 矩阵设计：两行

| 行 | tag | 配置 | runs | 目的 |
| --- | --- | --- | --- | --- |
| 主行（基线） | `baseline_full` | 全系统，top_n=8 | 3 | 简历数字"基线 __%"的来源 |
| 对照行 | `no_rag_control` | top_n=0（无 RAG 注入） | 1 | 简历故事"RAG 把执行准确率从 __% 提到 __%"的第一手证据 |

**要不要加"无 RAG 对照行"——建议：加。** 论证：

1. **成本可忽略。** 量级估算：每题 1-4 次工具调用 → 2-5 轮 LLM 请求；每轮 input = 系统提示词（静态骨架 + 注入 8 片 ≈ 1-2k token）+ 累积历史与工具结果，全题 input 累计约 4-10k token、output 约 0.5-1k。对照行 30 题 ≈ 15-30 万 input token 量级；主行 3 runs + 对照 1 runs 合计 120 次完整运行 ≈ 80-150 万 input token。按 DeepSeek 当前牌价的百万 token 几元人民币量级（**不写死单价**，编码时以官方价目页为准填旁注），全部跑完预估 **< ¥15**，远在需求 §10"全程 ¥50 以内"预算内。冒烟后按 `--limit 2` 实测单题 token 外推，超预期即砍（§6 风险 4）。
2. **失败样本本身就是简历素材。** 实验二已实测 top_n=0 的失败形态（"上个月"答成 8 月、正确数字就在它自己查出的结果里）。30 题系统级对照把这条轶事变成可引用数字——"RAG 检索的不只是知识，还有意图消歧的锚定"这个论点需要量化支撑，这正是需求 §8 RAG 整体题（"为什么用 RAG"）的最硬答案。
3. **它是 W6 消融矩阵的第一个格子。** W6 要做"各优化项贡献拆解"，top_n=0 是消融的原点，W3 先跑好，W6 只需扩格子。

被否的备选"再加第三行（如 top_n=4）"：那是 W6 消融的事（top_n ∈ {5,8,12} 已在 W2 设计 §3.4 预注册），W3 的任务是基线，矩阵每多一行都是成本与排错面，克制。

### 3.2 每题跑 1 次还是 3 次

**建议：主行 3 次，对照行 1 次。** 论证：

1. **主行数字要写进简历，得经得起"跑了几次"的追问。** temperature=0 仍有服务端非确定性（实验 1 已记录：逐字输出不稳定、结论复现；需求上下文亦确认），单次跑出的 87% 和三次均值 83%±3 是两个可信度等级。3 次还免费送一个面试素材："temperature=0 为什么还不确定"的一手量化数据（三次 run 间 overall 差 + 结果翻转题清单）。
2. **对照行 1 次就够。** 对照行的预期是"明显更差"（实验二预测：锚点消歧类题塌方），其作用是定性对比 + 错答模式采样，不需要精确定量；省下的一倍成本让给主行的稳定性。
3. **成本与时长**：120 次完整运行 × 单次 30-90 秒 ≈ 顺序跑 1-2 小时（可 `--runs` 拆批跑）。学习者时间比 API 费用更稀缺，1-2 小时挂机可接受；若不可接受，降级路径是主行先 `--runs 1` 拿数字，简历定稿（W8）前补 `--runs 3`——管线参数化让这件事零成本。
4. **判定抖动的处理**：3 次内结果不一致的题标 `flaky`，报告单独列出并人工复盘明细 JSON（看三次的 SQL 差在哪）——flaky 题不机械取众数，人工判断是"判定边界问题"还是"模型真实不稳定"，这个复盘过程本身进 experiment-log。

### 3.3 报告输出

每次运行产出两个文件（`eval/reports/`，进 git——报告是简历证据链）：

**Markdown 汇总报告**（`report_<tag>_<timestamp>.md`），固定结构：

```
# W3 基线评测报告：<tag>（<时间戳>）
## 运行配置：数据集版本 / top_n / runs / 模型与温度 / 快照锚点 2026-09-30 / 检索参数（top_k_each=20, RRF k=60）
## 四指标汇总
   执行准确率：overall + 分题型表 + 分层表（11 条有同款示例 vs 19 条泛化题，§1.3）
   Recall@8：整体 + 分 doc_type + 分题型
   延迟：mean / median / P95 / max（含分题型 P95）
   token 成本：单题均值 / 总量（分 input/output）
## 对照行对比表（baseline_full vs no_rag_control：准确率 + 分题型差值）
## 错答模式统计（trap:<id> / valid_alt_gloss / other / error 的计数与典型样本）
## 多轮评测节（4 条 MT 题的准确率 / 最后一轮 Recall / query 拼接行为观察）
## flaky 题记录（3 次结果不一致的题 + 三次结果对照）

```

## 4. 金标 SQL 的质量保障

### 4.1 真库核对（复用 W2 T2 流程）

`eval/verify_gold.py`：逐条加载 eval_v1.jsonl → 在 mart 库执行 `gold_sql` → 断言**执行通过且结果非空** → 打印每条行数 + 前 3 行预览 → 追加写核对记录 `docs/eval_gold_verification.md`（仿 qa_verification.md 格式：每条一行"✓ EV-0xx：执行通过；N 行；数值 sanity 说明"）。

核对附加检查（T1 验收项，命题风险的兜底）：

- **TOP-N 有序题（EV-002/010/013/015/019/021）检查边界平局**：金标 LIMIT N 的第 N 名与第 N+1 名排序键相等 → 该题 ordered 判定会随并列顺序抖动，必须改题（换 LIMIT 或换条件）；
- **EV-017/021 等依赖"实测分布符合命题预期"的题**：预期 8 类全覆盖 / 5 档严格降序——实测不符（如某类目 0 行）就改命题，不带病上线；
- **EV-009 的 quantity 版错答、EV-029 的 19,038,651.57**：T1 时真库执行，把实测值回填进 eval_v1.jsonl 的 standard_wrong（本文档留了占位标记）。

金标 SQL 遵守的口径与 W2 T2 同源：左闭右开、锚点 '2026-09-30'、退款必查 refunds 表、MySQL 方言。数据是 `--seed 42` 固定种子的静态快照（W2 §1.6/§1.8），核对一次终身有效——除非重导数据，重导后必须重跑 verify_gold（写进脚本头注释）。

### 4.2 陷阱题"标准错答"也要实测

每个 `standard_wrong` 条目的 value 不是拍脑袋写的：能从 qa_verification.md / experiment-log 直接引用的引用实测值；需要运算合成的（EV-029）T1 时真库执行错答 SQL 确认。理由：错答模式分类（§4.3）拿模型重放值与登记值做**数值比对**，登记值错一个位数就会把"错成陷阱"误分类成"错成别的"，整个 W6 消融的归因地基就歪了。

### 4.3 错答模式统计：为 W6 消融预埋的分析维度

判定 `fail` 时，judge 按序分类并写 `failure_mode`：

1. 模型重放结果与该题某条 `standard_wrong.value` 匹配（同 §2.4 规范化与容差）→ `trap:<trap_id>`（踩进已登记的陷阱）；
2. 与某条匹配但该条被标注为"合法他口径"（`valid_alt_gloss`，见下）→ `valid_alt_gloss`；
3. 都不匹配 → `other`（错出新花样，人工看明细归类，新错答模式值得回填登记——陷阱题的错答模式库会随评测越养越全）；
4. `error` 另计（no_usable_sql / replay_error / invoke_exception 三种子码）。

`valid_alt_gloss` 的意义：退款率双口径、GMV 与净销售额**都是合法指标**，模型算出另一个口径的数不代表能力差，代表没听题。把它与 `trap`（踩中真陷阱，如 5.65% 的 status 口径）分开统计，W6 分析才能回答"口径检索注入后，模型是'更会算'了还是'更会听题'了"——这两个改进来自不同的优化手段（前者靠 schema/示例，后者靠 glossary），混在一起会误判优化方向。

## 6. 风险与应对

| # | 风险 | 影响 | 应对与回退 |
| --- | --- | --- | --- |
| 1 | **多次工具调用导致 SQL 提取歧义**：最后一条调用可能是失败探索（列名错），真正答对的是倒数第二条；或模型不再调工具、用自然语言报数（幻觉风险） | 判定错题（把对的判 error，或漏掉"用旧结果作答"的行为） | §2.2 三级规则（最后成功 → 回退更早成功 → error）+ `sql_source` 字段记录走了哪级 + "以失败收尾"单独统计；明细保留完整调用序列，边界案例人工复盘；不解析 content 语义去救拒答（拒答=失败是诚实的口径） |
| 2 | **陷阱题判定争议**：双口径都合法（退款率 7.75%/8.86%、GMV vs 净销售额），模型答"另一个合法口径"算对还是错？ | 判定被质疑"冤枉模型"，数字公信力受损 | 三层预防：① 命题时把口径**写进题面**（EV-004"金额口径"、EV-030"订单口径"、EV-029"净销售额"——题面本身已消歧）；② 无歧义词的题（EV-003"GMV"）陷阱是"用错表/列"，错答结果可分辨且语义错误明确；③ "合法但答非所问"单独分类 `valid_alt_gloss`（§4.3），既不放水也不冤枉，报告单列这项计数 |
| 3 | **非确定性导致边界题抖动**：temperature=0 仍有服务端波动（实验 1 实证），个别题两次运行结果翻转 | 基线数字不可复现，被追问时尴尬 | 主行 3 次取均值 + 翻转题标 `flaky` 人工复盘（§3.2）；执行准确率（比较结果集而非文本）天然抗"措辞抖动"，只对"实质 SQL 不同"敏感——这是选执行准确率做头牌指标的固有收益，写进报告声明 |
| 4 | **token 成本超预算**：实测单题 token 远超估算（如模型陷入多次重试循环） | 费用超 ¥50 预算 | 流程闸门：T3 第一步先 `--limit 2 --runs 1` 冒烟实测单题 token，外推全量后再跑；超预期则砍对照行 / 降主行 runs=1；runner 遇单题异常不中断整场（题级 try/except，记 error 继续），避免"第 29 题失控拖死全场" |
| 5 | **金标边界平局**：TOP-N 题第 N/N+1 名排序键相等（DECIMAL 相等的概率低但非零），有序判定随并列顺序抖动 | 个别题判定不稳定 | verify_gold 的边界平局检查（§4.1）在 T1 就拦下，改题；数据是固定种子快照，核对一次终身有效 |
| 6 | **检索注入的非确定性**（已被论证排除，登记在案）：若检索不稳定，Recall 与准确率都会抖 | —— | 检索全链路确定性：BM25 词频固定 + bge embedding 确定性 + RRF 平局按 `(-score, id)` 稳定排序（W2 §3.4）+ HNSW 查询无随机性；实验三实测三问 top 集合稳定。同 query 必同注入，检索不是抖动源 |
| 7 | **明细行数超工具截断的题**：模型 SELECT 大宽表（如 order_items 全表）会被工具的 LIMIT 20 截断，模型可能基于截断结果"编"汇总 | 个别题 error/fail 属于工具行为而非模型能力 | 命题纪律已规避：30 条全部是聚合/排序题，无"全表明细"类题；若明细里出现此类 case（模型自作主张 SELECT *），归 `other` 人工复盘——它是"模型行为 × 工具约束"交互的真实样本，本身有分析价值 |
| 8 | **管线与线上行为漂移**：未来 main.py 改了检索注入逻辑（如 W5 加反馈闭环、W6 改 query 改写），评测管线没跟上 | 评测测的还是旧系统 | §2.3 同构对照表作为 T2 验收与每次改 main.py 后的复查清单；runner 顶部 docstring 写明"同构契约：main.py 每轮流程变更必须同步评审本文件"；W6 消融改线上逻辑时由审查方对照此表 |
