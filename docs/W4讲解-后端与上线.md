## 一、做了什么（系统全景）

上线形态：**https://sql.shanghl.club**（原生共存：宝塔 nginx + systemd 双服务 + 原生 MySQL 8）

```
浏览器（localStorage 只存掩码）
  │ ① HTTPS
  ▼
宝塔 nginx（80→443 跳转；/api 反代 8081，proxy_buffering off 保 SSE）
  ▼
Java :8081（text2sql-java.service，-Xmx384m）
  │ JWT 校验 → 限流 10/min → 并发闸 ≤4 → api_key 表 AES-GCM 解密
  │ ② 内网头三件：X-User-LLM-Key / X-User-Id / X-Internal-Token
  ▼
Python :8000（text2sql-python.service，MemoryMax 450M）
  │ 校验内部头 → prepare_turn（检索注入 → prompt → agent）→ 流式
  ▼                                   ▼
MySQL 8（mart 只读）              DeepSeek API（用户的 key）
```

四层交付：Java 后端（55 类）+ Python 服务化 + Vue3 前端（四页）+ 部署（systemd/nginx/certbot）。测试账本：Java 37 + Python 246 + 前端 30 = **313 项**，线上 8 步冒烟全过。

## 二、为什么这么做（六个决策的完整论证）

### 2.1 BYOK 的存储方案：为什么 AES-GCM 落库而不是 localStorage 透传？

需求 v1.3 要求"加密存储"，但技术上仍值得论证。两张方案的完整对比在设计 §1.3，核心逻辑：

- **暴露面位置**：透传方案把明文 key 的暴露面从"录入 1 次"变成"每轮请求"（每个请求头都带明文），且 XSS 可直接偷 localStorage；落库方案浏览器里只有掩码，服务端是密文+主密钥分离存储（拖库不泄漏）。
- **代价**：~150 行 Java + 主密钥管理。换来的是多设备 UX + 完整的密钥管理叙事。
- **密码学选型**：AES-**GCM** 而非 CBC——GCM 是认证加密，密文被篡改一个字节解密即抛 `AEADBadTagException`（防静默伪造），CBC 要自己再拼 HMAC。**IV 纪律**：GCM 同 key 同 IV 两次加密会泄漏明文异或——IV 必须 12 字节 `SecureRandom` 每次重新生成并与密文同存，这条注释写进了代码（面试密码学细节）。
- **主密钥**：环境变量注入、缺失即拒启（fail-fast——"缺主密钥的 BYOK 应用等于裸奔"）；`openssl rand -base64 32`（**必须恰好 32 字节**，部署实录：生成了 48 字节被 Java 拒启，见 2.6）。

**面试一句话**：安全选型 = 威胁模型 × 暴露面 × 实现成本三者的交点，不是"最高级的就是最好的"。

### 2.2 "哪些事不让模型管"——Agent 工程化的核心边界（本周最重要架构论证）

设计 §2.5 的职责分配表值得整表背下来：

| 职责 | 归属 | 为什么 |
|---|---|---|
| 历史写入 | **Java 代理后处理** | ① 每轮必然发生的**确定性副作用**交给概率性组件 = "审计依赖被审计者"；② 时机上根本不成立——写入参数含模型最终回答全文，而工具调用发生在回答生成**之前**，模型拿不到自己还没说出的话；③ 拒答/报错轮也要留痕，模型路径覆盖不了 |
| 反馈记录 | 前端直调 REST | 反馈主体是用户不是模型，让模型中转只会失真 |
| 限流/审计/BYOK | Java 前置 | **安全边界必须在不可信组件之前生效** |
| 查询历史检索 | @tool（`search_query_history`） | 这才是模型的判断域：要不要调、何时调、怎么组织回答 |
| W5 点赞→语料 | Java REST + 构建接口 | 触发者是用户点击不是模型 |

**面试一句话**：**读路径、判断密集的给模型；写路径、确定性副作用、安全边界的不给模型**——"不是所有事都该让模型管"，Agent 工程化恰恰体现在划清这条线。

### 2.3 BYOK 的客户端复用：为什么"全局单例换 key"是安全事故不是性能问题

每个 ChatDeepSeek 内部持有 openai SDK client（含 httpx 连接池），不缓存 = 每轮付 TLS 握手税。但**绝不能**用一个全局单例 client 每请求换 `api_key`——SDK 的 key 在构造时绑定，并发请求下两个用户的请求可能带上对方的 key。我们的方案：**按 sha256(key) 前 16 位 + 模型名做键的 LRU 缓存（容量 16）**，不同用户不同实例，auth 隔离天然正确。配套细节：不缓存明文 key 做键（避免明文常驻 dict）、线程锁保护、`None` 走环境变量分支且构造参数与重构前逐字节等价（评测同构的前提）。

### 2.4 SSE 的双层错误语义：为什么"无效 key"只能在流中报

DeepSeek 的 401 发生在第一次对话请求时——那时 SSE 已经 200 开始发送了。提前预检（每轮先 ping 一次）= 每轮多 300-600ms RTT，否决。所以契约是两层：**流前**（HTTP 状态码：403 key_not_set / 429 rate_limited / 503 concurrency_full——前端 fetch 先查 `res.ok`）+ **流中**（`event: error` + 业务码：llm_key_invalid / llm_insufficient_balance（402）/ llm_rate_limited——前端在流里消费）。这个设计直接决定了前端 fetch-stream 而不是 EventSource（后者只支持 GET、不能带 Authorization 头、错误拿不到响应体）。

### 2.5 为什么"审计不能依赖被审计者"是架构原则

历史写入若做成模型工具：模型可以漏调（审计出现空洞）、参数里的最终回答在工具调用时机还不存在、失败轮次无覆盖。Java 代理本来就要逐事件透传（旁路解析零额外成本），顺手落库。**推广到一般**：凡是"必然发生的记录类副作用"，放确定性代码；凡是"取决于语义的决策"，才给模型。这也是对"Agent 万能论"的工程回应——**LLM 是概率组件，系统的正确性不能以概率为地基**。

### 2.6 同构红线：为什么重构必须带着"逐元素全等"的验收闸门

W4 唯一触碰核心的动作是 `prepare_turn` 抽取（main.py 的每轮组装逻辑变成 CLI/FastAPI/评测三方共用的函数）。风险：任何细微行为漂移都会让 W3 基线（41.1%）与 W6 消融失去可比性。闸门：EV-003/017/029 三道固定题的 `injected_chunks` 与 W3 明细 JSON **逐元素相等**（检索全链路确定性保证同 query 必同注入——所以必须全等，不等即回归）。**实测结果：三题全等 PASS**。这是"重构安全性"的教学样板：不是靠小心，是靠机械对照。

## 三、面试考点（四件套）——本周的新弹药类型：工程与安全

### 3.1 "用户的 LLM API Key 你们怎么管理的？"（BYOK 场景题，2026 年新热）

**考察意图**：考密钥管理的工程完整度——只会说"加密存储"的人过不了第二轮追问。

**参考答法（90 秒口语稿）**：
> 我做了一个 BYOK 方案——用户自带 DeepSeek Key，服务端结构性不留站点级 key。全链路六跳：① 前端只存掩码，明文只在 HTTPS 请求体里出现一次；② Java 收到先调 DeepSeek 的 GET /models 免费校验（幂等，可重复触发），**校验不过不落库**——状态机里不存在"已存的无效 key"，省掉一整类处理；③ 落库用 AES-256-GCM（认证加密，密文被篡改解密即报错；IV 每次随机 12 字节——GCM 的 IV 复用是灾难性错误，这条注释在代码里）；④ 主密钥环境注入、缺失拒启；⑤ 对话时 Java 解密后通过**内网头**传给 Python（Docker/本机内网，Python 不发布端口），绝不进 URL——URL 会落访问日志；⑥ 日志里 key 的唯一替身是 SHA-256 前 8 位指纹，上线验收动作是 grep 日志里的 "sk-" 必须为 0。

**结合项目的加分句**：
> "选型时对比过 localStorage 透传方案——服务端零托管确实更'安全'，但它把明文暴露面从录入一次变成每轮请求，还丢掉多设备体验。**安全选型是威胁模型、暴露面、实现成本的三角**，不是越极端越好。"

**可能的追问**：
- "主密钥丢了怎么办？"→ 已存 key 全部不可解，用户重录即可——无数据损失，写进运维手册不做补救代码。泄漏 → 清表 + 通知重录。轮换留了 `key_version` 列的位，V1 不实现（诚实说"知道该怎么做、按成本选择不做"）。
- "Java 到 Python 那段内网为什么不再加密？"→ 防的是宿主机被 root——那个威胁模型下 MySQL 密码、JWT_SECRET 也全丢，单加密 key 是安全剧场。**记录为已知边界**：多机部署时必须升级 mTLS。
- "GCM 为什么比 CBC 好？"→ 内建完整性认证 vs 要自己拼 HMAC。

### 3.2 "限流怎么做的？为什么这么设计？"

**参考答法**：
> BYOK 后 LLM 成本用户自担，但站方仍要防三件事：拿检索层当免费跑批引擎、把 2 核 CPU 打满、刷 DeepSeek 接口。四道闸：对话 10 次/分/用户（人类最快调试节奏的 1.5 倍带宽，脚本滥用无利可图）、全局并发流 ≤4（2 核上每条流 = token 吞吐+检索+查询的物理真相，面试可讲"这不是商业限制是物理限制"）、key 校验 5 次/分（每次校验是一次出站调用，防被当代理）、登录 10 次/分/IP。
> 实现是手写固定窗口（约 40 行）+ AtomicInteger 并发闸。**被否 Bucket4j/Redis**：单实例部署下内存限流已满足事实，Redis 在 2G 服务器上是奢侈品——"生产做法是分布式限流，单机 demo 用固定窗口是成本匹配的选择"。

**可能的追问**：
- "并发的第 5 个请求会怎样？"→ 503 concurrency_full，友好文案"当前使用人数较多"。**finally 里必须 decrementAndGet**——流异常也要放闸，否则 4 次异常后服务永久拒绝服务（这个细节在代码 review 里专门验证过）。

### 3.3 "讲一次你印象最深的线上排障"（本周有三段，任选其一讲透）

**首选：h2c 协议升级头事件**（方法论最完整）：
> 现象：Java 网关调 Python 全部 422，但 curl 直连 Python 一切正常。
> 排查：先对比两边请求差异——curl 用的 HTTP/1.1，Java 用 JDK HttpClient；再上服务器看 uvicorn 日志，抓到关键一行 `WARNING: Unsupported upgrade request`。
> 根因：JDK HttpClient 默认版本是 HTTP/2，对**明文 http://** 地址会发起 h2c 升级（发 `Upgrade: h2c` 头），uvicorn 的 h11 解析器不支持升级请求直接 422。HTTPS 地址不受影响（ALPN 协商正常）——所以本地 curl 测试永远复现不了，只有 Java 发的请求挂。
> 修复：HttpClient 钉死 `Version.HTTP_1_1`（上游是 SSE 逐行分帧，h2c 本就无收益），注释里写清因果链。
> **方法论沉淀**：跨服务问题先二分（哪一段挂）→ 看接收端日志而不是猜发送端 → "只有特定客户端失败"的差异点往往在协议层。

**备选一：fastembed 模型缓存**：服务器上 /agent/chat 整体假死 60s 超时 → 根因是 fastembed 模型缓存在默认路径不存在，运行时向 HuggingFace 下载被国内网络挂死。修复：本地缓存打包上传 + `FASTEMBED_CACHE_DIR` 指向稳定路径 + 源码级 cache_dir 支持。教训：**"首次运行能下载成功"不等于"生产可用"——依赖外网下载的组件必须离线化**。
**备选二：env.prod 变量名冲突**：`MYSQL_PASSWORD` 被 Java（app 账号）和 Python（ro 账号）两个进程抢用 → ro 用户配上 app 密码 → 1045 拒绝。修复：**凭据变量名按消费者拆分**（MYSQL_APP_* / MYSQL_RO_*），并加了回归测试锁"Python 永不读 MYSQL_PASSWORD"。教训：**共享环境变量文件时，命名空间要按消费者划分**。

### 3.4 "为什么用原生部署不用 K8s/Docker？"（部署决策题）

**参考答法**：
> 先说服务器现实：2 核 1.87G、已有宝塔 nginx 承载另一个生产站点、原生 MySQL 8。Docker Desktop 在服务器上不存在，引入 Docker 意味着整套虚拟化开销吃掉 10-20% 内存——在 2G 机器上这是最贵的奢侈品。
> 方案：**原生共存**——nginx 按 server_name 分流两个站点（SSE 的 `proxy_buffering off` 是关键一行，等价 Caddy 的 flush_interval）；两个服务各一个 systemd 单元（内存上限 450M/550M 用 MemoryMax 封顶——任何单服务失控只 OOM 自己不拖死整机）；证书 certbot webroot 自动续期。
> **被否 Caddy**：设计时推荐它（证书零运维），但服务器 80/443 已被宝塔 nginx 占有，双 nginx 共存无意义——**方案要服从现场，不是文档**。
> 内存账本是逐项记账的：MySQL 450 + Python 450 + Java 550 + nginx 30 ≈ 1.48G + swap 2G 兜底。**部署验收动作是 docker stats/free 实测回填，不是照抄设计数字。**

**可能的追问**：
- "那什么时候该上容器/K8s？"→ 多机一致部署、独立扩缩容、滚动发布需求出现时；现在单机双站、个位数并发，systemd 是成本匹配解。
- "SSE 经 nginx 要注意什么？"→ `proxy_buffering off`（否则事件被缓冲到响应结束才到浏览器，打字机效果全灭）+ `proxy_read_timeout` 拉长（流可能静默数十秒）。

### 3.5 "JWT 无状态方案有什么问题？"（诚实边界题）

**参考答法**：
> 我的方案是 access 2h + refresh 7d 双 token、无状态校验。**已知限制：无状态 refresh 无法服务端吊销**——登出只是客户端丢弃，token 在剩余有效期内仍然有效。demo 规模接受；需要吊销时的正确做法是 refresh token 落库（登录写行、刷新校验并旋转、登出删行），代价是多一张表和一次查询。
> 应急手段：JWT_SECRET 整体轮换强制全员重新登录。
> SSE 有个交互细节：流建立后 token 过期不会中断流（鉴权只在建流时）——前端对策是进对话页前本地 exp 预检、剩 5 分钟内先静默刷新。

### 3.6 "你们前后端怎么分工的？为什么这么切？"（架构观题）

**参考答法**：
> 切分原则是"语言贴近职责"：Java 承担它擅长的（身份、密钥加密、审计、限流、SSE 代理——企业工程层），Python 承担它的生态优势（LangChain/检索/推理——AI 层）。中间用 SSE 头透传连接。
> 这也是国内大厂的真实分工——"Python 做大脑、Java 做工程化"。我简历上是全栈，这个项目让我两边都写了：Java 侧最难的其实是 SSE 代理的流式语义（逐行读逐行写每事件 flush），Python 侧最难得的是同构闸门保证的重构安全。
> **一条边界原则贯穿始终**：模型的输出是概率性的，所以它只出现在"回答生成"这个环节；所有需要确定性保证的环节（审计、限流、密钥）都在它之外。

## 五、动手实验（五要素）

### 5.0 工具速查

线上环境：浏览器直接访问 https://sql.shanghl.club（真实 BYOK 流程）。本地联调：`uvicorn agent.server:app --port 8000` + `cd backend && mvn spring-boot:run -Dspring-boot.run.profiles=dev`（先 source ../.env）。

### 5.1 实验一：完整 BYOK 用户旅程（产品视角）

- **验证目标**：以真实用户身份走通"注册→录 key→对话→反馈"全流程，感受错误路径的文案
- **操作**：线上注册新账号；设置页先录一个假 key（故意）；再录真 key；对话"上个月 GMV"；对回答点赞；历史页点开抽屉看 SQL
- **预期现象**：假 key → 红字"Key 无效或已被删除"且**不落库**（再录真 key 时状态干净）；对话时 ⚙ 指示行先出现、完成后变成可折叠"已执行 SQL"；点赞后刷新历史，状态仍在
- **思考题**：为什么录假 key 时要"不落库"而不是"落库标记无效"？（状态机的状态越少越安全——"无效但存在"的 key 需要在对话路径上再处理一次，而它永远不可能成功）

### 5.2 实验二：亲手触发三层限流（防御面体验）

- **验证目标**：限流不是文档里的数字，是可触发的行为
- **操作**：本地起双服务后，用循环脚本 30 秒内连发 15 次对话请求（同一账号）
- **预期现象**：第 11 次起收到 429 `rate_limited`；再开一个终端并发 5 个对话，第 5 个收到 503 `concurrency_full`
- **背后机制**：固定窗口按 `chat:{userId}` 计数；并发闸是 AtomicInteger，503 后 finally 释放——去看 ChatProxyService 的 `gate.exit()` 调用位置（两处异常路径都调了）
- **思考题**：如果把并发闸放在 Python 侧而不是 Java 侧，有什么区别？（Python 侧只能挡住"进入 agent 的处理"，挡不住已建立连接占用的传输资源；且 Python 无用户身份，只能全局计数——**限流必须在有身份语义的网关层**）

### 5.3 实验三：模拟主密钥丢失（灾难演练）

- **验证目标**：理解 BYOK 的灾难恢复模型
- **操作**：本地 dev 环境重启两次服务（dev 下每次生成**临时随机**主密钥）
- **预期现象**：第一次录入的 key 在重启后对话报"主密钥不匹配，请联系管理员重置 key"（AEADBadTag → 业务码）——**这就是"换环境忘迁 BYOK_MASTER_KEY"的现场模拟**
- **背后机制**：GCM 的认证加密保证"错误密钥解密"不是返回乱码而是直接抛异常——这是选择 GCM 而非 CBC 的实战收益
- **思考题**：dev 宽松（随机主密钥）与生产 fail-fast 的语义分歧为什么合理？（开发机丢密钥无损失，重启代价最小化；生产丢密钥 = 全员重录，必须防呆）

### 5.4 实验四：SSE 断线行为（前端韧性）

- **验证目标**：观察三层断线处理的差异（用户主动停止 / 网络中断 / 服务端错误）
- **操作**：对话进行到一半分别：a) 点停止按钮；b) 开发者工具切 Offline；c) （难模拟）等 llm 错误
- **预期现象**：a) 消息标"已停止"，服务端历史落 status=3；b) 已收文本保留 + "连接中断可重试"；c) error 事件按文案映射，无 done 无 saved（反馈按钮不出现）
- **背后机制**：前端 AbortController → 服务端 ClientAbortException → Java 落 status=3 → Python 生成器被断连守卫干净关闭（这是 T2 实测发现 GeneratorExit 不投递后加的守卫——设计假设被实测推翻的案例）
