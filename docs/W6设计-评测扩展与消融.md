### 0.3 设计总原则（延续 W3）

1. **消融行的数字必须可比**：同语料、同数据快照、同判定器、同 runs 口径——任何一行在这些维度上不同源，Δ 就是废数字（§3.5 语料冻结纪律）。

3. 每个决策带理由和被否备选；API 细节不确定的进 §8 验证清单，禁止编造。

## 1. 前置修复：判定器 v2.1（消融数字的地基）

### 1.1 修复一：无序比较排序键数值化分桶（W3 审查 P2-1）

**问题**（现行 `judge.py::_row_sort_key`）：`ordered=false` 的多重集合比较，排序键对 Decimal 单元格用 `str(cell)`。字符串序与数值序不一致（`'11' < '9.996'`），当金标与模型两侧的等值数值**格式不同**（`9.996` vs `10`，在容差内相等）且集合内还有其他行时，两侧排序错位、逐位配对配错行 → **假阴性**（把该判过的题判 fail）。

可复现的假阴性用例（T1 的回归测试就写它）：

```
金标 = {9.996, 11}，模型 = {10, 11}（9.996 与 10 满足容差 max(0.005, 1e-3×10)=0.01）
现行：两侧 str 排序 → 金标 [11, 9.996] vs 模型 [10, 11] → 首对 (11 vs 10) 不等 → fail（错）
修复后：数值排序 → [9.996, 11] vs [10, 11] → (9.996~10 ✓) (11=11 ✓) → pass（对）
```

**修复实现**：`_row_sort_key` 的 Decimal 分支改为数值序为主键、字符串仅做数值相等时的稳定决胜：

```python
def key(cell):
    if isinstance(cell, Decimal):
        if cell.is_finite():
            return (0, cell, str(cell))   # 数值序为主；str 只在数值相等（如 1.0 vs 1.00）时保证顺序确定
        return (0, Decimal("0"), str(cell))  # NaN/Inf 不进数值序（Decimal 排序会抛 InvalidOperation），按 str 决胜
    if isinstance(cell, str):
        return (1, cell)
    return (2, "" if cell is None else str(cell))
```

类型标签分桶（0/1/2）保持不变——同一列金标是 Decimal、模型是 str 时仍能排序不抛 TypeError。修复只动排序键，**逐位比较仍走 `_cells_equal` 的容差公式，容差规则本身不动**（0.0775 vs 0.0886 依然判不等，陷阱不放行）。

- **被否备选一：按容差网格分桶（如统一 round 到 3 位小数再排序）**。容差是相对的（1e-3×max|a|），固定网格无法表达相对容差，且网格边界两侧的相邻值会人为分裂，引入新的人工产物；数值直排 + 逐位容差比较是最小正确修复。
- **被否备选二：改成真正的多重集合匹配（对每行找容差内匹配后消去）**。容差"相等"不满足传递性，多重集合相等在数学上就没有良定义；数值排序后逐位配对就是该语义下的规范操作（greedy matching），且我们数据里陷阱值与金标差异 ≥20%、容差 1e-3 相对量级，greedy 即最优。写进 v2.1 语义注释。
- `ordered=true` 路径（不排序）与文本回退路径（无排序）不受影响；`classify_failure` 是单值比较，无排序，不受影响。

### 1.2 修复二：金标年份类小整数规避（W3 审查 P2-2，命题纪律）

**问题**：答案级回退（`extract_number_candidates`）从最终回答文本抽取**全部**数字候选，而回答文本几乎必含日期碎数（"数据快照截至 2026-09-30"、"2026 年 9 月"→ 候选 2026、9、30）。若某题金标恰好是这些环境数字（单值整数落在 1–31 或 1900–2100），SQL 级 fail 的题会被文本回退**巧合误判过**。

**决策：命题纪律规避 + verify_gold 自动检查，不动 judge。** 理由：judge 侧"智能忽略年份候选"（如识别"数字+年"上下文）需要 NLP 级启发式，脆弱且会引入新误判面；而我们完全控制命题，把金标设计成天然安全形态是零成本根治。新增命题纪律（并入 §2.4 纪律清单）：

> **年份窗口纪律**：纯整数的单行单列金标，值不得落在 1–31（月/日碎数）或 1900–2100（年份）区间。规避手法：①优先设计成带小数的量（金额/比率/均值——如 16,029,955.34 天然安全）；②或改多行题（多行不走文本回退，规则 4 天然免疫）；③确需纯整数计数时选大数值（如 5,639、4086，远离窗口）。

verify_gold 新增自动检查（T1）：逐条重放金标，凡"单行单列数值金标 ∈ [1900,2100] 整数"直接报错拦下；"∈ [1,31] 整数"给出警告人工确认（该窗口存在合法答案，如某类目商品数 8，但须确认答案文本不会同时出现同值环境数字）。现有 30 条扫描结论：无一条金标落入窗口（金额/比率类天然安全，计数值如 4,086/5,639 均远离）——**该纪律只约束新 20 条**。

### 1.3 修复后的 W3 基线复判：离线 rejudge，不重跑 LLM

**决策：新增 `eval/rejudge.py`，对 W3 三份 detail JSON（baseline_full_v2 / no_rag_control_v2 / multiturn_v2）离线复判，不重新调 LLM。**

- **可行性**：detail JSON 逐题存了 `sql_used`（全文）、`sql_calls`（全序列）、`final_answer_text`（最后一条 AIMessage 全文）；`ordered`/`standard_wrong` 从数据集按 id join 回来。判定是"给定 SQL 文本 + 金标重放 + 文本"的确定性函数——不需要 LLM 就能完整复现。
- **被否备选"重跑 W3 全量 LLM 验证数字不变"**：LLM 运行本身有大方差（W3 实测 r1=30.0% / r2=43.3% / r3=50.0%），重跑出来的数字变化混叠了"判定修复效应"与"运行间方差"，无法归因；离线复判把判定器变化这个单一变量干净隔离。且零 LLM 成本、分钟级跑完。
- rejudge 输出：`docs/rejudge_v2.1.md`——逐条翻转表（id / run / 旧判定 / 新判定 / 翻转原因行）+ 前后汇总数字对照。
- **数字处置（两种结果都有预案）**：
  - **零翻转** → W3 数字在 v2.1 下稳健，日志记一句"复判 132 次运行零翻转"（这本身是加分声明）；
  - **有翻转** → W3 基线数字按复判结果**诚实更新**并在 experiment-log 记录翻转清单与成因——"评测器自己也要被审计"是 W3 已验证的面试素材的续篇，不是丑闻。简历引用的 W3 数字同步改为复判后口径。
- 判定器版本记号升为 **v2.1**（无序比较排序键数值化），写进 judge.py 模块 docstring 与报告声明段；此后所有 W6 数字均为 v2.1 口径。

### 1.4 与 baseline_50 的关系

复判解决"W3 旧数字是否被误判"；但**消融矩阵的对照原点必须是全新跑的 `baseline_50`**（50 条 × 3 runs），不复用 30 条旧运行 + 20 条新运行的拼接——理由：①消融行全部是新跑，基线行若混入 10 月 10 日的旧运行，服务端模型/网络的时段差异成为未控变量；②50 条口径与 30 条口径本就不可比（题型分布变了）。W3 的 41.1%/64.4% 保留为历史数字（标注数据集版本），W6 简历数字以 50 条口径为准。

## 3. 消融矩阵设计（简历数字的核心）

### 3.1 总体策略：OAT（One-Factor-At-a-Time），不做全因子

**决策：每行相对 baseline_50 只改一个变量（OAT），不做全因子。**

- **理由一：归因清晰是第一需求**。简历数字是"各优化项贡献拆解"，面试追问"这个 +X 个点你怎么知道是 rerank 带来的"——OAT 的每一行 Δ 都可单变量归因；全因子里任何一格的差值都是多变量交互的混叠，解释成本高于信息收益。
- **理由二：成本**。全因子 top_n(3) × k(2) × BM25(2) × rerank(2) × few-shot(2) = 48 格（含 baseline 一格），减去无意义组合仍 20+ 格 × 3 runs × 50 题 ≈ 3000+ 次 LLM 运行，挂机 25-75 小时、且大量格子没有预注册假设——跑出来解释不了，是为跑而跑。
- **理由三：交互效应是二阶小量**。语料仅 28 片、单变量预期效应量在 5-15pp 量级、run 间方差本身 ±5-10pp（W3 三 run 极差 20pp）——这个信噪比下交互项大概率测不出来，预注册时就承认。
- **被否备选"全因子 + 只报主效应"**：既然只报主效应，全因子相对 OAT 的唯一收益是交互项，而交互项我们测不动——成本白花。
- **预注册对齐**：W2 §3.4 预注册的变量集（top_n ∈ {5,8,12}、k ∈ {10,60}、有无 BM25）全部纳入 OAT 行；rerank 与 few-shot 是 W6 新增变量（rerank 来自需求 §5 P1 承诺，few-shot 来自 W3 发现 2 的动机实证）。

## 4. Rerank 实现（消融的新变量）

### 4.1 新模块 `agent/rag/rerank.py`

- **API**：SiliconFlow `POST {SILICONFLOW_BASE_URL}/rerank`（默认 `https://api.siliconflow.cn/v1`），Bearer 认证；请求 `{model, query, documents: [str], top_n, return_documents: false}`，响应 `results: [{index, relevance_score}, ...]` 按 relevance_score 降序。模型 `BAAI/bge-reranker-v2-m3`（需求 §5 定案）。**具体字段名以 §8-1 的 curl 冒烟实测为准，禁止照抄本文档编码**。
- **配置**（config.py 新增，均带默认值）：`SILICONFLOW_API_KEY`（空=禁用 rerank）、`SILICONFLOW_BASE_URL`、`RERANK_MODEL="BAAI/bge-reranker-v2-m3"`、`RERANK_POOL=16`。开发机 .env 提供 key；**服务器 .env 不配**（§4.4 决策的自然落地——线上想开也没 key）。
- **HTTP 库**：复用仓库既有依赖（server.py 已用 httpx 则用 httpx；§8-6 确认），不新增依赖。
- **失败语义**：rerank 调用异常（网络/429/超时）**不吞不降级**——沿 runner 既有题级 try/except 落 `error: invoke_exception`，明细记录 error_detail；该行报告若 error>0，用 `--rerun` 补跑失败题。被否"fail-open 回退 RRF 顺序"：静默降级会让 F 行部分题实际没 rerank，消融变量失控；宁可显式 error 重跑。
- **重试**：单次内部重试一次（指数退避），仍失败即抛。

### 4.2 hybrid_retriever 的 rerank 钩子

`search()` 尾部插入可选重排段（伪码）：

```
fused = rrf_fuse([*bm25_ranked, *dense_ranked], self.k, top_n= rerank_pool if reranker else top_n)
chunks = [...]（现行为：直接取 fused 前 top_n）
if reranker is not None and rerank_pool > 0:
    ranked = reranker.rerank(query, [该片文本 for 片 in fused[:rerank_pool]], top_n=top_n)
    chunks = [对应 fused[index] 的 chunk for index, score in ranked]（rerank score 写入 rrf_score 字段位置，明细可区分）
```

- **候选池 16 = 2×top_n 的理由**：pool=8 时重排只能在原 top-8 内换序，**Recall 不可能提升**（救不回 RRF 排 9-16 名的相关片）——而 rerank 的核心假设正是"RRF 排位低但语义相关"（发现 3 的 schema 片），池必须大于注入数；2× 是重排实践的常规起点，池再大则 rerank token 线性涨而边际收益递减。
- **重排对象是融合后的并集排名而非单路**：保住混合检索的贡献叙事（"rerank 是对混合检索的精修"），也避免"rerank 单独接向量路"引入第二变量。
- **线上不接线**：`prepare_turn` 仅在收到 `retrieval_opts` 时传 reranker（评测 runner 专属路径），CLI/FastAPI 组装零变化。

### 4.3 成本估算

- 调用量：F 行 150 次 prepare_turn（50 题 × 3 runs，多轮复跑另加 12 次）→ 每次调 rerank 一次。
- 每次调用 token：query ≈30 + 16 片 × 平均 350（schema 片偏长、glossary/qa 偏短）≈ **5.6k tokens**。
- 合计 ≈ 0.84M rerank tokens + 12 次多轮。按 SiliconFlow rerank 模型"千 token 计费"的公开计费模式（单价以官方价目页为准，§8-2 实测回填旁注），量级 **< ¥1**——成本不构成决策变量。
- 延迟代价（对评测 P95 的影响如实记录）：rerank 每问 +0.3-1s 网络往返，F 行 P95 预计高于基线，报告中如实呈现（这是"线上要不要开"的输入之一）。

### 4.4 BYOK 冲突与"线上暂不启用"的决策

**决策：W6 rerank 只在评测侧（开发机）启用，线上不启用。** 理由三条：

1. **BYOK 架构原则**（需求 v1.3 §3 P1）："线上部署后 LLM API Key 由用户在界面输入并绑定账号，服务端不内置站点级 Key"。rerank 用的 SiliconFlow key 若由服务端内置，等于在刚立起来的原则上开洞——要么逼用户再注册一家 SiliconFlow 填第二个 key（交互与教学成本高，且 rerank 用户无感知），要么服务端内置（违例）。
2. **收益未证**：rerank 的 Δ 要等 F 行跑完才知道；若 Δ 不显著，线上启用是纯负担。消融先行、证据后行，是本项目"先测基线再优化"方法论的又一次应用。
3. **资源与延迟预算**：2C2G 服务器上每问 +0.3-1s 网络往返叠加在 P95 7.4s 之上；W3 延迟已是最弱指标。

**若 F 行 Δ 显著的后续路径（W7+ 候选，不在 W6 范围）**：①本地 ONNX rerank（bge-reranker 系列有 ONNX 版）——零 API 成本、离线、与 fastembed 技术栈呼应，但要验证 2C2G 内存放得下（模型 ~1GB 级，风险真实存在）；②BYOK 扩展为多 provider key（用户可选填 rerank key）——交互改造，等真实需求。**被否备选"W6 直接上线 rerank"**：上述三条理由的逆序叠加，且违反"12 月前不加 P2 负担"的砍法原则。
